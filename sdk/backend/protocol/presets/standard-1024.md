# 标准 1024 压力帧（32×32）

**JSON 预设**：[`standard-1024.json`](standard-1024.json) ✅ 系统可直接加载

这是整个系统里最常用的一种帧格式。坐垫（`sit`）、靠背（`back`）、头枕（`head`）三条串口通道
默认都按它解析，大部分 32×32 传感器（`car` / `sofa` / `carQX` / `volvo` / `wholeChair` / `humanBody` …）走的都是它。

## 帧结构

```
┌──────────────┬──────────────────────────────────┐
│ AA 55 03 99  │ 1024 × uint8                     │
│ 分隔符 4B    │ 压力点，0~255                     │
└──────────────┴──────────────────────────────────┘
```

| 项 | 值 |
| :--- | :--- |
| 分隔符 | `AA 55 03 99`（十进制 `170 85 3 153`） |
| 分帧方式 | 按分隔符切分，**分隔符不保留在帧内** |
| 有效载荷 | 1024 字节 |
| 数据类型 | `uint8`，一个字节一个点 |
| 点数 | 1024（32×32） |
| 默认波特率 | 1000000 |
| 校验 | 无。只靠帧长 1024 判断有效性 |

分隔符在传输里的位置其实是**帧尾**（上一帧数据 + 分隔符 + 下一帧数据……），
但 `DelimiterParser` 吐出来的是两个分隔符之间的那段，所以对使用者来说等价于「载荷 1024 字节」。

## 字节序说明

单字节类型没有字节序问题。第 0 个字节是矩阵的第 0 个点，第 1023 个字节是最后一个点。
**点序不等于显示顺序** —— 每种传感器的物理走线不同，从 ADC 顺序映射到屏幕坐标是线序表的事
（`backend/processing/lineOrders.js`），协议只负责把 1024 个数字取出来。

## 波特率不对怎么办

1000000 是这个协议家族的默认值，但同一格式的传感器有跑 921600 的。
预设里的 `protocol.baudRate` 是**最需要按实际硬件改**的字段，改了不影响分帧和解码。
若不确定，接上后看有没有连续出帧：波特率错了通常表现为完全收不到帧或帧长杂乱。

## 排错

| 现象 | 一般原因 |
| :--- | :--- |
| 收不到任何帧 | 波特率不对，或分隔符不是 `AA 55 03 99` |
| 帧长不是 1024，忽长忽短 | 波特率不对，或线路干扰 |
| 有数据但矩阵是乱的 | 协议解对了，线序表不对（不是本文档的范畴） |
| 整块常量值不变 | 传感器没供电 / 采样电路没工作 |
