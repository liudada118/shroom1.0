# 低密度坐垫 72 / 144 点

**JSON 预设**：[`low-density-72.json`](low-density-72.json) / [`low-density-144.json`](low-density-144.json) ✅ 系统可直接加载

低密度坐垫的两个帧长共用一个处理函数。它们**只靠帧长区分**，此外完全一样。

## 帧结构

```
┌──────────────┬───────────────────────────┐
│ AA 55 03 99  │ 72 或 144 × uint8         │
│ 分隔符 4B    │ 压力点，0~255              │
└──────────────┴───────────────────────────┘
```

| 项 | 值 |
| :--- | :--- |
| 分隔符 | `AA 55 03 99` |
| 分帧方式 | 按分隔符切分，分隔符不保留 |
| 有效载荷 | 72 **或** 144 字节 |
| 数据类型 | `uint8` |
| 点数 | 72 或 144 |
| 默认波特率 | 1000000（这些类型在传感器表里没有显式波特率，走默认值） |
| 校验 | 无 |

判定就是一行：

```js
if (buffer.length !== 72 && buffer.length !== 144) return null;
```

## 矩阵形状不在协议里

这是这两个预设和其它预设的关键区别：JSON 里 `"matrix": null`。

72 和 144 在传感器表（`backend/sensors/registry.js`）里**没有对应的矩阵定义**——
表里只有 32×32（1024）、16×16（256）、64×32（2048）、15×12（180）、10×9（90）、10×10（100）这几种。
也就是说，72 点摊成 12×6 还是 9×8、144 点摊成 12×12 还是 16×9，
是由展示配置决定的，协议层只保证「取出 72 个数字」。

用这两个预设时，波特率和解码会自动填好，**矩阵宽高得自己填**。

## 零点扣除

处理器只负责解码这 72/144 个点；统一输出边界随后按完整 channelId 记录未扣零源帧并应用
该通道的 processed baseline。零点是运行时状态，不是协议内容；刚开机没有捕获基准时读数可能整体偏高。

## 代码位置

| 想看什么 | 位置 |
| :--- | :--- |
| 帧处理 | `backend/extensions/built-in-sensors/legacyGenericMatrixFrameProcessor.js` 的 `processLowDensitySitFrame` |
| 矩阵定义（**这里没有 72/144**） | `sdk/backend/sensors/registry.js` |

## 排错

| 现象 | 一般原因 |
| :--- | :--- |
| 一帧都收不到 | 波特率不对 |
| 帧长是 72 但选了 144 的预设 | `valueCount` 不匹配，`decodeProtocolValues` 读不满会得到不完整结果 |
| 界面矩阵形状明显不对 | `matrix` 没填或填错 —— 协议不负责这个 |
| 读数整体偏高 | 没做零点 |
