# 触觉手套双包（130 + 146，含 130/142 + 146/158 分段变体）

**JSON 预设**：❌ 没有，而且**短期内也做不出来**。一帧数据要靠两个包拼，
现有 schema 没有任何跨帧组装的概念，见 [schema 缺口](#schema-缺口)。

一只手的 256 点压力被拆成两个串口包发。谁跟谁配对靠包内的**手侧字段**，不靠时间顺序 ——
左右手可以交替进来。

## 包结构

**首包 130 字节**

```
偏移   0      1      2 ──────────────── 129
     ┌──────┬──────┬────────────────────┐
     │ order│ 手侧 │ 128 × uint8 压力前半 │
     └──────┴──────┴────────────────────┘
      1B     1B     128B                  = 130B
```

**尾包 146 字节**

```
偏移   0      1      2 ────────── 129   130 ────────── 145
     ┌──────┬──────┬────────────────┬──────────────────┐
     │ order│ 手侧 │ 128 压力后半     │ 16B IMU          │
     └──────┴──────┴────────────────┴──────────────────┘
      1B     1B     128B              16B                = 146B
```

| 字段 | 偏移 | 长度 | 说明 |
| :--- | ---: | ---: | :--- |
| `order` | 0 | 1 | 分片序号。分段变体里 `order == 1` 表示首包 |
| `packetType`（手侧） | 1 | 1 | **1 = left，2 = right**（`PACKET_SIDE_BY_TYPE`），无法识别时用调用方给的 `fallbackSide` |
| payload | 2 | 余下 | `bytes.slice(2)` |
| IMU | 尾部 -16 | 16 | **只有尾包有** |

| 项 | 值 |
| :--- | :--- |
| 包长 | 首包 130，尾包 146（严格相等判定，不匹配返回 `null`） |
| 拼出的压力点数 | 128 + 128 = **256** |
| 默认波特率 | 921600 |
| 校验 | 无 |

## 拼包规则

解析器内部按 `left` / `right` 各存一份首包缓存：

- 收到 130：`chunks[side] = bytes.slice(2)`，**不输出帧**（返回 `complete: false`）。
- 收到 146：取出 `chunks[side]` 作为前半，本包 payload 去掉尾 16 字节作为后半，
  拼成 256 点，**清空该手侧缓存**，返回 `complete: true`。

两个后果值得记住：

1. **缓存是按手侧分开的**，所以左手首包和右手尾包不会串在一起。
2. **丢包会自愈但会吞一帧**：首包丢了，尾包会拿一份空的（或上一轮残留的）前半去拼。
   代码在拼完后总是清空缓存，所以错位不会无限传播，但那一帧的前半是错的。

解析器实例**必须和运行时链路一一绑定** —— 两条链路共用一个实例会互相抢缓存。

## 与 274 整包的手侧约定相反

这个协议是 `1 → left`、`2 → right`。
[整包 274](hand-glove-full-packet-274.md) 里那个（未被调用的）`getHandGloveFullPacketSide`
是 `1 → right`、`2 → left`，**正好反过来**。两个协议不要互相照抄。

## 分段变体：130/142 首包 + 146/158 尾包

另有一套更旧的分段协议，包头结构相同（`order` + `type` + payload），但长度多两种：

| 包 | 长度 | 说明 |
| :--- | :--- | :--- |
| 首包 | 130 **或 142** | `processBack130Segment` 用 `order == 1` 判首包，不是靠长度 |
| 尾包 | 146 **或 158** | 都从尾部拆 16 字节 IMU |

**158 字节尾包有一个额外语义**：它会让运行时进入 `rawPressureMode: 'pressure'`，
于是入库的 `rawPressureData` 存的是**标定后的压强**而不是原始 ADC：

```js
rawPressureMode: buffer.length === 158 ? 'pressure' : undefined
```

这条不是显示差异而是**存储内容差异** —— 用 158 尾包采的数据和用 146 尾包采的数据，
数据库里同一列的含义不一样。做数据分析时必须知道当时接的是哪种。

## schema 缺口

| 缺什么 | 具体挡在哪 |
| :--- | :--- |
| **跨帧组装** | 一帧压力来自两个串口包，schema 是一帧进一帧出 |
| `decoding` 支持多字段 | 尾包里压力段和 IMU 段类型/位置不同 |
| 按字段值路由 | 手侧要靠 `bytes[1]` 分流到不同缓存 |

补法（三条都要）：加 `assembly: {sideKeyOffset, orderOffset, chunkCount}` 之类的分片声明，
`decoding` 改字段数组，再允许 `assembly` 按字段值分组。这是本目录里离配置化**最远**的一个协议。

## 排错

| 现象 | 一般原因 |
| :--- | :--- |
| 压力矩阵一半是旧数据 | 首包丢了，尾包拿残留前半拼的（见拼包规则 2） |
| 左右手数据互相污染 | 两条链路共用了同一个解析器实例 |
| 左右手反了 | `packetType` 与硬件约定不符，或走了 `fallbackSide` |
| 只收到包但从不出帧 | 只有 130 没有 146（或反之），长度判定严格相等，差一个字节就整包丢弃 |
| 历史数据的压力列量纲不对 | 采集时用的是 158 尾包，存的是压强不是 ADC |
