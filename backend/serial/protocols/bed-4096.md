# 大床 4096 压力帧（64×64）

**JSON 预设**：[`bed-4096.json`](bed-4096.json) ✅ 系统可直接加载

和[标准 1024 帧](standard-1024.md)**用同一个分隔符**，只有帧长和波特率不同。
所以这两种协议在同一根线上是无法靠分隔符区分的 —— 系统靠传感器类型名加帧长来判定。

## 帧结构

```
┌──────────────┬──────────────────────────────────┐
│ AA 55 03 99  │ 4096 × uint8                     │
│ 分隔符 4B    │ 压力点，0~255                     │
└──────────────┴──────────────────────────────────┘
```

| 项 | 值 |
| :--- | :--- |
| 分隔符 | `AA 55 03 99`（与标准帧相同） |
| 分帧方式 | 按分隔符切分，分隔符不保留 |
| 有效载荷 | 4096 字节 |
| 数据类型 | `uint8` |
| 点数 | 4096（64×64） |
| 默认波特率 | **3000000** —— 全系统最高 |
| 校验 | 无 |

## 帧长不是唯一条件

后端的判定是**两个条件同时成立**：

```js
if (!String(context.file || '').includes('bed4096') || buffer.length !== 4096) return null;
```

传感器类型名必须包含 `bed4096`（`bed4096` / `bed4096num` 都算），**光帧长对不算**。
这意味着：把一个 4096 字节帧喂给一个不叫 `bed4096*` 的传感器类型，帧会被静默丢弃。
用预设时要连传感器类型一起选对。

解出的 4096 点会过一次 `zeroLineMatrix(frame, 64)` 做断线修补，那是处理层不是协议层。

## 3M 波特率的现实约束

3000000 不是所有 USB 串口芯片都支持。丢帧率高、帧长忽大忽小，先怀疑芯片和线材，
再怀疑配置 —— 这个波特率下线材质量的影响比其它协议明显得多。

## 代码位置

| 想看什么 | 位置 |
| :--- | :--- |
| 帧处理 | `backend/sensors/runtime/legacyGenericMatrixFrameProcessor.js` 的 `processBed4096Frame` |
| 传感器定义 / 波特率 | `backend/sensors/registry.js` 的 `bed4096`、`bed4096num` |
| 断线修补 | `backend/processing/matrixTransforms.js` 的 `zeroLineMatrix` |

## 排错

| 现象 | 一般原因 |
| :--- | :--- |
| 一帧都收不到 | 波特率不是 3000000，或 USB 芯片不支持该速率 |
| 偶发丢帧 | 3M 下的线材/驱动缓冲问题，不是配置问题 |
| 有帧但界面没数据 | 传感器类型名不含 `bed4096`，帧被前置条件挡掉了 |
| 矩阵只填了四分之一 | `valueCount` 按 1024 填了，应为 4096 |
