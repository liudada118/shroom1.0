# Shroom 产品埋点说明与补齐规范

实施进度：2026-10-29 已完成采集终态/修订发件箱和共同投递质量的技术链路，配套本地接收端支持 v2；详见[实施记录](telemetry-implementation-20261029.md)。有效区间、完整业务分母及客户试点等未实施项仍按本文目标验收。

更新日期：2026-10-29。适用对象：产品、客户端、后端、数据分析与测试人员。

当前结论：主要业务流程已有埋点，但异常终态、有效时长、功能可用分母和跨阶段关联仍有缺口。现有事件可以支持部分使用统计与排障，尚不能直接支撑完整的功能转化、客户留存和 Agent 价值分析。

产品决策边界：有效操作、业务任务完成和增量收益分开评价。先选定一种客户场景、一个决策问题和一条最小链路做真实试点，验证数据能支持一次产品行动后再扩围。除顶部实施记录明确列出的技术能力外，以下新增的场景、指标、决策规则与验收要求均为待验证设计，不代表客户需求已确认或试点已通过。

除顶部实施进度外，本文中的“现有”保留本轮实施前的核对基线；“待补齐”指完整产品与技术目标，最新代码状态以实施记录为准。源码能力不等于客户安装版已具备，也不等于生产服务已接收。生产覆盖需要按实际宿主、网页和服务端版本验收。

## 1 产品目标与统计范围

| 产品问题 | 需要的证据 | 支持的决策 |
| --- | --- | --- |
| 客户是否完成了核心工作 | 场景任务要求、有效操作、最终结果和任务验收证据 | 区分操作成功与实际价值交付 |
| 功能使用率为什么低 | 场景适用性、使用机会、功能可用、曝光、尝试、结果与反馈 | 分别验证需求、授权、入口、交互和功能问题 |
| 哪些展示能力值得投入 | 默认或主动选择、可比任务的完成效率、返工、可读性与复用 | 比较数字矩阵、点图、热力图等能力的任务价值 |
| 哪些流程最容易失败 | 同一次操作的尝试与终态、失败阶段、错误码和版本 | 安排可靠性改进 |
| Agent 是否帮助客户完成工作 | 全部已发起任务的结果、成果采用、人工返工及可比任务耗时 | 分别判断任务可靠性、采用和效率收益 |
| 客户是否减少使用 | 固定客户群、预期使用周期、有效使用、权限与可观测状态 | 形成需核实的客户跟进线索 |

默认按客户公司统计，安装实例用于定位设备侧行为。没有员工身份体系时，不把安装数、会话数解释成人数。行为事件只能说明发生了什么，放弃原因仍需客户反馈。

本规范覆盖 Electron 桌面应用、其本地后端与 Agent 的产品使用事件。原始传感器数据、聊天同步、模型请求分别遵循各自通道和设置。独立浏览器没有 Electron 桥时，当前前端记录函数会静默跳过，不能默认纳入桌面埋点覆盖。

### 1.1 分场景的价值定义

以下为待用真实任务校准的场景目录。有效操作是技术事实；业务任务完成还须满足执行前约定的任务要求；增量收益须有可比基线。非空保存、消费一帧、生成文件均不能单独证明业务任务完成。归零帧可有业务意义，不能把压力非零作为通用有效条件。

| 场景 | 客户要完成的任务 | 任务完成的验收证据 | 使用机会与复用周期 |
| --- | --- | --- | --- |
| S01 短时测量 | 在指定系统与通道完成一次测量并取得可用结果 | 所需阶段与通道的数据满足预定新鲜度、稳定性及结果要求，结果可读，并由任务脚本或客户确认可用；不套用每周 5 分钟门槛 | 一次计划测量为一次机会；按下次计划测量观察复用 |
| S02 连续监测 | 在计划区间持续观察或后台采集 | 满足预定监测区间、必要通道、有效覆盖比例及最长允许中断；展示与后台采集分别核对，若要求存储还需核对最终记录 | 按约定班次、天或监测周期；临时停机与非计划时段不自动算流失 |
| S03 实验采集 | 完成计划中的实验段或测量组并保存可分析记录 | 要求的记录组、时间范围、通道与必要结构齐全，最终保存证据和本地读取一致；一行非空数据不自动代表整次实验完成 | 按实验计划；重试仍归同一任务，下一次独立实验才是新机会 |
| S04 历史分析 | 查看指定记录片段并完成约定分析 | 目标片段真实消费，必需的选区、测量或分析结果可用并满足任务要求；无需强制播放整条记录 | 按实际分析任务；仅打开历史列表不算任务完成 |
| S05 数据交付 | 将指定记录按要求导出供后续使用 | 要求的文件与记录范围全部生成、可读、行数和结构满足约定；允许部分交付须在任务开始前约定，不能事后降低要求 | 按交付计划；不需要导出的监测任务不进入导出漏斗 |

Agent 是完成上述任务的一种方式；只有确有独立目标时才另建场景，不因生成了成果就另算一次客户任务。某次操作技术成功而场景要求未满足时，保留操作成功事实，任务标为未完成；任务要求或验收证据不足时标为待确认，不补猜成功或失败。

每个试点场景须在开始前建立任务验收卡，包含：场景 ID 与定义版本、任务目标、必要通道和阶段、计划区间或记录范围、有效性阈值、允许中断/部分结果的条件、观察截止、结果确认方式、预期下一次使用机会、负责人和证据位置。阈值由产品、交付与测试用任务样本共同确认；未定版的场景只展示操作事实，不发布任务完成率或价值结论。

S01 至 S05 均须在执行前规定发起信号：用户明确发起任务，或已配置任务实际启动时，首次建立稳定的业务任务 ID、范围、起点、截止与触发来源；任务级结果尚未知时就登记台账，发起后即使控制失败也保留。计划使用机会、进入页面不自动算任务发起；仅有计划但未发起的对象留在机会台账，不进入已发起任务分母。同一任务内重试或自动恢复关联原 ID，独立新任务另建 ID，不能因失败删除或事后补建起点。首期可由受控脚本/人工台账建立这些关联。

任务要求与原始证据留在受控的交付/试点记录中；分析侧只使用不透明任务关联、有限分类和验收结论，不上传实验内容、标签、客户自定义名称或原始矩阵。验收卡不要求扩大现有事件白名单。

### 1.2 客户分层与使用机会

客户公司是去重单位，公司内按场景、交付阶段（试用/验收/日常使用）、相关系统与版本、预期使用周期分层；安装实例用于排查，不替代独立客户数。跨场景汇总客户数再次去重，不能把各场景比例直接平均。

功能适用性、使用机会和技术可用性分别记录。适用性与周期优先来自交付档案、计划任务或简短访谈，注明来源、有效区间和定义版本；不得根据“后来用了”才认定适用、根据“没用”就剔除使用机会。仅有授权的客户不能自动解释为有近期需求。

场景或周期未知时保留“待确认”分层，不当成无需求或未使用。每月一次的实验与每日监测分别比较；周指标可用于观察活动，业务复用优先观察下一次预期使用机会。单个客户、安装或高频事件量都不代表整个客户群。

## 2 当前采集链路

```text
前端交互 → trackUsage / trackUsageOperation → 受限 Electron IPC
后端业务 → recordBusinessEvent / observeUsageOperation ─────────┐
Agent 状态 → Electron 业务事件观察 ──────────────────────────────┤
                                                              ↓
                                 usageAnalytics 白名单校验与脱敏
                                                              ↓
                                       按密钥范围隔离的本地队列
                                                              ↓
                      POST /api/usage/events/batch → 逐事件 ID 确认
```

现有原则：业务动作不等待统计网络；入队前限制事件名与字段；上传前等待队列持久化；只删除服务端确认的事件；换密钥不混发原范围队列。

接口接收方及授权方式见[电脑授权、网页缓存与使用统计](desktop-distribution-services.md)。本文不复制真实授权值，不代替配套服务端接口定义。

## 3 当前身份和字段

### 3.1 事件公共字段

| 字段 | 当前含义 | 使用限制 |
| --- | --- | --- |
| `schemaVersion` | 当前为 `1` | 新字段和事件仍须通过严格白名单 |
| `eventId` | 单条事件的 UUID | 重试保持不变；同 ID 不得修改正文 |
| `installationId` | 统计模块持久化的随机安装实例 UUID | 正常升级保留；不代表自然人 |
| `sessionId` | 统计服务本次创建时生成的 UUID | 不代表某次采集或某条用户工作流 |
| `eventName` | 事件类型 | 当前允许的 16 类事件见第 4 节 |
| `occurredAt` | 事件规范化入队时的 ISO 时间 | 不是统一的业务起始时间；存在客户电脑时钟偏差 |
| `appVersion` | Electron 宿主版本 | 不能单独代表实际启用的网页版本 |
| `environment` | `production`、`development`、`test` | 打包运行不自动区分正式客户与内部演示 |
| `runtimeVersions` | 可选的有限运行版本快照 | 历史事件重试保留产生时版本 |
| `properties` | 有限业务属性 | 不接收任意对象或额外字段 |

`runtimeVersions` 当前允许 `frontendReleaseId`、`frontendBuildId`、`hostContract`、`systemPackageVersion`、`serverContractVersion`。客户归属和接收时间由服务端确定，分析侧应核验 `customerId`、`receivedAt` 的实际入库结果，不信任客户端自报公司名。

### 3.2 当前业务属性白名单

| 属性组 | 字段与限制 |
| --- | --- |
| 功能与系统 | `featureId`、`systemType`、`systemOrigin`；来源为 `builtin`、`copy`、`custom` |
| 操作与结果 | `operationId`、`action`、`result`、`errorCode`；结果为 `success`、`failure`、`cancelled`、`unknown` |
| 数量与时长 | `count` 为非负整数，上限 `1e12`；`durationMs` 为非负毫秒，上限 24 小时，入队时取整 |
| 业务维度 | `format` 当前仅 `csv`；`connectionType` 为 `serial`、`halow`、`unknown`；`mode` 为 `realtime`、`playback`；另有 `algorithmId` |
| 错误诊断 | `module`、`errorType`、`severity`、`message`、`stack`；后两项仅错误事件可用并经脱敏 |

一般字符串须匹配有限标识格式，长度不超过 80。自定义系统身份会转为安装实例与密钥范围内的摘要，不能假定同一系统在不同安装中具有相同统计 ID。当前校验没有要求所有事件都携带 `operationId`，已使用包装器的动作与直接发送的事件关联能力不同。

### 3.3 数量和成功语义

| 事件组合 | 当前数量或成功的准确含义 | 不应直接解释成 |
| --- | --- | --- |
| `export_result` | `count` 为生成文件数 | 导出行数、测量次数 |
| `collection_finished` | 精确统计可用时，`count` 为 writer 已提交行数的差值 | 物理采样帧数、完整无丢失证明 |
| `usage_session_summary` + `sensor_frames/receive_summary` | `count` 为后端观察到的标准输出帧数 | 串口原始包数、硬件丢帧率 |
| `error_reported` | 原始错误事件未带 `count` 时算 1 次；后续汇总的 `count` 为新增重复次数 | 每条汇总再额外加 1，或只求和而漏掉原始错误 |
| 网页下载相关摘要 | 对应下载数量的单位为字节 | 使用次数 |
| `device_connection_result` + `connection` | 串口状态为打开 | 数据已经到达、画面已经显示 |
| `algorithm_result` + `runtime_stopped` | 运行引用集合已摘除实例 | 算法输出成功、销毁调用已经完成 |
| 工具箱的 `analysis_tool_used` | 工具回调完成；部分动作只是启用开关 | 完成框选、完成测量或得到有效分析结果 |

看板必须按 `eventName + featureId + action` 定义指标，不能把同名事件的全部 `count` 或全部 `success` 相加。

## 4 当前事件字典

### 4.1 事件类型

| 事件名 | 当前触发与记录方 | 关键属性或细分方式 | 当前边界 |
| --- | --- | --- | --- |
| `app_session_started` | Electron 统计服务初始化、重新开启统计 | 公共身份与版本 | 不是前端可用确认；重新开启可在同一会话再产生一次 |
| `feature_exposed` | 前端工具、算法/调节入口、Agent 提案与成果面板可见 | `featureId`、`action` | 不等于阅读或理解；不同入口的去重范围不同 |
| `feature_attempted` | 受包装的操作执行前，或特定提案/成果动作开始 | 包装器带 `operationId`；部分直接发送不带 | 未形成全功能统一的用户尝试分母 |
| `system_entered` | 门户监测页入场交接完成 | `monitoring`、系统与来源、成功 | 不保证收到有效帧或完成首帧绘制 |
| `device_connection_result` | 后端串口状态、首帧/断流观察；前端 HaLow 控制结果 | `featureId`、`action`、连接类型、可选耗时 | 打开、收到帧和恢复是不同阶段，必须分别分析 |
| `monitoring_usage_summary` | 门户监测页面卸载 | 系统、来源、`durationMs` | 当前为页面驻留时长，未区分前后台或有效数据；非周期增量 |
| `collection_started` | 后端采集开关从非采集转为采集 | `collection`、系统、成功 | 代表控制已开启，不代表第一行已写入 |
| `collection_finished` | 后端处理手动 `flag:false` 停采命令 | 系统、结果、耗时、可选已写行数 | 自动中断路径未统一发送；异步排空后没有结果补报 |
| `export_result` | CSV 服务发布结果 | `export`、`csv`、结果、文件数 | 缺本次导出操作/记录关联、耗时和细分错误码 |
| `playback_started` | 后端播放状态切换为开始播放 | `playback`、`mode=playback`、成功 | 不是历史首帧显示或完整回放完成确认 |
| `algorithm_result` | 算法手动启停、运行状态变化、自动绑定失败等 | 算法 ID、功能、动作、结果 | 控制完成、运行、暂停、停止含义不同 |
| `analysis_tool_used` | 工具、调参完成、视图切换、回放控制等 | 功能、动作、结果，可选关联与耗时 | 部分动作只表示控制完成；视图切换未携带目标模式 |
| `custom_system_saved` | 系统工作区相关操作结果 | 动作、系统、结果及包装器元数据 | 应按具体保存/复制等动作拆分，不能按事件名统一算新建 |
| `agent_task_result` | Agent 任务状态、提案生成/应用/恢复、算法成果启用 | 功能、动作、结果、可选耗时 | 多条分支未上传任务/提案/成果关联 ID |
| `usage_session_summary` | 授权、回放加载、采集控制/保存错误、收帧、更新、会话结束等 | 必须按功能和动作拆分 | 同一事件承载多个业务语义；会话结束摘要依赖正常清理 |
| `error_reported` | 页面异常、后端公共错误、Electron 异常等出口 | 模块、错误类型/级别、脱敏文本 | 重复错误可合并计数；不是完整日志或崩溃转储 |

### 4.2 关键细分事件和频率

| 事件组合 | 触发与频率 | 结果含义 |
| --- | --- | --- |
| `device_connection_result` + `sensor_first_frame/first_frame` | 真实打开连接收到第一个匹配系统和角色的实时非空标准帧 | 后端已收到帧；耗时从连接打开计算 |
| 同上 + `first_frame_timeout` | 打开后约 10 秒仍无首帧，每连接一次 | 此阶段失败；后续到帧仍可恢复 |
| 同上 + `first_frame_recovered` | 首帧超时后首次到帧 | 恢复成功，不能抹去此前超时 |
| `device_connection_result` + `sensor_stream_gap/stream_paused` | 曾收帧，超过约 2 秒无帧 | `unknown`，表示观察到断流 |
| 同上 + `stream_recovered` | 断流后重新收到匹配帧 | 后端接收恢复 |
| `usage_session_summary` + `sensor_frames/receive_summary` | 有帧的约 30 秒窗口，断开/切系统/关闭时补短窗口 | 帧数与窗口时长；窗口可能含等待和断流 |
| `usage_session_summary` + `collection_save/storage_error` | 采集存储错误广播 | 失败，当前固定错误码 `COLLECTION_STORAGE_FAILED` |
| `usage_session_summary` + `collection_save/stop` | 手动停采控制函数完成 | 控制函数结果，不能替代最终保存结果 |
| `usage_session_summary` + `playback_load/load` | 历史载入命令完成 | 命令回执结果，不代表画布已展示历史帧 |
| `analysis_tool_used` + `playback_control` | 播放、暂停、速度、跳转、阈值等命令完成 | 连续速度/跳转/阈值操作合并约 500 毫秒 |
| `analysis_tool_used` + `tuning_*/adjust` | 滑块松手或键盘操作完成 | 不逐拖拽步骤记录，不上传参数值 |
| `analysis_tool_used` + `display_switch/select_mode` 或 `select_renderer` | 选择显示方式并执行调用 | 当前没有目标模式/渲染器字段，不证明实际出图 |
| `agent_task_result` + `agent_proposal/generated_*` | 活跃任务首次生成待处理提案 | 提案生成成功，不代表应用成功 |
| `agent_task_result` + `agent_proposal/apply_*` 或 `restore_*` | 提案进入已应用、已恢复、失败或不确定状态 | 连接提案未验证有效帧时仍记 `unknown` |
| `feature_attempted` + `agent_results/enter_system` 或 `locate_system` | 点击进入或定位成果系统 | 当前只有发起，没有成果与操作关联信息 |

收帧观察会排除回放和授权暂停时段，不逐帧上传。工具曝光通常排除禁用项；工具箱按同次打开去重，Agent 提案按组件内提案身份去重，不能统一宣称“每会话一次”。

## 5 已确认缺口与实施优先级

P0 表示会直接影响核心结果判断；P1 表示影响行为解释和投入决策。本表是待实施事项，不表示本次已修改埋点代码。最小试点按所选决策链路实施必需子集，P0 不代表必须先完成全场景建设；全量扩围前仍须覆盖受影响的 P0 缺口。

| 编号 | 优先级 | 当前缺口 | 产品后果 | 补齐要求 |
| --- | --- | --- | --- | --- |
| G01 | P0 | 断线、授权失效、应用退出、系统撤回直接走本地采集收尾，没有统一统计终态 | 异常结束漏出完成率与失败原因分析 | 由采集会话最终结果统一发出终态，覆盖全部结束原因 |
| G02 | P0 | 手动停采按当时 writer 快照记结果，未承接异步排空后的最终结果 | 统计可能长期停在未知，或将控制成功误作保存成功 | 关联本地最终证据，明确排空超时、部分保存、未知及后续核对 |
| G03 | P0 | 页面驻留和收帧窗口时长均不能直接代表有效展示时长 | 高估实际使用；异常退出也可能少报 | 周期增量统计，分开接收、展示、前后台和交互时长 |
| G04 | P0 | 缺统一功能可用快照；部分操作没有成对关联 | 无法稳定区分不可用、未曝光、未尝试与失败 | 补功能可用分母，核心尝试与结果共用操作 ID |
| G05 | P0 | 丢弃计数主要在本机状态，覆盖/延迟未形成端到端质量验收 | 无上报易被误判为未使用或流失 | 补指标级完整性、质量摘要与离线容量验收，区分失去观测与真实零使用 |
| G06 | P1 | 显示切换不记录所选模式、渲染器或方案 | 无法比较具体展示偏好 | 补有限目标与选择来源，结合场景和默认配置分析，不直接按时长排名投入 |
| G07 | P1 | Agent 生成、曝光、应用、进入与后续业务缺稳定成果关联 | 生成成功数不能解释为成果使用率 | 关联全部已发起任务及成果链，保留生成前失败，并分开评价任务完成、采用和收益 |
| G08 | P1 | CSV、回放、部分工具只有局部结果；缺记录关联或有效动作确认 | 难定位导出失败阶段，难判断工具是否真正产生结果 | 补导出/回放关联，区分启用工具和完成有效分析动作 |

G01/G02 的本地采集证据已经存在，缺口是它没有成为统一的产品统计最终结果。不能据此声称软件没有保存证据或没有正确停采。

## 6 待补齐事件与字段

### 6.1 契约兼容要求

以下字段和新事件均为目标设计，当前客户端与服务端白名单不会自动接收。实施时先确定版本与服务端接收规则，再增加客户端采集；不得直接向现有 `schemaVersion=1` 队列塞入额外字段。

本次新增的业务任务与场景关联均为目标设计：ID 与版本采用不超过 80 字符的有限标识字符串，场景和来源为受控枚举。缺少业务任务或场景关联时允许保留技术事件，但不得用于对应的任务级比率；缺少选择来源时归入 `unknown`。首期证据可人工关联，后续是否产品化字段须按试点收益与成本决定。

本轮连接身份、区间和持久发布规则也是待实现契约，不改变第 3、4 节现状。新增 ID 为不透明有限标识；序号、修订号、分片号和时长为非负有界整数，`summarySeq` 从 1 开始；`validIntervalsMs` 是唯一明确新增的数值区间数组类型，必须专门校验，不能据此放开任意数组/对象。单事件仍受 4 KiB 限制。

## 7 核心流程的目标语义

### 7.1 连接与有效监测

| 阶段 | 事件或摘要 | 记录方 | 必须确认的事实 |
| --- | --- | --- | --- |
| 发起连接 | `feature_attempted` | 控制入口与连接管理层 | 明确发起建立操作 ID；按实际目标角色建立打开尝试 ID，标明用户或自动触发 |
| 打开结果 | `device_connection_result` | 连接管理层 | 成功/失败均关联原操作与尝试；仅成功后分配连接 ID，打开前失败省略该字段 |
| 首帧 | 同事件的首帧阶段 | 标准帧观察层 | 当前已建立连接、系统与通道收到匹配有效帧，关联原尝试；不得替失败尝试补造首帧 |
| 前端消费 | 对应阶段与监测摘要 | 渲染适配层 | 当前画布消费当前系统有效帧；加载占位不算 |
| 持续使用 | `monitoring_usage_summary` | 时长统计层 | 按数据阶段、实时/回放、前后台分开记录窗口 |
| 断流/关闭 | 连接阶段结果并截断摘要 | 连接与时长统计层 | 保留真实原因，不把断流恢复等同采集恢复 |

有效数据时长采用单调时钟累计，只计有效帧新鲜度满足阈值的区间；初始阈值沿用当前约 2 秒断流判断，低频系统需显式配置并随指标定义固定。无首帧、断流、切系统、休眠或授权暂停均截断。不能因一整个 30 秒窗口出现过一帧，就把整个窗口算作有效。

前台有效展示要求页面可见、当前画布已就绪且持续消费新鲜帧。后台持续采集单独计量，仍可产生业务价值。交互时长需另外定义交互信号与闲置截止，不把整段监测或采集时长算成人的操作时长。

同一安装的多个传感器并行时，系统级时长取区间并集，不能按角色相加；公司级多安装总时长可以求和，但必须标注为“安装总时长”。跨 24 小时的长监测拆成有限窗口，不只依赖当前 24 小时上限的退出摘要。

#### 7.1.1 连接尝试与已建立连接

一次控制操作可打开多个逻辑角色，因此 `operationId` 与 `connectionAttemptId` 不强制一对一。连接管理层是尝试/连接身份的唯一分配方；只用逻辑角色与范围匹配，不上传端口路径或硬件原始身份。

| 情况 | 身份与计数规则 |
| --- | --- |
| 合法打开意图且目标角色可确定 | 在授权、端口可用性和实际打开检查前为每个待打开角色分配尝试 ID，记录原操作 ID；用户点击一次不因多个回调增加尝试数 |
| 授权拒绝、端口占用、打开抛错或打开前取消 | 打开阶段结果携带原尝试/操作 ID，`connectionId` 缺失；失败与取消分别记录，不生成连接、首帧超时或有效时长 |
| 参数无效且目标无法确定 | 记录控制操作参数错误，不伪造角色或连接；该请求不进入真实打开尝试分母 |
| 真实打开成功 | 只生成一个连接 ID，建立操作、尝试、连接、系统与逻辑角色的绑定，首帧观察沿用此绑定；打开成功不等于首帧成功 |
| 同一打开请求因 HTTP/IPC 重传 | 沿用原操作/尝试身份并返回已有结果，不能重复执行或新计一次尝试；控制入口生成的操作 ID 作为幂等令牌透传 |
| 用户重试或自动重连 | 属于新一次真实打开尝试，生成新操作/尝试 ID，标明 `trigger`；成功后再生成新连接 ID，旧连接的迟到回调不得归入新连接 |
| 请求复用已经打开的连接 | 记录本次操作的 `reuse_existing` 结果及现有连接 ID，不新建打开尝试，不将原打开操作 ID 替换为新操作 ID |
| 同一已建立连接断流后恢复 | 连接未关闭时沿用连接 ID，只记录断流/恢复阶段；关闭后重新打开按新尝试处理 |

绑定应在统计观察处理该连接首帧前可读取；统计无法确认身份时标记关联缺失，不猜测归属，也不阻塞标准帧发布。复用连接结果不进入“新打开成功率”；打开尝试按范围、安装与尝试 ID 去重，多角色批次同时显示角色级尝试数和控制操作数。

控制层按“原客户范围 + 安装 + 宿主运行纪元 + 操作 ID + 逻辑角色/连接类型”匹配请求，并保留规范化参数摘要。同键异参数判冲突，不另开口；同键请求仍在执行时返回同一未决状态，已结束时返回原结果。幂等记录至少保留到该操作终结且声明的控制重试期限结束；过期或跨宿主重启无法确认旧请求时返回过期/未知，不自动重新执行，明确重试另建操作 ID。

#### 7.1.2 有效区间的计算与传输

采用源端先求系统并集的方案。`host_received` 的唯一计算方是本地后端标准帧观察层；`renderer_consumed` 的唯一计算方是当前页面统一渲染适配层。同一安装、系统与阶段不得让各角色分别上报冒充系统级摘要；两个阶段也不能相加。跨 iframe/worker 的消费通知先映射到该阶段计算方的单调时间轴，无法可靠映射时标记该区间证据不完整。

每个角色保留 `[start,end)` 半开有效区间：首次匹配有效帧开始，新的有效帧延长新鲜度，重复展示旧帧不刷新；到新鲜度截止、连接关闭、授权暂停或系统切换时截断。真正全零数据仍可有效，内部合成清屏帧不能打开或延长区间。统计新鲜度默认 2 秒，低频系统按定版策略配置；采集控制的 5 秒无数据停采是另一条策略，不能将有效时长补算至停采时刻。

计算方统一将单调时间按同一纪元向下量化为整数毫秒，再裁剪到最长 30000 毫秒的窗口，不对各角色独立四舍五入。跨窗口区间在共同边界切开；模式、客户范围、系统、可见性、显示来源、实际运行版本或有效性策略变化时提前结束旧窗口。墙钟时间只提供窗口日期映射，时钟跳变或映射不可信时保留区间长度事实，但不进入精确跨周/7 日归因。

对同一聚合范围内所有角色的区间按开始时间排序；下一段开始不大于当前结束时合并，否则保留空档。`coverageRule=any_channel` 的结果表示至少一个相关角色有效，系统时长为合并后长度之和。任务要求全部必要通道同时有效时，按定版必要通道集先取交集，另出 `required_channels` 摘要；缺失必要通道即不满足，不能拿并集证明任务完整。前台展示还须与页面可见、画布就绪区间求交，后台采集和交互时长分别核对。

| 同一 30 秒窗口的角色有效区间 | 系统并集 | 计算与验收证据 |
| --- | --- | --- |
| A `[0,15)` 秒，B `[0,15)` 秒 | 15 秒 | 输出 `[0,15000)` 毫秒，不能相加成 30 秒 |
| A `[0,15)` 秒，B `[15,30)` 秒 | 30 秒 | 合并为 `[0,30000)`，共同边界不重复计时 |
| A `[0,10)` 秒，B `[15,20)` 秒 | 15 秒 | 保留 `[0,10000)`、`[15000,20000)`，不能填平缺口 |
| A `[0,20)` 秒，B `[10,30)` 秒 | 30 秒 | 必要双通道交集另为 `[10000,20000)`，共 10 秒 |
| 仅第 0 秒收到一帧，此后无帧，新鲜度 2 秒 | 2 秒 | 输出 `[0,2000)`，第 5 秒停采不改变统计结果 |

稳定统计流限定为“原客户范围 + 安装 + 计算方纪元 + 系统/来源 + 数据阶段 + 实时/回放 + 可见性 + 显示模式/渲染器/方案/选择来源 + 实际版本 + 有效性策略 + 覆盖规则”。任何一项改变即关闭旧流并创建新 `summaryStreamId`；返回原配置也新建流。并集与必要通道交集各自成流，可交错产生摘要。`summarySeq` 只在本流内从 1 递增，不能拿客户 A、另一覆盖规则或筛选隐藏的流来补序或判断缺口。

源端为每个闭合窗口先固定 `summaryId`、纪元/流 ID、流内序号、策略/维度、合并区间和完整性，并持久保留该流清单；质量摘要声明本流 `lastClosedSummarySeq` 与活动/关闭状态。零有效时长的正常观察窗口也保留空数组和 0，不能以省略窗口代替零值。源端保留有界的角色区间/规则校验记录用于验收复算，不保留压力值；没有保留或无法核对的证据不得宣称已完整验收。

传输使用整数毫秒偏移 `validIntervalsMs`，窗口长度满足 `0 < windowDurationMs <= 30000`，每段满足 `0 <= start < end <= windowDurationMs`，排序且片内、片间不重叠。零长度窗口不生成摘要；有观察窗口但无有效数据时发送一片空区间、时长为 0 的摘要。每事件最多 32 段，最终 UTF-8 JSON 仍须不超过 4 KiB；不足以容纳时继续拆分，每个逻辑窗口最多 16 片。源端先持久固定完整分片清单、总片数和每片事件 ID/正文，再投递；各片共用摘要 ID、序号和窗口，`partIndex` 从 0 开始，`effectiveDurationMs` 为本片区间长度之和，不是重复的窗口总时长。

接收端按原客户范围、安装、`summaryId + partIndex` 及事件 ID 去重校验，并校验流 ID、流内序号和全部维度一致；全部片齐全且一致后，对区间复算合计并校验不超过窗口长度。相同片号异内容属于冲突；缺片或源端 `windowState=partial` 不得发布该窗口的完整精确值。同一流的预期序列缺口使对应缺失窗口和覆盖周期不完整，其他已核对窗口的确认事实仍保留。预期序列依据该流的持久清单/覆盖检查点确定，缺可信关闭或覆盖检查点时不能推定流尾部完整。超过 16 片、单片仍无法容纳、写盘失败或证据被淘汰时，记录质量缺口并降级，禁止删除小区间、跨空档合并或另报近似值冒充精确结果。分片及本地证据字节计入第 9.3 节预算。

异常退出时只恢复已持久闭合的窗口/分片清单。尚未闭合的尾部不能按“退出时刻”或“窗口应结束时刻”补足；有可信已封闭前缀时可单列确认下界，其余为观测未知。新计算纪元不重算旧尾部，不把观测缺失制造成业务 `unknown` 终态。

### 7.2 采集最终结果

采集生命周期统一为：明确发起 → 后端确认开始 → 封闭新写入 → 排空已接纳处理和写入 → 最终证据 → 统计终态。控制命令成功只说明控制函数完成。

`collection_finished` 的唯一事实来源是采集会话最终证据。用户停止、串口断开、授权失效、应用退出、系统撤回等均进入同一出口；事件包含采集 ID、工作流 ID、结束原因、已提交/失败行数、耗时和保存结果。

| `outcome` 目标值 | 通用 `result` | 产品解释 |
| --- | --- | --- |
| `saved` | `success` | 最终证据确认保存；有效采集指标还要求已提交行数大于零 |
| `partial` | `failure` | 有部分数据保存，但存在已确认处理或写入失败 |
| `failed` | `failure` | 已确认未完成要求的保存 |
| `cancelled` | `cancelled` | 符合预定义取消条件，不把所有用户正常停采都算取消 |
| `unknown` | `unknown` | 排空超时、进程异常或证据不可用，无法确认最终结果 |

`outcome` 是统计层映射，不直接把本地存储枚举原样透传。正常手动停止并保存成功应记成功；拔线后若已接纳数据全部保存，可同时记录 `saved` 与 `SERIAL_DISCONNECTED`，分别分析保存结果和异常中断。

每个采集只产生一次初始终态，`outcomeRevision=0`。未知结果后获得新的可信证据时，发 `collection_outcome_reconciled`，使用新 `eventId`、同一 `collectionId`、逐次加 1 的修订号并引用前一修订事件。相同证据的重复回调不增加修订；看板取观察截止时有效的最新修订，不能把修订另算一次采集，也不能修改旧事件正文重传。终态生成、持久化与恢复遵循以下协议。

#### 7.2.1 最终证据与本地事务性发件箱

由本地采集会话服务作为每个采集的唯一终态写入方。采用每采集一份、可原子提交的终态记录：同一记录内包含最终证据快照、证据版本、结果修订号，以及发布处置。统计启用且归属可信时，发布处置包含完整不可变事件信封和 `pending` 状态；不具备采集/发送资格时仅保留 `suppressed` 原因，不生成可上传正文。

准备提交时一次确定事件 UUID、原客户授权范围、安装/会话、故障或结束发生时间、产生时版本、采集 ID、修订和前序引用；完成白名单/脱敏后固定序列化正文及内容摘要。最终证据和该信封必须作为同一个持久化事务提交，禁止先写“最终结果已保存”再由内存通知临时生成事件。采用文件记录时，须验证临时写入、文件持久化确认与原子替换等同样满足该事务边界；不允许把两个独立文件各自写成功当作原子提交。

提交前后状态如下；SQL 实际数据保存不因统计失败回滚，证据/发布失败影响的是结果可确认性和统计完整性，不得谎称数据必然丢失或已经完整上报。

| 状态 | 持久事实与允许动作 |
| --- | --- |
| 未提交 | 新终态尚未成为可信持久事实；崩溃恢复读取上一份合法记录，按原会话证据重新收尾，不能把不完整临时文件当终态 |
| `pending` | 最终证据与原事件已一并提交；可向上传队列交接并重复交接同一事件，不因“已交给队列”就删除发件箱正文 |
| `acked` | 服务端有效存储回执已获验证，并且本地确认标记也已持久提交；此后才允许回收可上传正文，保留修订/事件摘要与处置状态 |
| `suppressed`、`dropped`、`expired` | 关闭/不具备资格、预算淘汰、过期等导致不再发布；必要的不可上传处置标记防止重启从采集证据复活事件，相关指标按原因降级 |

上传适配器必须支持受信宿主发件箱提供的既有事件信封，保留事件 ID、正文、时间、会话、版本和归属；不得重新走会生成新 UUID/当前时间的普通 `record` 来重建事件，也不得开放前端任意伪造身份的入口。上传队列重复入队同 ID 同正文视为幂等；同 ID 异内容作为冲突保留证据并暂停该记录，不静默覆盖。

服务端确认后先持久保存 `acked` 标记，再回收发送副本。若回执丢失或本地确认落盘失败，保留 `pending`，下次继续发送原信封；服务端按事件 ID 幂等接收，不增加逻辑终态次数。发件箱的交接/确认状态不能取代服务端存储回执。

重启只扫描已提交的待发布记录，不依据“发现历史采集文件但没有发送标记”临时补造事件。提交前崩溃的未收尾会话，通过恢复收尾流程在同一采集 ID 下原子创建其首次可信终态；无法证实原结果时仍按未知处理。旧格式证据、缺原归属/版本或损坏记录不得用当前客户、当前会话或新版本补齐后发送，单列恢复缺口。

#### 7.2.2 修订顺序与发布处置

新证据需要修订时，由同一写入方原子追加下一修订的证据、信封和 `pending` 状态，旧信封保持不变。服务端除了事件 ID，还对“原客户范围 + 安装 + 采集 ID + 修订号”施加唯一约束：同事件同正文幂等确认；同 ID 异正文，或同修订出现另一事件 ID/正文，均判冲突，不能新增一次采集或静默取最后收到者。

修订按序号而非到达时间生效。较新修订先到时可以保留已确认事实，但标记前序链缺口，依赖完整链的比率暂不发布；旧修订迟到不能回退最新结果。前序补齐且引用一致后重新核算；任何修订都只影响同一个采集，初始采集数仍为 1。

发件箱、分片清单和上传队列共用同一开关、授权与条数/字节/期限预算。同事件的物理副本只算一次逻辑事件，但实际占用字节全部计入预算，发件箱不能成为无限的第二队列。预算淘汰或过期必须先持久记录处置，再删除正文；关闭统计先使并发写入/发送失去资格，再清理待传正文和保存抑制标记。重新开启不追溯补建关闭期间事件，清空队列或重启也不能绕过处置标记。

处置标记仅为随采集证据保留的有限本地恢复元数据，不作为新的使用事件发送；证据已删除或超出保留期时不扫描复建。客户切换只隔离原范围，不能改写归属；恢复原范围且仍符合开关、有效授权、期限与预算时才能补传。操作系统或磁盘无法提供可信持久提交、证据损坏等情况仍属于观测缺口，本协议不承诺任何断电或硬件故障下零丢失。

### 7.3 回放与导出

回放分开记录载入请求结果、播放控制、首个历史帧消费和有效回放摘要。只打开历史列表或点击播放按钮不能作为有效回放。

导出从发起到最终文件写入结果共用 `operationId`，以不透明 `recordId` 关联来源记录。文件数、数据行数和耗时分别记录；目录不可写、记录不存在、读取失败、文件写入失败采用有限阶段错误码。多文件导出说明全部成功或部分成功，不能用一个非空文件列表掩盖局部失败。

### 7.4 Agent 与分析工具

Agent 漏斗按同一成果关联：提案生成 → 实际曝光 → 用户应用 → 应用结果 → 点击进入 → 实际进入 → 收到/消费有效数据或完成业务。阅读历史不算新生成；应用成功不等于成果已被使用；定位系统不等于进入系统。

任务层从用户明确发起支持范围内的任务开始计数，由 `feature_attempted` 与任务结果关联，不能从生成成功才建分母。生成前失败、无成果结束、主动取消、超时和未知均保留；支持范围在试点前固定，超范围请求另列，不能因执行失败事后改判超范围。同一任务的重试不增加业务任务数，独立新任务才另计。无需生成成果的受支持任务也按约定目标验收。

成果采用只说明采用行为。Agent 收益需在相同场景、难度和设备条件下，与人工方式做可比任务验证，记录端到端耗时（含等待、重试与修复）、人工返工、结果质量，以及可获得的调用次数/成本元数据。任务失败和未完成不得从耗时样本中静默删除；完成任务耗时与全体任务结果并列。小样本配对或顺序平衡的任务观察用于探索，未经足够对照不能宣称效率提升；比较不采集聊天正文或实验内容。

工具事件区分 `enable`、`complete`、`disable`。例如打开量尺只是启用，完成两点测量且产生有效距离才记一次完成；进入框选模式只是启用，产生有效选区结果才记完成。显示切换记录目标有限枚举；真实成功须由新视图就绪确认，而非只看选择回调未抛错。

显示分析同时保留产品初始默认、用户主动选择、沿用历史配置、自动切换与未知来源，并记录当时场景、系统与版本。按来源和可比任务分组后，结合任务完成、耗时、返工及可读性反馈判断投入；默认展示的长驻留不能直接解释为偏好。受控试点可轮换初始展示方式并平衡顺序，先确认硬件与任务条件可比。

## 8 产品指标与看板口径

统计时区为 `Asia/Shanghai`，周为周一至周日自然周，趋势比较完整周期。当前 `occurredAt` 是规范化入队时间；没有独立业务时间证据时只能标为该时间口径，不冒称统一业务发生时间。同时保留接收时间，时钟异常的事件单列，无法可靠定时的事件不进入跨周或 7 日归因。除特别说明，以下为补齐后的目标口径。

### 8.1 指标定义与使用限制

| 指标 | 定义 | 当前可用程度 |
| --- | --- | --- |
| 周有效操作客户数 | 一周内有有效实时监测、非空成功采集、有效回放或成功非空导出的去重客户数 | 原“周有效使用客户数”的技术活动口径；仅能部分近似，不代表任务完成 |
| 场景任务确认完成率 | 已到观察截止的已发起业务任务中，符合第 1.1 节定版要求且有验收证据的任务数 / 同批已到截止任务数 | 新目标；分母须有完整发起台账，未知保留在分母并单列，此时该比率为确认完成占比 |
| 功能客户使用率 | 在预先确认的场景使用机会内，该分母资格人群中成功有效使用功能的客户数 / 同范围功能适用、当时可用且该指标观测完整的客户数 | 缺适用性、机会、可用快照及完整性资格；不再按事后“活跃”筛分母，须并列固定人群状态 |
| 入口曝光覆盖率 | 该分母资格人群中实际曝光客户数 / 同范围功能适用、当时可用且曝光可观测的客户数 | 原“入口发现率”更名；曝光不证明发现、理解或需求 |
| 尝试转化率 | 曝光后明确尝试的客户数 / 同范围曝光客户数 | 核心路径需补统一入口与关联 |
| 操作成功率 | 观察截止时成功操作数 / 已达到业务观察截止的尝试数 | 按同一操作 ID 关联；失败、取消、未知均单列 |
| 非空采集保存成功率 | 最新终态为 `saved` 且已提交行数大于零的采集数 / 已结束或达到收尾截止的已开始采集数 | 原“有效采集完成率”更名；自动中断与结果修订待补，不代表实验任务完整 |
| CSV 导出成功率 | 满足导出要求的成功终态操作数 / 已达观察截止的导出尝试数 | 缺成对关联与局部失败语义 |
| Agent 任务确认完成率 | 支持范围内已明确发起且已到截止的任务中，满足场景目标的任务数 / 同批已到截止任务数 | 新目标；覆盖生成前失败、无成果、取消和未知，须有完整发起证据 |
| Agent 成果采用率 | 分母为截至观察截止已满 7 日、生成成功且该窗口完整可观测的成果数；分子只计该成果群中生成后 7 日内发生有效业务使用的成果数 | 原“Agent 成果使用率”更名；依赖成果关联，只衡量采用，未成熟和不完整成果另列 |
| Agent 任务效率与返工 | 可比任务的端到端耗时分布、人工返工、质量及调用/成本元数据，连同全部任务结果分布报告 | 先做受控试点，不以采用率推导效率收益；缺失成本标明未知 |
| 条件跨周复用率 | 同一分母客户群中次周仍有有效使用的客户数 / 首次有效使用某功能、已满观察期且仍适用、可用、该指标观测完整的同群客户数 | 原“跨周复用率”明确为条件指标；不得单独解释为客户留存 |
| 下一预期机会复用 | 固定首用场景客户群在下一次约定使用机会的复用状态与条件复用率 | 新目标；月度/不定期任务不统一按次周判未复用，周期未知单列 |
| 上报触达覆盖率 | 周内有支持能力且收到合法数据的交付客户数 / 同范围已交付客户数 | 原“数据可观测覆盖”明确为触达；需交付清单，不能证明窗口完整 |
| 指标观测完整率 | 同一指标中达到完整性资格的客户观察窗口数 / 交付/试点台账确定的同范围应观察客户窗口数 | 新目标；按第 8.3 节判定，不由收到事件客户反推分母 |
| 上报延迟与损失 | 时间可信时的 `receivedAt - occurredAt` 分布，配合持久化丢弃/无效计数、队列积压及时间异常数量 | 延迟为入队至接收的近似；本机已有部分状态，集中质量摘要待补齐 |

实时监测每周累计有效时间至少 5 分钟仅保留为活动观察的候选阈值，不能用作通用价值门槛；正式活动阈值与第 1.1 节任务验收分别定版。采集和导出的非空条件也只证明操作事实。未补齐或尚未定版的指标显示“口径未就绪”及原因，不以零替代。

指标更名保留旧名称与定义版本的对应关系；分母、阈值、时间或完成语义变化时另建指标定义版本，新旧趋势并列标记，不直接拼接。任务确认完成率与操作成功率可以同时展示，但不得用其中一个补填另一个的历史值。

所有条件比率的分子严格取自同一分母资格人群。窗口不完整但已有确认使用事实的客户，仍可在固定群中显示确认使用，不进入要求完整窗口的条件比率分子。

操作观察截止按业务配置：连接采用该产品确认的连接/首帧截止，采集采用最终收尾截止，导出采用实际任务截止。不能把仍在正常执行的操作提前算失败，也不能把失去观测默认算取消。

功能使用归因到动作发生时的有效可用区间，不能用客户当前权限回推历史分母。关联键始终限定服务端客户来源范围和安装实例；当前会话 ID 不因每次换密钥而重建，不能仅按会话 ID 混合不同客户事件。

包含离线补传的转化和复用指标，在观察窗口结束后保留补传宽限期；宽限期按实际延迟基线配置并在看板标明。定版后收到合法晚到事件时重算受影响成果群和日期，保留修订提示，不将新成果混入已成熟成果群的分子。

### 8.2 固定客户群与样本要求

交付激活与首用后复用分别建立固定客户群。前者包含已进入交付且满足试点范围的全部客户，保留从未完成首次任务的对象；后者按首次有效操作或首次任务完成建群，并明确采用哪一种起点。客户群不能因后续失去授权、配置变化或失去观测而缩小。

每群并列主结果“确认复用、已到期且确认未用、观察未知、尚未到预期机会”，四类互斥并合计等于固定群总数；权限退出、配置不可用、计划停机和使用周期待确认另作条件标签。权限退出的客户保留在固定群中，退出原因待核实，不自动判为流失；“确认未用”必须有该窗口完整观测证据。条件复用率只解释仍具备条件的人群，并同时展示被排除的数量和原因。

所有比例同时显示分子、分母、独立客户数、任务数、场景、观察窗口和观测完整率。多安装与百万条事件不能增加独立客户数；同一客户内任务相关性须在比较时考虑。比例和差异报告适用的不确定性范围，极小样本以计数和案例描述为主，不将波动直接用于功能下线或投资排序。

2 至 4 个完整周仅是初期基线观察安排，实际须覆盖所选场景至少一个完整使用机会及相应截止/补传期；低频场景可更长。对研发投入、默认展示或效率收益的比较，须在采集前按拟决策差异、可接受误判和客户/任务差异确定证据门槛，不设置通用的“看满几周就充分”。未达门槛时只触发补充观察或访谈；已复现的保存失败等可靠性问题可直接进入修复，不必等待统计显著。

### 8.3 指标级观测完整性

完整性按“客户 × 指标 × 观察窗口”判断，并能追到相关安装与操作；收到一条合法启动事件只证明触达。应观察窗口来自交付/试点台账和使用机会，不能只从已收到事件反推。

成熟度、观测完整性和业务结果分别判断。未到业务截止或补传期未结束时先标“未成熟”，不因暂缺终态判失败或业务 `unknown`；已知丢弃仍可同时标记观测不完整。成熟后仍缺终态事件或所需证据，属于观测不完整，不能由“没收到”制造业务 `unknown`。来源系统明确发出且可核对的 `unknown` 终态，若起点、事件链与窗口均齐全，可同时是观测完整、业务结果未知；其在确认完成占比的分母中保留并单列。

| 资格 | 最低判定条件 | 报表处理 |
| --- | --- | --- |
| 完整 | 相关版本支持该指标；范围身份、可用区间与所需起点齐全；窗口连续性或预期序列经核对，所需终态事件及事实证据齐全（结果允许为 `unknown`）；已过业务截止与补传期，且无未解释的相关丢弃/拒收/时间异常 | 可进入该指标的完整观测样本；证据确认结果为未知仍须单列，不能转成功 |
| 不完整 | 已知相关摘要、开始/终态、快照或成果关联缺失，发生相关丢弃/拒收，或窗口连续性无法证明 | 保留已确认事实，排除依赖完整窗口的条件比率；固定群与损失数量仍保留 |
| 未知或不支持 | 无可核对的相关覆盖证据、统计关闭、版本不支持或范围/时间不可信 | 单列原因；不把无事件当零使用，不绕过统计开关补采 |

采集指标至少核对发起/开始台账、同一采集最终证据与修订；时长指标核对窗口增量、缺口和去重；成果采用核对完整生成名单、成熟时间及后续使用窗口。仅有全队列丢弃计数而无法判断事件类别时，相关范围和期间保守标记不完整；不能因为另一类合法事件到达就恢复该指标资格。

若全部尝试有独立完整台账，可以报告“确认成功数 / 全部已到截止尝试数”并列出未知，必要时给出未知全部成功时的上界；若发起台账本身不完整，停止发布总体成功率，只展示已核对样本。指标观测完整率与固定群状态先于业务趋势展示，覆盖变化先调查数据质量，再解释产品变化。

### 8.4 决策规则与反馈闭环

每个首期指标必须绑定一个决策卡，填写：待验证问题、场景/客户群、指标与质量资格、基线、触发条件、独立客户/任务证据门槛、负责人、可采取动作、复查日期和停止条件。涉及比率变化时须写明数值阈值及不确定性要求；负责人和门槛未填完整时仅观察，不自动触发客户结论或资源调整。本规范没有指定实际人员和阈值，须在第 11 节阶段 0 定版。

| 决策问题 | 允许触发行动的证据 | 责任角色、行动与复查 |
| --- | --- | --- |
| 核心采集是否需要优先修复 | 保存证据与任务结果不一致，或同类失败经逐项对账/复现确认；先排除上报缺失 | 研发负责人安排修复，产品确认受影响任务；测试复验原场景，产品在下一轮同场景任务复查，不能只看错误事件减少 |
| 功能低用是否需要调整入口或交互 | 有事前确认的需求/机会且功能可用，指标观测完整；同场景漏斗异常达到决策卡门槛，并经访谈核实障碍 | 产品负责人每周复盘，交付负责人在下一次计划使用前核实任务与障碍；选择入口、交互或培训改动，在下一完整机会复查曝光至任务结果 |
| 哪种展示应设为默认或追加投入 | 来源和版本已区分，可比任务样本达到预设门槛；任务结果、耗时、返工及可读性反馈共同支持 | 产品负责人组织可比任务试点，研发评估成本；在约定复查日期比较原任务，不按驻留时长直接排序 |
| Agent 是否值得扩大使用 | 全部已发起任务结果可核对，可比人工任务基线存在；质量、耗时、返工与成本满足决策卡要求 | 产品与 Agent 研发负责人复盘失败链及人工介入，分别优化完成率或效率；证据不足时保持小范围探索，避免以成果采用代替收益 |
| 客户是否需要跟进 | 固定客户群已到预期机会，有使用变化信号；权限、计划停机和观测状态已标明 | 产品提出核实清单，交付负责人在下次计划使用前访谈，记录无需求/计划变化/操作障碍/可靠性问题/未知等有限结论；自动上报不等同自动联系客户 |

决策记录须保留原假设、证据范围、所选动作、负责人、实际复查日期和结果。复查同时看任务完成与成本/可靠性护栏；没有改善时记录无效或证据不足，决定改方案、继续有限观察或停止扩围。用户反馈仅保留有限结论与受控证据引用，不把自由文本自动写入使用事件。

### 8.5 看板最小内容

- 总览：触达覆盖、各指标完整率、固定客户群状态、版本与场景、有效操作和任务完成，随后才展示条件使用/复用与数据延迟。
- 客户详情：安装实例、预期使用机会、最近可观测活动、权限/配置状态、有效监测与后台采集时长、任务证据和关联工作流。
- 核心漏斗：分别展示仅监测、采集保存、历史分析、导出任务，分开操作成功与场景任务完成；不把不需要导出的客户当作流失。
- Agent：全部已发起任务的结果分布、成果采用与可比任务效率/返工分开展示，保留失败、取消、未知和人工介入。
- 决策记录：当前待验证问题、负责人、证据是否达标、采取的动作及复查结果。最小试点可用人工核对表，不以完整看板开发作为前置。

不据“没有事件”自动判断客户流失，不将版本相关性直接解释为改版效果，也不把默认展示占比解释为真实偏好。

## 9 上传和数据范围

### 9.1 当前队列行为

| 项目 | 当前实现 |
| --- | --- |
| 批次与频率 | 每批最多 50 条，约 30 秒一轮；达到 50 条可提前触发；单次只发送一批 |
| 容量 | 每个密钥范围最多 2000 条，满额丢最旧项；单事件最多 4 KiB |
| 恢复 | 重读队列时仅保留 30 天内合法事件，检查重复 ID、额外字段和大小 |
| 失败 | 网络、限流和服务错误退避；明确的非 429 的 4xx 暂停自动重试，可手动重试 |
| 确认 | 只有有效回执完整确认该批所有 ID 后才删除；重复补传保持同一 ID 和内容 |
| 客户隔离 | 按密钥摘要选择队列，不使用新密钥上传旧范围事件 |
| 关闭统计 | 停止新记录/发送并清理待传使用统计；不删除聊天或传感器数据 |
| 本机状态 | 可见启用、积压、成功时间、错误、重试和丢弃等状态；不能直接当作服务端质量看板 |

30 天是当前队列恢复过滤窗口，不是服务端保留期限，也不是持续运行时精确逐日清理保证。服务端使用统计保留目标为 90 天，实际执行以服务端部署验收为准。

### 9.2 内容与访问边界

只记录有限功能元数据、结果、时长、数量和版本。禁止将聊天正文、附件内容、原始传感器矩阵、客户自定义名称、采集标签、完整文件路径、硬件身份原值或密钥加入事件。

错误文本入队前脱敏，服务端继续校验；新诊断出口应沿用这一限制。系统、记录和成果关联采用不透明 ID。客户明细按后台权限隔离，导出分析数据遵循同一客户范围。关闭使用统计不等于关闭聊天同步或模型请求，说明与设置分别维护。

### 9.3 离线容量与事件预算验收

目标中的 30 秒窗口不能未经容量评估就全部作为独立事件入队。按持续离线、初始空队列、每 30 秒仅一条监测摘要且容量保持 2000 条推算，约 60000 秒（16 小时 40 分钟）即满；其他事件、多角色或其他摘要会更早占满。这是设计推算，不是实测，也不表示当前页面卸载摘要已改成周期事件。30 天恢复过滤窗口不能证明可承受 30 天离线。

每个试点须先声明事件预算：单安装各类事件峰值频率、典型使用时长、所需离线保障时长、条数与字节容量、关键事件保留方式、合并规则、满额策略和联网后排空时间目标。约 30 秒形成业务窗口与上传频率分开；是否合并、降低摘要入队频率、调整容量或保留关键事件，先做有界方案选择并验收，不默认无限扩大磁盘队列。

聚合不得跨客户范围、系统、模式、显示来源、可见性或版本边界混合；保留有效区间和可核对的缺口，不能把断流空档填成有效时长。已分配事件 ID 的正文和重试内容不变；合并应发生在事件定型前，或采用明确的新摘要/替代契约并防止双计，不能改写待重传事件。

区间分片按第 7.1.2 节固定清单与身份，终态发件箱按第 7.2 节恢复；这些记录和物理副本统一计入预算。任何淘汰、过期、关闭抑制和部分窗口/缺片都须传导到指标完整性，不能依靠重建事件 ID、扩大隐藏缓存或重新合并已定型正文掩盖缺失。

容量验证须覆盖预算内离线、刚好触及容量、超过容量、重启与恢复联网。预算内关键发起/终态/修订须可逐项对账；超预算时丢弃数量和影响范围可解释，并使受影响指标降为不完整，不能报为正常覆盖或零使用。若暂时只有全范围丢弃计数，按第 8.3 节保守降级。无法满足声明的离线保障或排空目标时，先调整预算/方案并重新验收，再扩大试点。

同时记录统计启用前后的采集/渲染负载、队列磁盘上限与用户任务表现，性能护栏在试点前填写。统计功能导致任务可靠性或资源护栏越界时停止扩围；关闭统计的选择及客户隔离保持生效。容量边界可用受控加速事件验证，真实设备的长时负载与离线表现仍须独立核验。

### 10.1 受影响链路的技术验收

| 场景 | 可核对的通过条件 |

| 无数据、后台与休眠 | 页面驻留、后端接收、前台展示、后台采集和交互时长可分别核对 |
| 长时监测与异常关闭 | 周期摘要可恢复；不依赖页面卸载；超过 24 小时不被一次截断冒充全时长 |
| 正常停采及异步排空 | 控制成功与最终保存分开；全部已接纳写入完成后确认最终结果 |
| 断线、授权失效、退出、系统撤回 | 每次已开始采集均有统一最终结果或明确未知，附结束原因 |
| 部分写入失败/排空超时 | 不报完整保存成功；部分、失败和未知有可解释证据 |
| 未知后恢复证据 | 新事件修订同一采集，历史事件不改内容，统计采集数不增加 |
| 无数据采集与空导出 | 即使控制/文件创建成功，也不计入非空有效核心使用 |
| CSV 多文件部分失败 | 总体和文件结果一致，操作/来源记录可关联，数量单位明确 |
| 回放及工具使用 | 点击播放不冒充有效回放；工具启用与完成有效动作可区分 |
| 显示切换 | 每种目标模式可区分；异步挂载失败不能报最终展示成功 |
| 功能可用性变化 | 授权/配置变化产生新快照；无权限、未曝光、未尝试和失败可区分 |
| Agent 成果链 | 同一成果从生成至真实业务使用可追溯；历史读取不增加生成数 |
| 断网、重启与回执丢失 | 补传内容及 ID 不变，服务端去重后次数与人工脚本一致 |
| 队列满额与过期 | 计数和丢失原因可核对，覆盖提示生效，不把数据损失显示为客户不活跃 |
| 换客户与关闭统计 | 旧事件不归新客户；关闭后无新统计发送；清理行为符合设置说明 |
| 版本与内部数据 | 事件携带产生时版本；旧版缺字段单列；内部/演示/测试不混入客户报表 |
| 真实安装与后台入库 | 实际安装包 IPC、断网补传、正确客户入库和看板聚合逐项核对 |

#### 10.1.1 三项契约的专项验收

以下是待执行的专项用例。时间区间用受控单调时钟输入；崩溃注入在隔离进程和 userData 内执行，逐项核对持久记录、原事件正文、服务端存储及聚合结果，不以回调被调用或 HTTP 200 作为通过依据。

| 编号 | 注入或输入 | 必须满足的结果 |
| --- | --- | --- |
| C01 | 端口占用、授权拒绝、打开抛错和打开前取消分别执行 | 每个真实尝试有稳定操作/尝试 ID，连接 ID 缺失；失败/取消正确，不产生首帧计时和有效时长 |
| C02 | 同一控制操作打开两个角色，一个成功一个失败 | 一个控制操作、两个尝试，仅成功角色有连接 ID；两角色结果不混归，按角色统计打开成功为 1/2 |
| C03 | 同一幂等令牌重发三次，再由用户明确重试一次 | 重发仍为一次真实尝试；明确重试新增一次；成功的新尝试取得新连接 ID，事件重传不增加尝试数 |
| C04 | 活跃连接断流后恢复，再关闭重开；旧回调迟到 | 未关闭时保持原连接；重开使用新尝试/连接；旧回调不满足新连接首帧，复用已有连接不新增打开尝试 |
| T01 | 分别在终态原子记录替换前、替换后终止进程 | 前者读取上一合法记录并恢复原会话收尾，不得出现可信终态缺发布处置；后者恢复相同初始事件信封及 revision 0，采集数为 1 |
| T02 | 事件已进入上传队列、发件箱交接状态尚未保存时终止 | 重启重复交接仍用原事件 ID/正文；服务端只有一个初始终态，不因重启更新会话、时间或版本 |
| T03 | 服务端已存储但回执丢失；另测有效回执后本地 `acked` 写入失败 | 两种情况都保留原 `pending` 并可重复发送；确认落盘前不回收唯一正文，接收端逻辑计数不增加 |
| T04 | 原子提交下一修订时终止；再按 2、0、1、2 顺序投递合法修订 | 未提交修订不能成为可信结果；已提交修订恢复原信封；乱序不回退，缺前序时不标完整，补齐后最新为 2、采集数仍为 1 |
| T05 | 同一事件 ID 改正文，或同一采集/修订改用另一事件 ID | 明确冲突且保留原记录，不覆盖原事实，不增加采集数，不靠随机新 ID 继续重试 |
| T06 | 容量淘汰、过期、关闭后清空队列，再重启/重新开启 | 处置记录生效，不从采集证据复活正文；关闭期间不补采；发件箱与队列的实际字节和逻辑条数符合共同预算 |
| T07 | 客户 A、会话 S1、版本 V1 产生 pending，升级 V2 并换客户 B | 不向 B 发送、不改成新会话/版本；恢复 A 且资格仍满足才补传原正文；缺原归属/版本时只保留缺口 |
| U01 | 同 30 秒窗，A、B 均 `[0,15)` 秒 | 系统区间 `[0,15000)`，并集恰为 15000 毫秒，不得得到 30000 |
| U02 | 同窗 A `[0,15)` 秒、B `[15,30)` 秒 | 系统区间 `[0,30000)`，并集恰为 30000 毫秒，共同边界不双计 |
| U03 | 同窗 A `[0,10)` 秒、B `[15,20)` 秒；再测 A `[0,20)`、B `[10,30)` | 前者并集 15000 且保留缺口；后者并集 30000、必要双通道交集 10000，两种覆盖规则不混算 |
| U04 | 单帧在第 0 秒，2 秒新鲜度；第 5 秒才触发停采 | 仅计 `[0,2000)`；真实全零帧可延长，重复旧帧和合成清屏帧不延长 |
| U05 | 区间跨 30 秒边界，或第 12 秒切模式/可见性/版本 | 窗口先切分再聚合，边界连续且不重叠；长度守恒，模式、阶段与版本不混合；不相加 host 与 renderer 时长 |
| U06 | 同窗 40 个互不相交子区间，拆两片，先仅送一片，再补齐并重复两片 | 缺片时不发布完整精确值；补齐后按区间和去重复算；每片至多 32 段且不超过 4 KiB，重复不增加总时长 |
| U07 | 超过 16 片或单片无法容纳，再测同片号异正文 | 超限显式记录缺口并降级，不截掉区间或跨空档合并；异正文判冲突，不覆盖已接收片 |
| U08 | 第 18 秒异常退出，仅有已持久封闭前缀 `[0,15)` 秒 | 确认下界可为 15000；尾部观测未知，不补满窗口，不伪造业务终态；新纪元保留旧缺口 |
| U09 | 改变墙钟但保持单调输入不变，再重复投递全部分片 | 区间时长不变、重传不双计；无法可靠映射日期时退出精确跨周归因，不把新时间写回旧事件 |
| U10 | 同 owner 先给 A 产生五窗，再换 B；另让并集与必要通道交集交错上报 | B 新流从序号 1 开始，不要求 A 的窗口；两种覆盖规则各自连续；返回 A 新建流。只有本流清单声明已闭合但缺少的窗口才判缺口，不能把其他流或筛选掉的窗口算成丢失 |

所有专项用例必须同时检查其对第 8.3 节完整性的影响；已确认结果未知、缺少事件、缺片和明确处置是不同状态。真实设备时长误差另由阶段 0 定义容差，上述整数时钟用例要求数值精确一致。

### 10.2 最小产品闭环验收

首期建议选择 S03 实验采集中的一个完整任务，验证“任务未完成是否与异常中断或保存有关”，覆盖任务发起、连接/采集、最终证据、任务验收、接收端聚合和产品行动。该建议尚未经过客户需求确认；阶段 0 可依据真实交付任务改选 S01 至 S05 中的一种，并记录理由。只实施该决策必需的 G01 至 G05 子集及其他必要关联，不先完成全部工具、Agent、展示比较或全量看板。

| 环节 | 必须交付的证据 | 通过条件；不通过时处理 |
| --- | --- | --- |
| A 试点准入 | 一张已定版场景任务验收卡、一张决策卡、范围/版本清单、参与客户与机会台账、统计选择、负责人、预算和复查日期 | 必填项齐全，真实任务与观察周期已由交付/产品确认；未定阈值、未指定负责人或仅有假设任务时，不启动客户试点 |
| B 人工真值脚本 | 预先写明每次任务、操作、开始/结束、预期记录及结果；包含正常、非空但任务不完整、异常中断、未知后修订、取消/未完成等所选路径 | 人工任务数、技术操作数和场景完成数可分别核对；期望事件/ID/状态逐项一致，时间误差不超过预先约定容差；差异未解释前停止发布对应比率 |
| C 真实安装与端到端对账 | 实际宿主、网页、系统包和接收端版本，真实设备运行记录，本地证据、接收端入库与人工聚合表 | 从一次任务到接收/聚合结果可追溯，客户不混归、补传不双计、修订不增任务数；合成夹具不能单独通过此项 |
| D 离线与缺失识别 | 第 9.3 节预算、容量边界记录，断网/重启/恢复联网及回执丢失的核对记录 | 预算内关键事件无未解释缺失；超预算的丢弃和缺口使对应指标降级，固定群保留未知；若仍显示完整或客户未用，本项不通过 |
| E 指标与反例复算 | 以相同截止和台账手算分子分母、固定群状态、完整性及条件比率，并记录规则版本 | 与接收端聚合逐项一致；验证“一条非空记录仍未完成任务”“权限退出不移除固定群”“启动事件不证明整窗完整”“缺终态与已确认未知终态分开”；报表不能混用操作与任务成功 |
| F 一次产品决策与执行 | 按决策卡评估证据，记录选择、责任人、实际行动和复查安排，关联有限的客户反馈结论 | 有据可查地执行一次修复、交互调整、交付指导或继续/停止试点的决策；证据不足可决定补充观察，不编造问题和收益，但尚不能据此通过扩围收益门槛 |
| G 复查与扩围评审 | 下一完整使用机会的相同任务要求、版本/条件变化、结果、返工及成本/可靠性护栏 | 行动效果按原规则复查，改善、无效或证据不足均如实记录；证实闭环运行不等于证实产品收益，扩围须另满足第 10.3 节 |

以上 A 至 G 环节记录状态统一为“未开始、进行中、通过、不通过、证据不足”，并填写证据位置、实际责任人和日期。本次新增试点环节状态均为“未开始”；不以文档表格存在代替执行证据。真实试点开始前可用受控样本验证技术链路，但内部/演示/测试数据不能混入客户指标。

### 10.3 扩围、继续观察与停止条件

- 扩围：所选链路 A 至 G 证据齐全、技术与人工对账通过；客户任务标准可用、指标完整性达决策卡要求；实际行动的结果支持扩围且成本/可靠性在预定护栏内。只扩到证据覆盖的场景和版本，新场景重新定义任务与预算。
- 继续有限观察：链路可对账但客户/任务样本、使用机会或对照证据未达到决策门槛，或行动结果尚不确定。保留原固定群、写明待补证据、观察上限和复评日期，不自动延长或宣称收益。
- 停止扩围并处理：客户混归、关键结果无法对账、缺失仍被算完整、违反统计开关/内容边界、统计引入任务可靠性或资源护栏退化。修复并重验对应环节后再评审，不以扩大样本掩盖链路错误。
- 调整或终止该方向：复查证明场景无近期需求、行动无效，或达不到事前约定的收益/成本条件。保留证据与结论，由产品负责人记录取舍；不要求为了验收而继续开发全部埋点和看板。

纯文档变更按 Fast 检查引用与格式。后续实现涉及 Electron、采集、授权、HTTP/WS 或跨层契约时，按仓库规则运行 `scripts/verify-changed.ps1 -Mode Full`，并将构建输出写入临时目录。合成测试通过后，仍需真实安装包、真实设备和配套接收端验收。

产品负责人维护场景价值、指标与决策卡，并对是否扩围负责；交付负责人确认客户阶段、任务/机会与反馈；研发负责人维护事件来源、关联、预算和接收契约；测试负责人维护脚本、真机与逐项对账；数据分析负责人维护完整性、固定群、去重、迟到重算、观察窗口和报表。各角色可由同一人员兼任，但实际姓名、承诺日期和复查日必须在阶段 0 填写，不以角色名称代替排期承诺。

首轮试点用于验证任务定义和决策闭环，不自动代表全部客户。观察结果只支持所覆盖的任务、版本与条件；参与方不足、证据不足或无可执行决策时先缩小范围或停止，新增埋点与看板的投入须有对应问题和后续行动。
