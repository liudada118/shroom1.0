# Shroom 错误上报现状与补齐规范

更新日期：2026-10-29。适用对象：产品、客户端、后端、测试和运维人员。

实施进度：2026-10-29 已补齐投递质量基础和早期启动故障的技术链路，配套本地接收端支持新增契约；范围、验证及尚未实施项见[实施记录](telemetry-implementation-20261029.md)。下文完整目标与客户试点验收不因此全部视为完成。

当前已具备常规 JavaScript 错误采集、有限错误码与安全堆栈位置、脱敏和有界离线上传。早期启动、进程故障、已处理的界面失败、资源与渲染异常仍有覆盖缺口，生产源码还原及送达质量也需要补齐。

除顶部实施进度外，下文“现状”保留本轮实施前的核对基线；最新代码与专项验证以实施记录为准。“补齐方案”和“验收标准”仍是完整目标，不代表真实安装包或生产接收端已经验收。发布覆盖必须按宿主、网页、后端和服务端实际版本确认。

规范原稿完善事故计数、业务影响、分范围恢复、跨版本关联、暴露分母、启动失败自助路径和最小处置闭环。除实施记录明确列出的能力外，新增字段、状态、阈值与流程仍为目标设计；实际负责人、响应时限和预算须在试点启动前定版。

## 1 目标与边界

错误上报应帮助团队回答：客户遇到了什么故障、影响了哪项工作、发生在哪个版本和阶段、能否定位、哪些范围已经恢复，以及团队是否完成处置与复查。

| 层次 | 定义 | 判断依据 |
| --- | --- | --- |
| 已识别 | 对应错误出口捕获了故障 | 错误回调、有限错误码或明确失败状态 |
| 已持久化 | 脱敏诊断已写入本机可恢复存储 | 重启后可恢复相同记录，而非仅在内存 |
| 已接收 | 接收端确认并存储了事件 | 事件 ID 回执与服务端记录一致 |
| 可定位 | 能关联运行环境并找到故障位置或原因类别 | 版本、阶段、代码位置、错误码及必要关联 |
| 已恢复 | 后续验证确认指定范围的功能恢复 | 明确验证范围与证据，原任务结果和剩余损失另列，不能只看提示消失 |
| 已处置 | 已认领、采取行动并完成约定复查，或有证据决定不行动 | 处置单保留负责人、时限、行动、复查和关闭理由；关闭不等于原任务已补救 |

本地日志、业务失败结果和错误诊断相互补充。`agent_task_result` 或 `algorithm_result` 可以说明任务失败，但不自动提供进程退出原因；出现 `logger.error` 也不自动证明记录已经送达。

当前错误上报共用“使用统计与错误上报”的开关、授权范围和队列。补齐方案继续遵循该选择，不增加绕过关闭状态或客户归属的隐藏上传通道。原始聊天、传感器帧、任意日志文件和原生崩溃转储不属于当前事件范围。

计数分为出口观察、独立事故和受影响操作；技术严重性与业务处置优先级分别判定。接收成功、进程重启和后续没有错误记录，均不能单独证明客户任务成功、故障消失或修复有效。对未抛异常但结果不可信的情况，须依靠业务证据或客户反馈建立诊断，不承诺异常监听能发现全部业务错误。

## 2 当前实现

### 2.1 采集与发送链路

```text
页面 error / unhandledrejection → describeRendererError → Electron IPC ┐
后端 common logger.error → businessEvents ────────────────────────────┤
主进程 uncaughtExceptionMonitor → usage.record ───────────────────────┤
                                                                    ↓
                                 normalizeEvent 白名单校验与脱敏
                                                                    ↓
                                  按密钥范围隔离的本地异步持久队列
                                                                    ↓
                             POST /api/usage/events/batch → ID 回执
```

页面监听只在存在 Electron 服务桥且 `AppServices` 的 effect 已执行后注册。后端业务事件总线只向当时的订阅者发送，不缓存订阅建立之前的日志。统计服务在 `getAppServices` 创建后才订阅；端口预检位于此之前。

### 2.2 覆盖矩阵

| 范围 | 现有能力 | 当前边界 |
| --- | --- | --- |
| 页面运行异常 | 全局 `error` 与 `unhandledrejection` 转为 `error_reported` | 覆盖监听就绪后向该窗口暴露的异常；纯浏览器无 Electron 桥时不上报 |
| 前端定位信息 | 保留 Error 消息/堆栈，缺有效位置时补浏览器文件坐标 | 有构建文件坐标，不等于原始源码已还原 |
| 后端公共日志 | `backend/common/logger.js` 的 `error` 镜像为错误事件；保留有限错误码、类型和堆栈 | `warn` 原样走本地日志；直接 `console.error` 不由该封装自动接管 |
| 本地监听失败 | `localServiceErrors` 记录日志并通知启动失败处理 | 能显示失败原因；统计服务尚未创建时，日志镜像没有上传订阅者 |
| 主进程 JS 异常 | 注册 `uncaughtExceptionMonitor`，已有服务时尝试入队 | 注册较晚，且致命退出前不能依赖异步落盘完成 |
| Agent 任务和提案 | 任务/提案有部分成功、失败、取消和未知结果事件 | 业务结果不能代替进程级诊断；并非所有中断状态都有对应终态事件 |
| Agent worker 退出 | 拒绝未决请求、更新状态并发送界面 `runtime.error` | 未统一生成 `error_reported`；启动时忽略子进程标准输出 |
| Python worker | 保留 stderr 尾部、本地控制台输出，退出时拒绝请求并处理进程生命周期 | stderr、error、exit、坏 JSON、握手/重启失败没有统一诊断出口 |
| 算法运行失败 | 部分算法路径有 `algorithm_result` 与固定错误码 | 不包含完整进程故障原因；不能说 Python 或算法失败全部无统计 |
| Agent 渲染模块 | 超时、iframe 错误及加载失败有错误界面与重载入口 | 这些处理分支只更新界面状态，没有主动发出错误事件 |
| 上传故障 | 本机设置显示积压、失败原因和重试状态 | 不是服务端完整性看板，也不能证明丢弃情况已集中可见 |

### 2.3 当前事件字段与容量

当前统一事件为 `error_reported`，`schemaVersion=1`。公共字段包括 `eventId`、`installationId`、`sessionId`、`occurredAt`、`appVersion`、`environment` 和可选 `runtimeVersions`，详细身份说明见[产品埋点规范](shroom-usage-tracking-spec.md)。

| 字段或限制 | 当前含义 |
| --- | --- |
| `module`、`errorType` | 有限模块标识和错误类型；页面当前通常按浏览器事件类型分类 |
| `severity` | 支持 `warning`、`error`、`fatal`；实际各出口自行设置 |
| `errorCode` | 部分出口提供的有限错误码；公共 logger 不读取任意额外对象字段 |
| `message` | 仅错误事件允许，脱敏后最多 400 字符 |
| `stack` | 仅错误事件允许，脱敏后最多 1800 字符；保留允许的脚本文件名和行列号 |
| `featureId`、`systemType`、`systemOrigin`、`operationId` | 已在通用白名单中，但各错误出口并未统一附带 |
| `count` | 原始错误缺失时按 1 次；后续重复摘要中的值表示新增重复次数 |
| 版本快照 | 允许网页 release/build、宿主契约、系统包和服务端契约的有限版本标识 |
| 单事件和队列 | 单条最多 4 KiB；每密钥范围最多 2000 条，与功能事件共用，满额丢最旧项 |
| 上传 | 每批最多 50 条，约 30 秒一轮，达到批次阈值可提前发送；同一时刻一批 |
| 重复错误 | 按脱敏后的完整属性生成指纹，最多保存 128 类；重复次数定期生成新摘要事件 |
| 恢复与过期 | 重读队列时只恢复 30 天内的合法事件；该窗口不是服务端保留期限 |

重试保留原事件 ID、正文和版本快照；收到有效回执完整确认该批 ID 后才移除记录。网络、429 和服务错误退避重试；明确的其他 4xx 暂停自动重试。关闭统计清理待传统计；没有密钥时当前 `record` 直接返回，不进入待传队列。

`compactStackLocations` 已保留安全的文件名及行列号，再由通用脱敏移除凭据、URL、邮箱和本机路径。不能将现状描述为“只记录类型，没有定位信息”。生产构建当前关闭 source map，且包含混淆和压缩，原始源码还原仍有缺口。

## 3 缺口与优先级

“已确认”表示在对应源码出口可以确认缺少接入；“待专项验证”表示存在静态覆盖边界，不能据此断言所有相关故障都会漏报。P0 优先处理启动、闪退及诊断丢失，P1 补齐可定位性与专项覆盖。

这些是补齐工作的实施优先级，与第 5.2 节单次事故的处置优先级分别管理。E09 中关键保留、限流、丢弃可见和递归保护为新增采集出口的前置门槛，不能等接入全部故障类型后再补。首期按一个高价值故障实施必需子集，再按证据扩围。

| 编号 | 优先级 | 缺口与证据性质 | 影响 | 对应补齐方案 |
| --- | --- | --- | --- | --- |
| E01 | P0 | 已确认：端口预检和部分初始化发生在统计订阅之前 | 启动失败能弹框，但可能没有远程记录 | 提前建立最小诊断与有界本地恢复记录 |
| E02 | P0 | 已确认：主进程异常入口依赖已存在的统计服务和异步写盘 | 致命错误即使进入回调，也不保证退出前持久化 | 有限的致命故障证据和下次启动恢复 |
| E03 | P0 | 待专项验证：未见渲染/GPU/原生崩溃的统一诊断与重启补报 | 闪退、卡死、原生终止缺少可解释记录 | 进程级生命周期观察与未正常退出识别 |
| E04 | P0 | 已确认：Python/Agent 进程错误主要走控制台、IPC 或界面状态 | 任务失败缺进程原因，级联错误也难关联 | 子进程诊断适配、意外与主动停止区分 |
| E05 | P1 | 已确认：Agent 渲染器已处理错误仅更新状态 | 用户看到模块错误，后台没有对应诊断 | 在明确错误状态转换处主动报告 |
| E06 | P1 | 已确认入口边界：页面监听晚于入口依赖和首次渲染，缺根级专用报告 | 首屏故障及组件上下文覆盖不足 | 最早启动监听、根级报告和适当错误边界 |
| E07 | P1 | 待专项验证：资源错误捕获和 WebGL 丢失/恢复没有明确统一接入 | 资源失败、画布异常可能无法定位或跟踪恢复 | 资源捕获与实际 canvas 生命周期接入 |
| E08 | P1 | 已确认：生产无 source map，完整构建变换链未建立还原验收 | 只能看到压缩文件位置，排障成本高 | 私有、匹配实际发布资源的源码映射 |
| E09 | P0 | 已确认：错误与行为共用有界队列；新增重复次数在摘要前保留内存 | 容量满或突然退出会丢诊断/重复次数；集中质量不透明 | 优先级、限流、累计质量状态和故障窗口核对 |
| E10 | P1 | 已确认范围限制：公共自动镜像只包装 `logger.error`，缺统一故障关联 | 用户可见但已捕获的失败可能只留本地，多个出口可能重复计数 | 统一诊断入口与明确接入清单 |

不将所有 `warn`、用户取消、正常主动停止或一般授权拒绝自动升级成故障告警。是否需要错误事件，依据用户影响、可恢复性和是否存在异常行为确定；业务结果仍保留在原业务事件中。

## 4 补齐方案

本节均为目标设计，不表示已实现，也不在本次文档任务中启用上传或改动运行代码。

### 4.1 早期启动与致命退出

在加载高风险应用依赖、预检固定端口和创建窗口之前，建立只依赖必要本机能力的最小诊断入口。读取持久开关失败时不静默开启采集；已有关闭选择继续有效。启动失败先形成有限本地证据，再显示错误和执行原有退出流程。

建议首版恢复记录使用独立小文件，最多 100 条、合计 256 KiB、最长 7 天，单条仍不超过 4 KiB，先达到的上限生效。这些是拟定配置，实施时与产品确认并固化到测试。记录只包含错误码、阶段、发生时间、版本、不透明会话/故障标识和安全位置，不保存原始错误对象或任意正文。

归属在故障产生时固定。已知原授权范围的记录只能在相同范围和有效授权下补传；无法确定归属时保留为本地未归属证据，不能在以后输入新密钥后自动归给新客户。关闭上报时清除可上传的诊断恢复记录；必要本地运维日志沿用其独立规则，不自动转为上传材料。

致命回调只做有界、尽力而为的最小证据写入，不在故障进程内等待网络，也不为了上报吞掉致命异常后继续运行。强制终止、原生崩溃、断电或磁盘故障可能使最后一条记录无法写出，不能承诺零丢失。

正常退出写入关闭状态；下次启动发现未正常关闭标记时，只能报告“上次未确认正常结束、原因未知”。没有确证时不能推断为 OOM、原生崩溃或客户强制关闭。正常升级、主动关闭、预期子进程停止与真实意外终止分别判定。

### 4.2 主进程与子进程

| 对象 | 目标接入 | 必要区分 |
| --- | --- | --- |
| Electron 主进程 | 尽早安装 JS 诊断出口，保留启动阶段；以外部可观察证据和下次启动状态补充致命故障 | 未捕获 JS 异常与未确认正常退出不混为同一原因 |
| 渲染/GPU 等进程 | 接入宿主实际支持的进程退出/无响应通知，记录有限原因和退出信息 | 无响应是观察状态；恢复、意外退出与主动关闭分开 |
| Agent worker | 初始化失败、请求超时、意外退出进入统一诊断；保留原界面错误和任务结果 | 请求超时不自动等同整个 worker 崩溃；正常 dispose 不报异常 |
| Python worker | 启动、握手、管道、协议解析、超时、意外退出、重启失败进入适配器 | 只提取有限错误类别及安全堆栈摘要，不直接上传 stderr 全文 |

同一进程故障造成 `error → exit → pending reject` 时，共用故障关联标识；一次逻辑故障不算成三次独立事故，但各出口观察可分别保留。每个受影响业务操作仍可各自产生失败结果，通过操作 ID 关联诊断，不删除业务结果来减少数量。事故建立、持续与复发按第 5.3 节执行，不能仅靠相同指纹或时间邻近合并根因。

原生崩溃转储不加入现有 4 KiB 事件。若以后确需转储，应单独定义采集范围、内容处理和接收能力；当前先完善有限退出原因、版本与恢复证据。诊断恢复不自动重开采集或连接设备。

### 4.3 前端与用户可见失败

最小前端诊断在应用模块加载和首次渲染之前建立，与宿主的页面加载失败和就绪超时观察互补。根级 React 报告与适当的 ErrorBoundary 提供组件范围和降级界面；和全局监听使用同一诊断入口，防止同一故障重复计数。

`AgentRendererHost` 在加载超时、iframe 明确错误、加载失败状态处主动报告，使用有限错误码、渲染器身份和本次加载 ID。界面重载是一次新尝试；恢复确认与原故障关联。跨 iframe 不复制任意错误正文，按既有消息边界提取允许字段。

资源错误使用适当捕获出口，区分脚本、样式、图片、模型或懒加载模块等有限类别，只记录允许的资源标识和构建版本，去掉完整 URL、查询参数与凭据。被业务 catch 的失败在业务事实确定处记录，不依赖全局未处理异常兜底。

WebGL 需要在实际创建/销毁 canvas 的层接入上下文丢失、恢复和恢复超时。先核对 SDK 与渲染器已有恢复逻辑，避免重复监听；恢复事件只说明上下文状态，仍需验证画布重新消费有效帧并恢复绘制。卸载、重建或正常释放画布不算故障。

### 4.4 私有源码还原

按实际发布的网页 release/build、资源文件名与哈希，私有保存源码版本和完整 source map。映射必须覆盖打包、压缩及混淆的组合变换；仅将构建选项改为生成映射不视为完成。

客户端只上传已有的安全构建文件名、行列号与版本。还原在有权限的诊断侧执行，不将源码、私有映射或客户本机路径放入公开网页资源或错误事件。缺映射、资源哈希不符、版本不明时显示“无法还原”及具体原因，不猜测源码位置。

### 4.5 投递质量与诊断闭环

保留现有“先持久化、后上传、逐 ID 确认、按授权范围隔离”的原则。为关键诊断设置队列保留优先级或有界配额，避免普通功能事件挤掉启动/进程故障；错误风暴按故障类别和实例合并，不能靠无界增大队列解决。

新增出口前先固定关键事件/摘要配额、单类峰值频率、最大离线保障时长、条数与字节上限、满额策略、排空目标和性能预算，并验证普通行为与错误风暴并发时的关键记录保留。优先级按事故证据价值和业务影响设定，不能只按 `fatal` 日志等级抢占容量；未确认影响的启动/进程证据仍有保留额度。

风暴合并保留第 5.3 节三种计数：同一事故的重复观察可汇总；独立复发不能因指纹相同合成一次事故。摘要按客户范围、安装、事故、观察出口和产生时版本/会话分界，不用单个 `incidentId` 代表多次独立事故。事件定型前可按契约聚合，已分配 ID 的正文不改写；合并不足或丢弃时记录计数与受影响窗口，不能用未知丢失补造精确次数。

持久化有限的累计入队、确认、丢弃、校验拒绝和最老积压时间，复用[埋点规范](shroom-usage-tracking-spec.md)拟定的 `usage_delivery_summary`。没有证据时不把服务器“没有错误记录”解释为“运行正常”；设置与看板分别显示关闭、无有效授权、队列不可写、服务拒收和延迟。

上报器自身失败只能更新有限本地状态或独立受限记录，不能再次无条件调用同一个错误入口，形成递归上报。正常网络恢复后核对服务端已存储事件，不能仅凭 HTTP 200 判定送达。

### 4.6 无法进入主界面时的用户处理路径

启动失败提示须能在主界面和统计服务不可用时独立出现，提供稳定错误码、有限失败阶段、可执行的安全排查步骤，以及诊断是否留存/可发送的真实状态。原因未知时说明未知，不把端口占用、授权问题、磁盘故障一律显示为“重启重试”。用户只需查看错误说明，不必先成功进入设置页。

提供用户主动复制安全摘要或导出有限诊断的路径，材料仅来自规则允许保留的脱敏记录，保持单条、总量、期限和客户范围有界。导出前可预览允许内容；不包含密钥、聊天、原始传感器数据、stderr 全文或完整本机路径。关闭统计后不为导出重新采集或恢复已清理的待传记录；没有可用材料时明确告知。

复制/导出只在本机发生，不自动发送给他人或生产端，也不自动绑定新密钥。未归属材料保持未归属；换客户时不能把旧范围诊断混入新范围文件。必要本地运维日志继续按独立规则处理，不能整包替代白名单诊断。提示和处理步骤须说明是否需要用户重新发起任务，不能把服务重启表述为原任务已经补救。

## 5 统一诊断契约

### 5.1 字段与版本

继续以 `error_reported` 记录故障事实；新增恢复事件拟命名为 `error_recovery_result`。新事件及以下新增属性均需客户端和服务端共同定义并升级白名单，当前 `schemaVersion=1` 不会自动接受。服务端先兼容，再发布客户端；不得修改已入队事件正文后复用同一 ID 重试。

| 字段 | 当前或目标 | 语义 |
| --- | --- | --- |
| `eventId` | 已有 | 单条不可变记录；重试同 ID，新的摘要或恢复使用新 ID |
| `incidentId` | 待新增 | 范围内一次持续故障的稳定标识，连接多个观察出口和恢复结果；建立、关闭与复发见第 5.3 节 |
| `operationId` | 已有，待补接入 | 用户或业务操作标识；同一事故可影响多个操作 |
| `module`、`errorCode`、`errorType` | 已有，待统一枚举 | 模块、公开稳定错误码和错误类型；不把任意文本当错误码 |
| `category`、`phase` | 待新增 | 有限故障类别与阶段，如启动、加载、握手、协议、写入、渲染 |
| `processType`、`processInstanceId` | 待新增 | 主进程、页面、Agent、Python 等类型及随机实例标识 |
| `severity` | 已有，待统一规则 | 记录发生时的异常等级；业务影响与处置优先级另判，不能只按此字段排修复顺序 |
| `handled` | 待新增 | 是否已由应用处理；已处理但影响工作仍可需要诊断 |
| `exitReason`、`exitCode` | 待新增 | 有真实退出证据时提供有限原因和退出码；没有证据则缺失或未知 |
| `resourceId`、`rendererId`、`loadId` | 待新增 | 有限资源/渲染器身份及本次加载标识，不使用客户自由文本 |
| `message`、`stack` | 已有 | 经过原有脱敏与长度限制的诊断摘要 |
| `count` | 已有 | 沿用原始错误与新增重复摘要语义：缺失按 1，摘要仅含新增次数；属于出口观察次数，不代表事故数或受影响操作数 |
| `impactKind`、`impactConfidence` | 待定义，可先由处置台账维护 | 有限影响类型为任务无影响、降级、阻断、数据完整性异常、未知；证据为已确认、疑似或未知，不以日志等级推导 |
| `originEventId` | 待新增 | 引用原故障事件的不透明 ID；恢复事件可据此及事故 ID 查询原上下文，原事件缺失时明确无法还原 |
| `recoveryScope`、`recoveryAttemptId` | 待新增 | 范围为服务可用性、原操作补救或数据完整性；每次验证有独立尝试 ID，以功能/操作标识限定对象 |
| `result`、`recoveryAction` | 结果已有，动作待新增 | 恢复记录使用成功、失败、取消、未知及有限动作；成功只对声明范围成立，部分恢复由各范围结果汇总，不新增通用 `result` 枚举 |
| `runtimeVersions` | 已有，需按事件语义使用 | 旧故障补传保留产生时版本；新恢复事实记录验证时的真实运行版本，不覆盖原故障上下文 |

旧故障事件和其离线重传保留原安装/客户范围、会话、发生时间与版本；补传不改为当前上下文。新发生的恢复验证使用验证时真实的会话、进程实例、时间和版本，通过 `incidentId`、`originEventId` 关联原故障。新观察若仍属于未结束事故，也记录自身真实上下文，不为关联而伪造旧版本。原故障归属与恢复时环境分开展示，恢复不能跨客户范围补绑或迁移事故。

重复指纹用于归类相似问题，`incidentId` 用于关联一次事故，`eventId` 用于投递去重，三者不能互相替代。新增字段须在实施前定版来源、类型、大小上限、缺失含义和引入版本；ID 采用不超过 80 字符的有限标识，类型/范围采用受控枚举，不上传任意证据对象或客户自由文本。首期影响判定、关联修订和处置状态可留在受控台账，不要求全部立刻新增客户端字段。

### 5.2 严重性和错误码

| 严重性 | 使用条件 | 示例 |
| --- | --- | --- |
| `fatal` | 阻止应用启动或使关键进程无法继续提供服务 | 启动服务失败、已确认的关键进程意外终止 |
| `error` | 某项用户工作已失败或结果不可信 | 导出写入失败、渲染模块加载失败、算法协议错误 |
| `warning` | 出现可恢复异常或观察到风险，尚未确认核心工作失败 | WebGL 上下文短暂丢失、上次退出状态未知 |

上述三档描述异常现象，不能直接作为产品修复排序。影响评估另列受影响功能/操作、是否阻断、持续时间、是否存在不可逆损失、已确认影响范围与证据状态；没有证据填未知，不能将进程未退出当作结果可靠。后续发现损失或恢复时新增判定记录并保留修订历史，不改写原事件严重性。

| 业务影响证据 | 处置优先级 | 响应与复查规则 |
| --- | --- | --- |
| 已确认异常导致不可逆数据损失；或已确认结果不可信且可能继续影响后续工作 | 紧急 | 单个确证即进入响应，先控制继续受影响的范围、保全证据，再定位与验证；不等待错误量基线或统计显著 |
| 已确认无法启动或关键任务持续阻断，缺少有效替代；或存在需优先核实的关键任务损失信号 | 高 | 在处置卡约定时限内认领、核实范围并给出下一步；疑似影响保留疑似，不能升级成已确认损失 |
| 任务失败但可重试/替代，影响范围和补救办法已确认 | 常规 | 按任务影响与频度安排修复，复查原任务是否完成及返工成本 |
| 已确认未影响任务；或短暂降级且相关功能已验证恢复，并已核对任务无剩余损失 | 观察 | 记录趋势和恢复证据；新增任务失败、损失或复发证据时重新评估，不能因一段时间无日志自行降级 |

因此，自动重启且确认没有业务影响的 worker 即使记录 `fatal`，也不自动压过记录为 `error` 的不可逆任务损失。影响尚未知时优先补证，不把未知当无影响；若涉及关键工作，处置卡须规定核实截止和超时升级路径。实际认领人、响应/更新/验证时限在试点前填写，不使用无负责人、无截止的“后续跟进”。

首批拟统一的错误码可包含 `STARTUP_PORT_IN_USE`、`RENDERER_LOAD_TIMEOUT`、`RENDERER_RESOURCE_FAILED`、`WEBGL_CONTEXT_LOST`、`PYTHON_PROTOCOL_INVALID`、`PYTHON_PROCESS_EXITED`、`AGENT_PROCESS_EXITED`、`DIAGNOSTIC_STORAGE_UNAVAILABLE`。这是目标分类清单；其中部分名称可能已在业务层存在，实施时以共享契约统一，不按本文自动改变现有返回码。

告警规则与事件采集分开配置：正常取消和预期关闭不告警；重复故障聚合后按业务影响、受影响客户/安装、版本、持续时间和观测完整性评估。数量/趋势类告警阈值需建立基线后确定，紧急确证不受该等待条件限制；不把一条日志直接等同客户事故。

### 5.3 事故计数、归并与复发

| 数量 | 目标计算规则 | 不得解释成 |
| --- | --- | --- |
| 出口观察次数 | 仅对唯一 `eventId` 的错误原始记录与新增重复摘要累加 `count`，原始缺失按 1；不加入恢复事件或业务失败结果 | 独立事故数、受影响任务数 |
| 独立事故数 | 在客户范围与安装内，对已确认边界的 `incidentId` 去重；前端、宿主和子进程可同属一次事故 | 错误出口条数、同指纹类别数 |
| 受影响操作数 | 对已关联事故的范围内 `operationId` 去重；跨事故汇总时再次去重 | 观察次数；没有任务关联时也不能称业务任务数 |
| 相似问题类别数 | 按定版指纹/错误码规则归类，并保留规则与版本范围 | 已确证的共同根因或独立事故数 |

事实所属模块或其宿主适配器在第一次明确故障时建立事故 ID，并向相关进程/操作透传；每类出口的建立方、关联来源和稳定窗口须在接入字典中指定。一次 worker 故障的 error、exit 和未决请求拒绝保留各自观察，共用事故 ID，每个受影响操作仍有自己的业务结果。

持续故障中的重复通知、同一失败的重试、重载和进程重建不自动产生新事故。只有约定的相关服务范围恢复、验证通过且稳定窗口结束，才能确认该运行故障结束；之后再次独立发生须新建事故 ID，即使指纹相同。旧任务补救未完成可继续处置，但不阻止已经恢复的服务在下一次独立失败时记新事故。提示关闭、执行重启、暂时无日志或观察窗口结束均不是故障结束证据。

没有可靠关联证据时保留“待关联观察”，不能仅凭同文本或时间邻近强行合并，也不把每条观察宣称为独立根事故；已确认事故数与待关联观察量并列。跨客户、安装的相似问题可归同一问题类别，不合并为一个客户事故。历史事件缺事故 ID 时只保留原观察口径，不回填假定事故数。

关联与边界判断如需修订，在诊断台账记录新判定、依据和修订版本，重算受影响统计，原事件正文和 ID 不变。摘要窗口跨独立事故时拆分记录；若受限丢弃导致事故边界或观察总数不可确认，显示不完整与已知下界，不承诺精确总数。

### 5.4 恢复范围、剩余损失与版本关联

每条恢复验证声明 `recoveryScope`、功能/操作对象、尝试 ID、有限动作、验证证据和实际运行上下文。一次动作可需要多个范围的验证，各范围分别记录结果；业务 `result` 继续使用现有四值，未执行验证不制造成功事件。不适用范围须说明依据，不能用成功占位。

| 恢复范围 | 成功需要的证据 | 仍需保留的事实 |
| --- | --- | --- |
| 服务可用性 | 对应功能重新完成约定健康检查或真实新操作；渲染须消费有效帧并恢复绘制 | 只对该功能成立，其他功能可能仍失败或未知；进程存活本身不足 |
| 原操作补救 | 原失败操作确已按要求重试、补做或恢复，其结果与原操作/任务可关联 | 新请求成功不代替原操作完成；重试为新操作但仍关联原业务任务 |
| 数据完整性 | 本地最终证据和所需记录核对通过，满足该任务的数据要求 | 已确认部分/不可逆损失继续显示；能继续运行不代表旧数据已补回 |

事故汇总分别显示“服务恢复状态、原任务补救状态、剩余损失与未知范围”。只有已声明必要范围逐项验证成功且没有未解决损失或未知范围时，才可称完全补救；部分范围成功只称部分恢复。服务已恢复而原任务永久失败时可按第 5.6 节有据关闭处置，但关闭结论须保留损失，不能把原失败改为成功。不自动重开采集或连接设备。

例如版本 A 发生故障，版本 B 的新会话验证恢复：原错误仍归 A，恢复事件归 B，关联后显示“A 发生、B 验证恢复”。是否因升级修复、重启暂时恢复或其他条件变化，须另有验证证据，不能仅从版本先后推断因果。跨重启时缺少可靠时间证据则时长未知，不能以补传时间代替恢复时间。

### 5.5 暴露分母、覆盖与趋势比较

沿用[产品埋点规范](shroom-usage-tracking-spec.md)的客户范围、固定客户群、观察成熟度和指标完整性规则。以下为错误专项的目标指标，来源与分母资格须在试点前确定；关闭、无授权、离线丢失、不支持版本和未再次启动均单列，不能解释为健康。

| 指标 | 分子与分母/范围 | 使用限制 |
| --- | --- | --- |
| 启动故障率 | 同一分母资格人群中确认失败的去重启动尝试数 / 相关阶段可观测完整且已达业务截止与补传期的启动尝试数 | 分母来自早期启动台账，不能只统计服务创建成功的会话；台账缺失时不发布总体率 |
| 操作受影响率 | 同一分母资格操作中，确认被事故影响的去重操作数 / 同范围已到截止且观测完整的已发起操作数 | 按连接/采集/导出等类型分别计算；业务任务受影响率须另有任务台账，不能用操作数冒充 |
| 故障客户占比 | 同一资格人群中有确认事故的去重客户数 / 同场景、版本和窗口具完整相关故障观测的客户数 | 同时显示固定人群中的不完整、未知与退出数量；已确认受影响但窗口不完整的客户另列事实，不混入条件比率分子 |
| 阻断与损失 | 按事故/功能统计确认阻断时长、受影响操作、部分/不可逆损失和未知数量 | 阻断结束以范围验证为准，未结束显示仍在进行或已知下界，不填零、不剔除长尾 |

所有比率分子严格来自相同分母资格范围，展示独立客户/安装、尝试数、版本、窗口和相关观测完整率。不能按错误总量直接排名功能可靠性；高频长时使用与偶尔使用须按对应暴露机会比较。固定人群不因故障后退出、授权变化或失去观测而缩小，条件指标仅描述具资格的样本。

启动尝试在早期入口建立不透明尝试 ID 或等价人工台账键，同次尝试发生多条错误仍只计一次失败；不能用较晚创建的统计 `sessionId` 代替全部启动尝试。正常转交已有窗口、主动取消等预期结果在接入字典中单列，不能自动算故障。

对同一问题的修复前后比较，同时核对发布覆盖、任务/设备条件和诊断采集规则。错误数下降可能来自使用减少或送达变差；观测不完整、样本不足或旧事件无法关联事故时停止发布确定的改善结论，只展示已核对样本和待补证据。诊断监听不能单独证明没有静默的数据/结果错误。

### 5.6 事故处置与关闭规则

处置状态在受控台账中按“待分诊 → 已认领 → 处理中 → 待验证 → 处置关闭”维护，与运行故障是否持续、事件是否接收、原任务结果分开。每单记录：事故/原事件引用、影响与证据状态、认领人及模块负责人、响应和更新截止、用户可执行的处理办法、拟采取行动、验证范围/方法、复查日期与关闭理由。

接收方首先按第 5.2 节核实影响并认领；需研发时携带有限证据和受影响工作转交对应模块，需客户补充时只索取必要信息。诊断侧保留交接和超时状态，未认领或超时按处置卡指定角色升级；本次文档不授权自动向客户或他人发消息。

关闭须有原故障复验和受影响工作核对，或明确记录误报、预期行为、重复归并、不行动/停止调查的证据与取舍。存在不可逆损失可按已确认处置结论关闭，但服务恢复、原任务失败和损失继续可见；未再收到事件不能作为关闭理由。停止调查而原因/恢复未确认时保持未知，不将关闭解释为健康。新复发按第 5.3 节新建事故并关联同一问题类别，不能直接抹掉原关闭记录。

## 6 验收标准

以下全部是待执行的验收项。使用隔离 userData、合成授权和测试接收端注入故障；进程终止在受控夹具中执行。每项保存注入条件、本地记录、事件 ID、接收端存储结果和业务状态，未授权时不向生产端发送测试事件。

### 6.1 技术与口径反例验收

| 编号 | 场景与操作 | 通过条件 |
| --- | --- | --- |
| A01 | 统计初始化前令固定端口被占用，或注入早期初始化错误 | 原有失败提示和退出正确；按开关留下有限启动诊断；下次启动可恢复，缺授权不发送 |
| A02 | 在受控主进程夹具中分别于诊断初始化前后触发未捕获异常 | 记录实际退出状态；能持久化的记录可恢复；不能写出的窗口明确列为限制，不将仅调用 `record` 算通过 |
| A03 | 受控终止后重启，再分别执行正常退出和升级退出 | 未正常退出只标未知原因；正常关闭/升级不增加崩溃数；不自动恢复采集 |
| A04 | 模拟渲染进程意外退出、GPU 相关退出通知和持续无响应后恢复 | 有有限进程信息，意外与主动关闭可区分；无响应和恢复可关联，不推断未知根因 |

| A06 | React 首次/后续渲染错误及错误边界捕获 | 保存允许的组件上下文；降级/恢复范围正确；React 与全局出口不重复增加同一事故次数 |
| A07 | Agent iframe 加载超时、明确 ERROR 消息、加载失败分别注入 | 每次加载有对应错误码与加载 ID；重复通知不重计；重载新建尝试，恢复关联原事故 |

| A10 | Python EPIPE、坏 JSON、握手失败、意外退出、重启失败 | 本地原始 stderr 保留原用途；远程仅有限诊断；error/exit/请求拒绝共用事故标识，不重复算根故障 |
| A11 | Agent 初始化失败、请求超时、运行中进程被终止 | 界面稳定错误码和原业务结果保留；诊断队列有对应阶段；正常 dispose 不报异常退出 |
| A12 | 调用公共 logger，传入带 code/stack 的 Error；令诊断观察器抛错 | 本地原输出和业务异常不变；有限字段进入队列，任意额外对象不上传；观察器失败不替代原故障 |
| A13 | 一个已处理但用户可见的失败及一个正常取消 | 前者在事实所属层显式报告；后者按规则记录业务取消，不制造系统故障 |
| A14 | 预算内，同一持续事故在一个已声明出口产生 10 次观察，覆盖至少一次摘要窗口 | 首条按 1，加后续摘要为 10 次观察，事故数为 1；摘要使用新 ID；重复补传后两种数量均不增加 |
| A15 | 一次进程故障经 K 个预先声明的诊断出口观察，关联 N 个受影响操作 | 事故数为 1，出口观察次数按脚本为 K，受影响操作按 ID 去重为 N；业务结果和恢复事件不加入错误观察次数 |
| A16 | 最终生产资源触发已知位置错误，并测试错误版本和缺失映射 | 正确版本还原到预期源码位置；混淆和压缩的组合映射有效；错版/缺失明确报无法还原 |
| A17 | 错误混入测试 Key、Authorization、URL 查询、邮箱、本机路径、采集内容 | 队列、HTTP 请求和接收端存储均无禁止原值；允许的错误码、类型与安全坐标保留 |
| A18 | 断网、重启、服务端已入库但回执丢失 | 重试保持原 ID、正文与版本；服务端幂等接收，确认前不删队列，迟到不归错日期或客户 |
| A19 | 模拟 400/401/403/409/413/429/5xx 和无效成功回执 | 明确拒绝按规则暂停，限流/服务异常退避；无效回执不清队列；状态可诊断，业务不被阻塞 |
| A20 | 目录不可写、磁盘不足、超过 2000 条或 128 类指纹 | 本机显示错误/丢弃状态；无递归错误风暴；符合配置的优先保留与容量上限；不能声称无损 |
| A21 | 关闭统计、没有有效授权、换客户后恢复旧记录 | 不绕过开关或授权；关闭清理待传诊断；旧范围不归新客户，未归属不自动补绑 |
| A22 | 超过启动恢复记录条数、字节和 7 天候选上限 | 达到任一限额即按规则淘汰，原因计数可核对；本地数据与内存有界 |
| A23 | 在真实安装包中执行一次允许的合成故障 | IPC、实际版本、正确客户归属、服务端存储和诊断页面逐项一致；HTTP 200 不作为唯一证据 |
| A24 | 在约定设备负载下对比开启/关闭诊断并注入错误风暴 | 记录采集率、显示率、event-loop lag、writer lag、丢帧与积压；符合事先确认的性能预算，不以单元测试替代实测 |
| A25 | 预算内，同一指纹的故障独立发生 10 次，每次均完成规定恢复验证与稳定窗口 | 有 10 个事故 ID、10 次独立事故；风暴合并不能合成 1 次事故，观察与受影响操作另计；未确认关联的观察另列 |
| A26 | 对比一次确认无任务影响的自动重启与一次已确认不可逆记录损失，再注入影响未知的关键任务故障 | 技术严重性不单独决定处置顺序；损失进入紧急响应；未知按证据与核实截止处理，不判为无影响 |
| A27 | 画布/新请求恢复，但原采集仍停止或原记录不可逆丢失 | 服务、原操作补救、数据完整性分别验证；可显示部分恢复，原失败与损失保留，不自动重开任务、不宣称完全补救 |
| A28 | 版本 A 原会话故障，版本 B 新会话验证恢复；再重传两种记录并尝试换客户关联 | 原事件始终归 A，恢复事件记录 B 的真实会话/进程/时间，关联后仍是一次事故；重试不改上下文、不跨客户补绑 |
| A29 | 用不同使用频率的样本手算启动/操作故障率，包含未再启动、缺失起点和仅收到启动事件的窗口 | 分子来自同一资格分母；缺口、未知与固定群退出可见，单条合法事件不证明窗口完整；不按原始错误量排名或宣称健康 |
| A30 | 始终无法进入主界面，分别在允许、关闭、无授权和无可用本地材料状态查看提示并主动导出 | 稳定错误码、排查步骤和真实诊断状态独立可见；允许材料有界、脱敏且可预览；无材料如实说明，不绕过开关、不自动发送或补绑 |
| A31 | 先混合行为事件与错误风暴，再扩大一个诊断出口；覆盖离线、满额、恢复联网和上报器自身失败 | 扩大前关键记录保留/限流/丢弃/递归保护已验收；预算内关键记录可对账，超预算标明不完整，不靠无界队列宣称无损 |
| A32 | 同一故障服务已恢复但处置未认领、验证缺失或原任务损失未说明，再模拟停止调查与新复发 | 无负责人/证据不能伪装完整闭环；关闭须有理由并保留未知/损失，新复发新建事故；无日志不自动关闭 |

容量、超时、无响应截止、故障结束稳定窗口、计数规则版本和性能预算需在实施前固定到测试配置。启动恢复记录的候选上限见第 4.1 节；原有批次、队列、文本限制继续有效，变更时同步更新接收契约和验收配置。

### 6.2 最小处置闭环

首期建议选“启动端口占用导致无法进入工作界面”这一可受控复现的故障，贯通有限诊断、正确接收或用户主动导出、分诊、定位、处理和原工作复验。该建议仍待实际交付问题确认；也可选择一种有明确任务影响的采集/进程故障，并记录改选依据。只接入该问题必需的出口、关联和映射，完整看板或全部 source map 建设不是最小试点的前置。

| 环节 | 证据要求 | 通过或不通过规则 |
| --- | --- | --- |
| B01 准入定版 | 一种故障、一项待验证问题、所选场景/任务要求、客户/安装与版本范围、人工真值脚本、责任人、响应/验证时限、事件/性能预算和复查日期 | 项目实际人员与数值门槛须已填写；只写角色、没有截止或没有业务验收要求时不启动试点 |
| B02 取得可用诊断 | 实际安装包与测试范围中复现，保留本地证据、投递状态和原事件/事故引用；或验证用户主动导出的安全材料 | 自动接收和主动导出分开标记，导出本身不算服务端已接收；重传不双计，旧范围不归新客户，关闭状态不被绕过 |
| B03 分诊与认领 | 收到诊断的时点、影响类型与可信程度、受影响工作、认领人、处置优先级及下一步截止 | 能从实际业务影响形成处置选择，影响未知列出补证与升级条件；仅展示一条 fatal 日志不算完成分诊 |
| B04 形成可行动定位 | 错误码/阶段、匹配版本的安全位置或必要源码还原、复现和排查记录，实际耗时与人工补充信息次数 | 能确定应由哪个模块/环境环节采取什么行动，或明确剩余未知；仅显示压缩堆栈不自动算可行动定位，无法定位记证据不足 |
| B05 执行处理 | 修复、环境指导、回退或有据不行动的决定，实际执行人、条件/版本变化、预期验证范围与失败后处理办法 | 有证据的动作已执行或不行动理由已审核记录；不编造修复效果，不将用户看到提示等同任务得到补救 |
| B06 原工作复验 | 原故障脚本和同场景工作再次验证，分服务/原操作/数据范围记录结果、剩余损失、真实版本和稳定窗口 | 必要范围逐项核对，未知/不可逆损失保留；只重启进程或出现一帧不能通过全部范围，原业务结果不可被覆盖 |
| B07 关闭与复查 | 认领至定位/处理/验证的记录、关闭理由、原问题在约定后续使用机会的表现、暴露分母及观测质量 | 形成可追溯处置结论并完成到期复查；无效、再次发生或证据不足均如实记录，不以无新日志替代验证，不把闭环完成自动解释为效率提升 |

处置卡同时登记可确认的观察/故障起点、收到诊断、认领、可行动定位、采取行动、范围恢复和关闭时间。分别计算对应的发现、等待认领、定位和恢复耗时；仅有观察起点时明确标为观察至接收时间。离线补传延迟、等待客户补证与实际处理耗时分开展示，未结束的事故保留进行中和已知下界，不仅统计已快速关闭样本；时钟/起点不可信则对应时长未知。

如拟证明“诊断使定位或恢复更快”，试点前还须约定与原人工排查方式的可比故障、计时起点、目标差异和证据门槛，并核对任务质量、人工介入和性能成本。没有可比基线时只证明链路和处置可执行，不宣称效率收益；单次合成故障通过也不代表全部客户覆盖。

### 6.3 扩围与停止条件

- 扩围：所选路径的技术反例与 B01 至 B07 有实际证据，计数/影响/版本/恢复范围可逐项对账，关键保留和性能预算达标，实际处置及复查支持扩围。只推广到已验证的故障、场景和版本，新出口先重验投递门槛。
- 继续有限观察：处置链可运行但使用机会、样本、对照或恢复证据未达到预定门槛，列出待补证据、观察上限和复查日；保持未知，不自动宣称有效或无限延长。
- 暂停受影响结论或试点：事故数无法对账、恢复掩盖原任务损失、版本错归、关键记录丢失仍显示完整、客户混归、开关失效或诊断使业务超出性能预算。按问题暂停对应发送/结论或扩围，修复并重验，优先保证原业务运行。
- 调整或终止方向：原问题无近期需求、行动无效或收益/成本不满足事前条件，记录产品取舍和残余风险，不为完成清单而扩展全部采集能力。

新增验收环节统一记录“未开始、进行中、通过、不通过、证据不足”、实际负责人、日期和证据位置。本次文档修订未执行上述验收，状态均为“未开始”，也未指定实际人员、完成阈值或客户试点。

## 7 实施顺序与完成定义

| 阶段 | 内容 | 完成证据 |
| --- | --- | --- |
| 阶段 0：问题与处置定版 | 选定一个故障与受影响工作，明确事故边界、业务影响、恢复范围、版本/分母和处置卡 | B01 必填项齐全；真实负责人、响应/验证时限、稳定窗口、预算与复查日期在启动前定版 |
| 第一阶段：投递与契约准入 | 先做 E09 必需的关键保留、风暴限流、丢弃/质量和递归保护；定版所选事故/恢复字段与接收白名单，明确 E10 的实际接入清单 | 兼容、离线/满额/错误风暴与性能预算验收通过，三种计数、原故障/恢复版本可区分；不待所有出口完成再补质量 |

| 第三阶段：按问题扩展覆盖 | 依证据补其他 E01 至 E04，再选择 E05 至 E08；扩充私有源码映射和 E10 接入清单 | 每一新增出口先通过投递门槛，实际资源/进程与业务状态验证可追溯；不混淆事故数、观察次数与恢复范围 |
| 第四阶段：持续运行与复查 | 固化分诊、认领、升级、处置关闭及复发跟踪，维护暴露分母、观测完整性和效率基线 | 在已验证场景持续核对质量、任务影响和处置时效；对新故障/版本重复最小闭环，避免只验收页面展示或事件入库 |

产品负责人维护业务影响、处置规则及扩围取舍；交付/支持负责人核实用户任务、有限补充信息和自助处理结果；各模块研发负责人提供事实出口、定位/处理与范围恢复证据；诊断/服务端负责人维护幂等、范围隔离、归并修订、投递质量与映射；测试负责人按观察、事故和操作分别对账，并验证原工作。角色可兼任，但实际姓名、认领与响应时限、备援/升级角色、验证与复查日期必须在阶段 0 明确，不以“纳入排期”替代承诺。

完成定义分两层：技术层要求约定故障有明确出口、持久化/接收状态、真实版本、可定位信息、计数边界和测试证据；产品层要求至少一类高价值故障经过实际认领、可行动定位、处置、分范围复验与到期复查，并明确原任务结果及残余损失。闭环运行与效率收益分别验收，未覆盖和无法确认的边界持续可见。不能使用“所有错误自动上报”“任何崩溃必达”或“服务恢复即原任务成功”作为结论。
