# Shroom 产品设计反驳与补充评审

评审日期：2026-10-19。初评对象：[客户端与服务端协同设计说明](客户端与服务端协同设计说明.md) 1.1 版；本轮按 1.3 版的对话分析方向与到期决策更新。

这份设计已经清楚说明跨端职责、授权约束和数据边界，适合作为产品、研发与交付的协作说明。作为对客户作出承诺的依据，它还需要完成一轮产品决策：确定优先服务谁、哪些结果可以承诺，以及关键异常下用户究竟能做什么。

本评审中的反例是假设场景，用于检验规则；不代表已经发生的事故。除明确标注的已确认产品决策外，下文补充条款均为候选方案，不改变现行授权、系统包及数据契约，也不表示相关能力已经实现。

## 一 需要保留的设计

- 区分串口打开、收到有效帧、实际按压正确和持续稳定，避免用界面成功替代设备成功。
- 区分入队、数据库提交和记录可读取，明确画面正常不代表正在保存。
- 区分原始读数、相对量与标定物理量，以及采样率、处理率、存储率和显示帧率。
- 区分发布、安装、客户验收和验证层次，承认离线授权及撤回存在生效边界。
- 已经定义指标口径、上传样本限制和待决策台账。问题主要在决策尚未闭合，不能笼统归结为没有考虑这些问题。

## 二 十项主要反驳

### R1 目标用户与阶段价值应先于交付承诺确定

**原文位置**：第一章“阶段目标与用户价值”“成功指标与统计口径”；第九章将“目标用户与价值”列为 P1。

原文已经提出员工配置交付、客户独立采集的阶段目标，并区分购买者、操作者和验收人；第九章也已要求在试点启动前明确目标。因此，这里并非没有前置门槛，而是应拆开“试点前确定入组对象与任务”和“试点中验证价值假设”。文档同时容纳设备配套工具、定制交付平台、客户分析工具和自助训练工具，尚未确定优先服务的客户类型及其核心业务结果。

**反驳**：客户完成采集、回放、导出，证明操作链可以完成；还不能证明这些数据能帮助客户完成原定实验、比较方案或作出判断。不同客户需要的交付结果可能不同，不能共用一个“完成 CSV 导出”作为价值判断。

**反例**：两个试点都顺利导出 CSV。客户甲只需要确认点位响应，认为交付完成；客户乙需要比较两次测试结果，但缺少一致的配置和量值依据，仍无法开展工作。操作成功率相同，客户价值不同。

**补充**：在首个商业试点启动前确认一个主要客户群、一个主要任务、一种付费或配套权益关系和一个验收结果。将“完成操作”与“取得可用于约定任务的结果”分别统计。首阶段可优先验证员工配置交付与客户独立采集，但这仍是需要客户证据支持的选择。

**优先级**：探索阶段可继续验证；形成商业试点范围、资源承诺或销售承诺前，应成为前置决策。

**本轮讨论修正**：已确认通过客户与 Agent 聊天，从具体问题出发按需组织比较、判断和报告，不为每种设备预建完整分析流程，也不要求客户先选择固定功能模块。通用工具完成数据读取与计算，Agent 结合对话确认目标、编排分析和组织结果；仅在缺少必要信息时追问。仍需用真实对话验证问题解决效果，数据质量、可比条件和判定依据不能省略；用户只要直接回答时不强制生成报告。

### R2 发布与推广的隔离目前依赖客户是否已有版本指针

**原文位置**：第四章“公司系统授权与版本交付”“发布影响与撤回边界”。

原文明确规定：没有适用指针时使用最新已发布版本，也明确指出新发布可能影响客户，并提出候选版本经显式推广的建议。

**反驳**：这个风险已被识别，但尚未被产品规则消除。同一个“发布”动作，对有固定指针的客户可能没有影响，对无指针的客户可能直接改变目标版本。管理员需要额外理解数据状态，才能判断一次发布的真实影响。

**反例**：员工修复某型号的映射并通过审核。发布者认为只是形成新版供试用，无指针客户却在后续同步中获得新版。输入尺寸未变，并不保证客户正在执行的测试口径不变。

**补充**：推荐首次交付建立明确版本基线，后续发布先形成候选，显式推广后才改变客户目标版本。迁移前应清点无指针客户并保留其实际适用基线；不能只改规则，让原有客户突然进入无版本可用状态。推广前展示影响客户、版本差异、兼容组合、启用时机和回退路径。

**优先级**：P0，任何会影响存量客户的版本发布前定案。

### R3 正常到期规则已确认 实现与其他失效状态仍需核对

**原文位置**：第三章“软件权益与业务终止”；第四章“运行中授权失效与数据收尾”。

**本轮已确认产品规则**：软件密钥正常到期时立即停止采集；到期前已接收的数据及待写队列继续提交当前采集数据库；允许查看、回放及 Agent 分析已有数据，结果可在软件内查看，禁止采集数据和分析结果导出。不设继续采集的宽限期。

原评审对正常到期时点及回放、导出权益未定的质疑已由上述选择解决。现在需要证明实际停止、原库收尾、回放与分析入口和导出拒绝符合该规则，并将提前预警与结束原因向用户说明。

**仍需检验的反例**：本机已知密钥到期时间，但只等每 2 小时联网刷新才停止；或者回放入口也因统一授权拦截而无法进入。这两种实现都与已确认的规则不一致，但本次未据此认定当前代码存在这些问题。

**补充**：正常到期与凭证失效、暂停、吊销等其他状态分开定义。到期后 Agent 分析及软件内查看结果已明确允许；数据、比较结果与报告等文件导出仍被禁止，不能通过新增工具绕过限制。

**优先级**：正常到期已完成产品选择；实现与验收为对应交付的 P0，其他授权失效情形仍待决策。

### R4 数据完整性与历史可解释性不能分开排优先级

**原文位置**：第四章“采集结果与完整性”“历史结果追溯”；第五章“参数作用范围”；第九章将历史追溯列为 P1。

原文已经明确完整性计数、配置依据和旧记录未知项。但尚未裁决采集中修改协议、映射、归零、算法或标定时，记录如何保持可解释。

**反驳**：每一行都成功落盘，仍可能得到无法比较的数据。一旦承诺跨次比较、定量分析或可复核导出，解释数值所需的最小依据就成为这些承诺的前提，不能统一后置为 P1。

**反例**：一次采集过程中执行归零，后半段数值基准变化；或算法版本在会话中切换，矩阵尺寸保持不变。导出文件连续且没有缺行，但使用者无法知道哪些数据可以直接比较。

**补充**：定义会话与处理配置的绑定关系。协议、映射和主链路算法等变化，默认在采集停止后生效；确需会话中变化的，记录生效位置并形成可识别分段。归零等必要操作保留事件、参考依据及影响范围。纯视图变化与影响存储值的变化分别处理。

只保存支撑所承诺结果的必要快照与摘要，不要求无差别保存全部串口原始字节。旧数据缺少依据时标为未知，并限制相应比较结论。

**优先级**：定量、跨次比较与追溯交付为 P0；仅做即时相对展示的场景可采用较小范围。

### R5 本地保存缺少完整的数据生命周期与恢复约定

**原文位置**：第五章“运行数据位置”；第八章“更新”“客户交付确认”。

原文说明正常升级应保留用户数据，也说明换电脑和删除目录不属于正常升级，但没有形成备份、恢复、迁移和删除的完整用户流程。

**反驳**：本地存储解决了采集落盘问题，客户仍需要知道电脑损坏、重装和换机后怎样找回可解释的数据。CSV 导出也不能被自动当作完整备份，它未必包含原生回放和追溯所需的配置。

**反例**：客户采集数周后电脑故障。软件授权可以换机处理，但采集记录、配置依据和相关报告只有旧电脑上有副本。交付验收时全部任务通过，后续仍无法完成客户的数据保管要求。

**补充**：明确备份对象、触发方式、保存位置、恢复范围和责任方。至少提供可执行的数据迁移办法，即使首期由交付人员操作。换机时将电脑授权迁移与数据恢复分为两个步骤，不把旧电脑凭据当作可迁移业务数据。删除、磁盘清理、异常退出后恢复和版本不兼容时的只读取回，也应有规则。

**优先级**：依赖长期记录的客户交付为 P0；临时演示场景可明确不承诺长期保管。

### R6 软件密钥无法说明共享电脑上谁能看哪些记录

**原文位置**：第三章“账号角色与操作身份”“身份区分规则”；第七章上传队列凭据隔离规则。

原文已经区分管理端角色与客户端使用者，也正确隔离不同凭据的上传队列。但客户端主要依赖软件密钥，尚未说明多人共用电脑、员工为多个客户配置系统时，本机记录如何分组和授权。

**反驳**：软件使用授权、操作人的身份、本地数据访问权限是三件不同的事。服务器队列隔离不能自动证明本机历史、附件和导出文件也按业务归属隔离。

**反例**：交付员工在同一电脑上服务客户甲与客户乙，随后将电脑交给另一名员工。切换密钥后应能看到哪些本机历史？恢复备份到客户电脑时，哪些对象必须排除？现有规则不能回答。

**补充**：先决定是否支持共用设备和多客户工作。如果首期只支持专用电脑，应写入支持范围；如果支持，则定义工作区或项目归属、操作人记录、历史和附件访问、导出与迁移范围，以及切换密钥时的提示。不必因此直接引入完整企业身份系统。

**优先级**：共用设备或多客户工作进入支持范围前为 P0；否则明确限制并观察需求。

### R7 Agent 的验收应包含失败成本与人工完成路径

**原文位置**：第四章“Agent 配置任务与提案应用”“Agent 价值与效果验收”；第一章 Agent 任务收益指标。

原文已经把配置提效与自助训练分开，也纳入人工接管和恢复成本。首批任务、费用承担方与效果门槛仍待决策。

**反驳**：训练最多 60 秒，仅约束一个本地训练阶段，不能证明完整任务省时或费用可控。附件整理、模型等待、选数标注、校验与返工都可能决定最终收益。训练出模型，也不等于客户愿意长期准备标签。

**反例**：Agent 快速生成配置，但员工花更长时间定位错误映射；一次成功演示看起来提效，失败任务和后续排障却消耗更多工时。

**补充**：首批仅选择输入清楚、人工基线可测、可以核验和恢复的任务。对照记录全部尝试的端到端时间、费用、首次通过、接管和返工；避免只统计成功案例。模型不可用或预算耗尽时，应有人工配置或交付支持路径。客户自助训练需要另行证明标注负担、使用频率和实际分类收益。

**优先级**：作为可选试点为 P1；作为销售承诺、默认工作入口或费用承诺前为 P0。

**通用分析方向的边界**：交互方向已确认为客户先提具体问题，Agent 再组织所需分析与结果。现有[Agent 手册](embedded-agent.md)已列出分类训练与评价能力，自动分析报告仍列为暂未支持，因此交互方向确认与能力接入分别记录。计算由本机工具完成，结论关联记录、区间、参数和工具结果；已有能力不足时说明缺口，提供替代分析或转交支持。业务评价缺少依据时先澄清，不将生成回答解释为任意新功能已经可用。

### R8 上传内容并不自动形成有效的客户支持

**原文位置**：第六章“管理观测范围”；第七章“上传选择与队列恢复”；第八章统一问题单建议。

原文已经说明聊天和统计覆盖不完整，接收方与开关分别管理，上传不代表全量可观测。但保存期限、访问和删除流程尚未定案，问题单仍是建议。

**反驳**：更多聊天不一定更容易定位串口、磁盘或版本问题；客户也可能关闭上传。支持能力如果依赖聊天可见，就无法覆盖不使用 Agent、长期离线或不允许同步的客户。

**反例**：客户报告“有画面但没有保存”。管理员能看见聊天，却没有本机实际写入状态、磁盘余量和当时版本组合，仍需反复联系客户；另一名关闭同步的客户连这部分线索也没有。

**补充**：先明确支持必需的本机状态与用户主动提供的诊断摘要，包括版本、连接、最近有效帧、采集及写入状态、磁盘和错误阶段。用户预览后再选择导出或发送；默认排除凭据、聊天正文和原始压力数据。收到问题后记录责任人、处理状态和关闭证据。聊天同步作为独立能力评价其支持收益。

上传选择还应覆盖重新开启后的历史队列、打开旧会话的触发、接收方变化、服务端保存期限和处理入口，不能只介绍首次开启。

**优先级**：涉及上传内容和处理规则的扩大交付为 P0；诊断体验可按支持成本分期实现。

### R9 软件回退能否恢复业务取决于数据与配置兼容性

**原文位置**：第八章“网页缓存与回退”“性能容量与版本组合验收”。

原文已经区分安装包、网页和系统包，也要求组合验收、数据可读性和回退验证。这些要求仍缺少具体门槛与不兼容时的处理策略。

**反驳**：软件能切回旧版本，不足以证明业务可恢复。如果安装包升级引入数据迁移或配置格式变化，旧版可能不能继续使用新数据。网页外壳启动成功也不足以支持扩大推广。

**反例**：新版升级完成并能打开界面，客户在采集后发现异常。旧版安装恢复成功，却无法读取新版本写入的记录；客户仍无法继续工作或取回结果。

**补充**：对每个拟支持的版本组合明确关键任务、负载和通过门槛，单独说明数据或配置迁移的可逆性。不支持直接回退时，提供经验证的恢复副本、兼容读取或导出取回路径。推广前确定停止条件、负责人及客户恢复办法。

**优先级**：涉及数据或配置迁移、对存量客户推广的组合为 P0。

### R10 交付提速还需要标准范围与持续支持成本约束

**原文位置**：第一章“交付周期与支持工时”指标；第三章“软件权益与业务终止”；第四章“Agent 价值与效果验收”。

原文已要求计入失败和返工，并将费用承担方与支持范围列为待决策。尚需补充的是如何据此决定定制范围、接单边界及后续投入。

**反驳**：配置更快，不代表一类客户就值得扩大交付。首次适配只占交付工作的一部分，后续校准、解释数据、修改算法和特殊环境支持也可能持续消耗员工时间。

**反例**：一套新设备一天完成配置，却需要员工每周协助修标签和解释分类结果。首次交付周期缩短，但服务投入随着客户数量持续增加，产品复用收益无法覆盖支持负担。

**补充**：将一次性适配、客户专属修改、可复用产品能力和约定期支持分别记录。销售前明确标准交付、可选服务和单独评估项；对新设备、定量测量与专属算法按完整交付及支持投入评估范围和费用。先建立个案基线，再决定扩大、另行报价或暂不承接，不编造统一利润目标。

**优先级**：受控试点可持续收集数据；形成可重复销售方案及批量接单前定案。

## 三 可以直接补入原文的候选条款

以下条款供产品评审采用，其中密钥正常到期部分已由产品方确认。涉及现行行为变化的，应同步专项契约、实现、迁移和验收记录。

### 补充一 阶段交付基线

建议放入第一章“阶段目标与用户价值”之后。

> 每阶段启动前确定主要客户类型、核心业务任务、交付对象和成功结果，并明确不纳入本阶段承诺的场景。以员工完成受支持设备配置、客户独立完成一次可复核采集任务作为首阶段候选目标；客户自助训练独立试点。
>
> 客户验收同时检查操作链完成和约定业务结果。试点记录客户原有方法、当前耗时或失败点、使用后的结果、员工协助及返工投入，保留未完成和中止样本。涉及数据比较的任务，应先确认其量值和追溯依据。
>
> 扩大交付前，以预先确认的目标值和支持环境判断是否继续。尚未确定目标值的指标仅用于建立基线，不作为对外成功承诺。
>
> 标准交付、客户专属修改和持续支持分别约定范围，并记录失败与返工投入。超出标准范围的新设备、算法、定量分析和服务要求，在承诺前单独确认工作量、责任及费用。

### 补充二 授权状态与用户动作

正常到期条款已写入第四章“运行中授权失效与数据收尾”。下表区分已确认规则与其他候选方向，实施时需核对专项授权契约。

| 情况 | 新建受限操作 | 当前接收与尾部提交 | 已有本机数据 |
| --- | --- | --- | --- |
| 网络失败且凭证、密钥仍有效 | 按有效范围允许 | 按有效范围继续，并显示有效期限 | 按既定权益访问 |
| 软件密钥正常到期，已确认 | 阻止新建或继续采集 | 立即停止新增接收；到期前已接收队列继续提交当前库并核对结果 | 可查看、回放及 Agent 分析，软件内查看结果；禁止数据和分析结果导出 |
| 凭证失效但密钥尚未到期，待决策 | 提供刷新入口，按确认规则限制 | 停止时点与收尾规则另行确认 | 历史权益另行确认 |
| 服务端明确拒绝，待决策 | 按拒绝范围阻止 | 执行对应受控结束规则；已有队列提交不视为继续采集许可 | 历史访问与导出权益单独确认，并记录拒绝范围及原因 |
| 更换电脑 | 按新电脑授权结果处理 | 先核对旧任务与数据状态 | 数据恢复与授权迁移分开验收，不迁移电脑绑定凭据 |

> 正常到期应在开始可能跨越有效期的任务时明确提示。预警时点仍需确定；停止时点已确认为到期立即停止，不设继续采集时段。已知到期时间不等待下一次联网刷新，断网不延长期限。
>
> 授权中断后分别展示停止接收、正在收尾、提交完成、部分保存或保存结果待核查。正常到期后保留历史查看、回放和 Agent 分析入口，结果在软件内展示，数据及分析结果的文件导出请求被拒绝；其他终止状态另行定义。

### 补充三 会话配置与历史解释

建议放入第四章“历史结果追溯”之后。

> 每次采集绑定当时实际生效的系统与通道身份、处理配置修订、数据阶段、单位、时间来源和存储策略。只承诺在已保存依据能够支持的范围内复现、比较和解释结果。
>
> 影响输入身份或存储值解释的协议、映射和算法修改，默认在停止采集后生效。允许采集中变更的操作，须记录生效时间或数据位置、变更内容及影响范围，并在回放与导出中保留分段依据。归零操作记录参考状态；纯显示参数按是否影响导出解释分别处理。
>
> 历史查看使用原记录的解释依据；使用新算法计算时生成独立分析结果并关联原记录。未知依据显式标记，不以当前配置补写历史事实。

### 补充四 本机数据保管与恢复

建议放入第五章“运行数据位置”之后。

> 交付时说明采集数据、配置、报告和附件的保管责任、备份范围及恢复方式。CSV 是数据交换结果，只有在满足约定恢复范围时才能作为备份交付。
>
> 备份应列明包含对象、生成时间、版本、校验结果和可恢复范围。活动数据库通过已支持的一致性备份方式处理，不能以随意复制运行中文件代替有效备份。换机恢复后核对记录数量、通道、配置依据、回放和导出，再确认迁移完成。
>
> 软件密钥、模型密钥和电脑绑定凭据不随普通数据备份自动迁移。删除与清理操作说明实际影响、是否可恢复和处理结果；异常退出后标识未正常结束的会话，分别核对已提交、可恢复和未知范围。
>
> 如首期暂不提供自助备份，应提供可执行的交付支持办法并明确边界，不能默认由客户理解内部数据目录。

### 补充五 版本推广与恢复

建议放入第四章“发布影响与撤回边界”和第八章对应小节。

> 首次交付建立明确版本基线。后续版本发布形成候选，经目标环境验证和显式推广后改变适用客户的目标版本。迁移前保留现有客户实际适用基线，并明确无指针客户的处理办法。
>
> 推广前展示客户范围、版本差异、已验证宿主与网页组合、启用时机和恢复方案。采集中的安装切换、待启用版本和撤回提示分别定义，不把后台下载等同于可立即启用。
>
> 涉及数据或配置迁移时，说明旧版本的可读和可写范围、迁移可逆性，以及不能直接回退时的数据取回和恢复办法。版本已切回、已有记录可读和客户核心任务恢复分别验收。
>
> 撤回记录未下载、待安装、已安装、运行中及离线客户的实际状态。发布负责人持续跟踪到客户完成约定处置；不能仅凭服务端状态认定客户已恢复。

### 补充六 Agent 试点与人工支持

建议放入第四章“Agent 价值与效果验收”之后。

> Agent 首批任务按输入可确认、修改可核验、失败可处理的原则选择。每类任务记录准备、执行、验证、接管和返工的总耗时，统计全部尝试的费用和结果，与同类人工任务比较。
>
> 历史分析从客户对话中的具体问题开始，按需组织比较、判断或报告。验证样例用于确认能力，不成为客户必须选择的固定入口；缺少必要数据、评价依据或计算工具时，说明缺口与可执行的后续办法。
>
> 任务开始前说明模型接收方、预计处理内容及适用费用控制；达到既定费用、时间或失败门槛后，提供停止和人工完成路径。取消任务后继续核对已发生的修改与费用，不能以停止回答代表全部动作撤销。
>
> 自助训练单独验证标签准备负担、数据适用范围、误报漏报、未知结果和识别延迟。未达到门槛时限制在已确认试点中使用，不随配置助手一起扩大承诺。
>
> 按工具列明可继续、可恢复和必须人工处理的动作。任务中断后如发生人工修改、依赖删除或其他任务复用，继续和恢复均重新核对对象修订；冲突时不覆盖后续修改，并给出剩余处理动作。

### 补充七 支持与数据提供

建议放入第六章“管理观测范围”之后。

> 关闭聊天同步、使用统计或模型服务后，客户仍有问题反馈入口，并能查看必要的本机运行状态。支持记录至少关联版本组合、目标系统与通道、连接及有效帧状态、采集和写入结果、错误阶段。
>
> 诊断摘要由用户预览后选择导出或提供，默认排除授权凭据、模型密钥、聊天正文和原始采集数据。额外业务数据按本次支持需要单独选择。
>
> 支持请求记录影响、责任人、临时处置、下一次处理节点及关闭证据。若现场已停止工作或存在保存异常，应按预先确定的优先级处理；响应时间由具体服务方案确认，不在能力说明中暗示统一承诺。

### 补充八 上传选择与服务端处理

建议补入第七章“上传选择与队列恢复”。

| 用户动作 | 必须可理解的结果 |
| --- | --- |
| 首次开启 | 接收方、内容类别、用途、触发方式和适用查看范围 |
| 暂停 | 停止新的上传；明确本地待传内容保留与否 |
| 清理待传 | 清理指定范围的本地队列；说明不等于删除本机会话或服务端数据 |
| 重新开启 | 明确是否恢复旧队列及其会话、时间范围，按确认的范围处理 |
| 打开旧会话 | 明确是否触发本次同步，避免仅凭“不遍历归档”推断不会上传 |
| 改接收方或凭据 | 复核接收范围与队列归属，旧范围内容不自动发送至新范围 |
| 请求处理已上传数据 | 提供保存期限说明、受理入口、处理责任和结果反馈 |

> 服务端数据处理流程和自定义接收方责任在相应能力扩大交付前确认。对上传范围的选择不自动改变外部模型任务请求，两者按实际接收方分别说明。

## 四 交付前的故障情景验收

以下为需要补齐的场景设计，尚无实测结果。每项绑定具体版本、环境、预期和证据；数值门槛在对应试点或推广开始前确认。

| 场景 | 必须回答的问题 | 通过证据 |
| --- | --- | --- |
| 长时采集中密钥正常到期 | 是否立即停止新增接收、已有队列是否提交原库 | 到期中断原因、停止位置、原库提交、可回放及 Agent 分析、数据与分析结果导出拒绝；覆盖断网、重启及休眠恢复 |
| 采集中收到服务端明确拒绝 | 按该拒绝类型如何受控结束，历史权限如何处理 | 已确认的独立规则、授权原因、停止位置及提交结果 |
| 界面有画面但存储失败 | 用户何时知道，怎样取回已保存范围 | 写入状态、异常提示、数据库可读范围及缺口 |
| 收尾时退出或断电后重启 | 哪些记录已确认，哪些待核查 | 恢复检查、结束原因、提交边界，不误报正常完成 |
| 会话中归零或尝试改映射 | 是否允许，数据怎样分段解释 | 生效位置、配置依据、回放及导出的一致解释 |
| 新版发布但尚未推广 | 各类客户目标版本是否变化 | 固定指针、默认指针与无指针客户的前后对照 |
| 问题版本撤回 | 不同安装与联网状态的用户怎样恢复 | 客户实际版本、运行状态、处置结果及未处理范围 |
| 新版本迁移数据后回退 | 旧版还能读写什么，不能时怎样恢复 | 原记录、新记录、配置兼容结果及取回路径 |
| 换电脑或恢复备份 | 业务数据是否完整，授权是否单独处理 | 记录和配置清单、回放导出结果、授权登记结果 |
| 关闭同步后再开启 | 旧队列上传范围是否符合用户选择 | 操作时的选择、实际事件范围及对应接收确认 |
| Agent 写入后回执丢失或用户随后手动修改 | 是否能辨认已完成步骤，避免重复和覆盖后续修改 | 实际对象修订核查、任务状态、后续可执行动作 |
| 共享电脑切换客户 | 本机记录、附件和导出可见范围是什么 | 工作区归属或明确的专用电脑限制 |

## 五 风险分级与下一轮决策

### 必须处理的风险

这里的 P0 指对应能力承诺或推广前的阻断项，不要求为了关闭全部风险而停止所有探索。

| 项目 | 范围与优先级 | 建议牵头人 | 必须完成的结果 | 完成节点 |
| --- | --- | --- | --- | --- |
| 主要客户与任务 R1 | 商业试点前置项 | 产品，销售与交付参与 | 一份明确的试点范围、业务结果及价值验证计划 | 商业试点启动前 |
| 发布与推广 R2 | 存量版本交付 P0 | 发布负责人，客户端及服务端参与 | 版本规则、存量迁移和影响预览 | 影响存量客户的发布前 |
| 授权与历史权益 R3 | 正常到期产品规则已确认，实现与其他失效规则为 P0 | 产品，商务与研发参与 | 原库收尾、可回放与 Agent 分析但不可导出的验收；其他状态权益矩阵 | 订单承诺及场景交付前 |
| 历史依据 R4 | 定量或可比较数据 P0 | 产品，数据与算法负责人参与 | 最小依据、变更分段和未知项展示 | 承诺对应结果前 |
| 数据保管 R5 | 长期数据使用 P0 | 客户端与交付负责人 | 备份、恢复、迁移和删除流程 | 长期记录场景交付前 |
| 本机访问 R6 | 共用电脑或多客户支持 P0 | 产品与客户端负责人 | 可见范围，或明确的支持限制 | 纳入支持范围前 |
| Agent R7 | 可选试点 P1 | Agent 产品及交付负责人 | 人工对照、完整成本与退出标准 | 扩大入口或承诺费用前 |
| 支持与上传 R8 | 数据处理承诺 P0，诊断体验按需迭代 | 产品，服务端与支持负责人 | 接收、保存、处理规则和可执行支持入口 | 扩大上传能力前 |
| 组合回退 R9 | 迁移及存量推广 P0 | 发布、存储与测试负责人 | 兼容范围、恢复路径和停止推广条件 | 对应组合推广前 |
| 定制与支持 R10 | 可重复销售前置项 | 产品、商务与交付负责人 | 标准范围、完整投入基线及超范围处理办法 | 批量承诺与接单前 |

### 不宜过度投入的担忧

- **必须立即变成纯云产品**：本地采集有清楚的职责定位。优先把本地保存、授权和恢复做可靠，无需为形式统一而迁移高频链路。
- **必须马上统一所有历史存储结构**：对外解释一致、必要追溯依据与兼容读取可以先完成；内部格式统一应由具体收益驱动。
- **必须立刻支持完全断网导入公司包**：只有目标客户确有隔离网需求时才成为交付前置条件。当前不支持应清楚说明。
- **必须让 Agent 覆盖全部操作**：先验证少量高价值任务；自动化覆盖率本身不能证明产品价值。

### 仍需客户证据的假设

1. 购买者实际购买的是设备配套能力、定制交付服务还是持续的软件分析能力，不同答案会改变投入和权益设计。
2. 操作者取得 CSV 后是否仍依赖员工处理，是否需要标准报告或其他后续流程。
3. 客户是否具备准备训练标签的时间和判断能力，自助训练是否形成持续需求。
4. 现有电脑与网络是否符合支持范围，长期离线、共用电脑和换机是否为常态。
5. 公司系统是否能稳定复用，还是每次交付都需要大量特殊修改；这决定配置平台能否实际降低支持投入。

建议在试点登记时记录原有做法与验收结果，观察真实任务，并持续记录失败、等待和返工。用这些证据决定继续、收缩或停止某项投入，避免仅用内部演示裁决。

## 六 建议的修订顺序

先确定第一章的主要客户、阶段任务及成功结果，再关闭授权、版本交付和数据解释等会影响客户承诺的规则。随后补齐数据恢复与支持流程，最后依据选定场景填写性能门槛和 Agent 试点标准。

第九章应从待办清单升级为决策记录：每项明确采用方案、确认人、适用客户、影响契约、迁移安排、实现状态和验证证据。对原文已有的待决策项，重点是完成裁决及落实；继续添加更多原则性提示不能代替这一步。
