# Shroom 平台介绍与使用指南

> 面向非技术用户、应用工程师和开发者的统一说明  
> 文档状态：产品目标态说明 + 当前版本使用指南  
> 更新日期：2026-08-28

## 先看这一页

**一句话愿景：让懂传感器场景的人，不写代码、不触碰稳定内核，也能把需求变成可验证、可部署的传感器应用。**

Shroom 不是一个“让 AI 随意写软件”的工具。它把平台分成两部分：

- **稳定内核**负责连接传感器、正确接收和处理数据、保存、回放、导出，以及在本地可靠运行。
- **应用包**负责每个项目不同的界面、展示方式、指标、操作流程、品牌和报告。

在目标平台中，AI Studio 位于桌面内核之外。它根据用户需求，从经过验证的能力中组装一个应用包，再经过预览、检查和批准后交给 Shroom Desktop 运行。

```text
用户需求与项目资料
        ↓
平台外的 AI Studio
        ↓
声明式 Shroom 应用包
        ↓  检查、仿真、预览、批准、签名
稳定的 Shroom Desktop 内核
        ↓
本地连接、实时展示、采集、回放与导出
```

> [!IMPORTANT]
> 本文同时描述“当前可用能力”和“目标态能力”。目标态不等于已经上线的功能，也不构成当前版本的交付承诺。

### 当前边界

| 状态 | 含义 | 代表能力 |
| --- | --- | --- |
| **当前可用** | 已存在于当前项目，可按具体传感器和交付版本使用 | 桌面运行、串口连接、实时数据、2D/3D 展示、本地采集、回放、CSV 导出、后端 SDK |
| **逐步建设** | 已有基础，但仍需统一产品入口、规则和验证 | 传感器配置中心、能力目录、应用模板、统一诊断与完整回归 |
| **目标态** | 理想 Shroom 平台计划提供，尚不能视为当前产品能力 | AI Studio、声明式应用包、签名发布、兼容检查、一键回滚、团队模板库 |

当前版本仍以压力和触觉传感器桌面应用为主，并非已经完成的通用 AI 应用生成平台。不同传感器的支持程度不同；只有经过真实硬件验证的配置，才应进入正式交付。

### 怎么阅读本文

- 第一次使用 Shroom：先看“产品与角色选择”以及“快速开始”。
- 要为客户制作一套新应用：重点看“能力中心”“AI 推荐路径”和“使用指南”。
- 要接入新传感器或算法：重点看“开发者路径”和项目的 [SDK 说明](../sdk/README.md)。
- 要理解产品范围：查看 [Shroom 产品概念一页纸](./shroom-product-concept-one-pager.md) 和 [当前 PRD](../PRD-Shroom.md)。

## 1. 价值主张：从重复开发到可靠复用

### 1.1 现在的问题

传感器项目经常从同一组工作重新开始：接协议、调线序、做清零、写采集、画热力图、接三维模型、做导出，然后重新打包交付。

这带来三个直接问题：

1. **交付慢**：懂场景的人要排队等软件开发。
2. **维护难**：每个客户一套分支，项目越多越不敢改。
3. **错误隐蔽**：方向、线序、标定或算法错了，软件可能不报错，却把错误结果一路带到回放和报告。

### 1.2 Shroom 的回答

Shroom 把“应该稳定的能力”和“需要变化的需求”分开：

- 连接、接收、保存、回放和导出由稳定内核负责。
- 传感器配置、算法节点、展示组件和报告模板沉淀到能力中心。
- AI 帮助用户表达需求并选择能力，但不能替用户发明硬件事实。
- 每个项目最终交付一个独立应用包，不为小改动重写整个桌面程序。

### 1.3 用户获得什么

| 用户 | 使用前 | 使用后目标 |
| --- | --- | --- |
| 非技术用户 | 看不懂串口和原始数字，只能等人做界面 | 选择现成应用，连接设备后直接观察、采集和导出 |
| 应用工程师 | 每个客户需求都要交给开发人员 | 用自然语言和模板做出应用，拿真实数据验证后交付 |
| 开发者 | 大量时间消耗在重复页面和项目分支 | 专注接入新硬件、验证算法和维护稳定内核 |
| 企业 | 软件交付依赖个人经验，项目难复用 | 把验证过的协议、算法、渲染和模板变成长期资产 |

### 1.4 三条不妥协原则

1. **测量正确优先于画面好看。** 漂亮的热力图不能证明方向、标定或数据含义正确。
2. **AI 负责加快表达，不负责决定事实。** 线序、标定系数、硬件参数和安全阈值必须有依据。
3. **客户和 AI 不修改桌面内核。** 变化发生在应用包中；超出能力中心的需求必须转交开发者或厂商处理。

## 2. 产品与角色选择

### 2.1 先选择你的角色

| 角色 | 典型情况 | 适合入口 | 你最终会得到 |
| --- | --- | --- | --- |
| **非技术用户** | 使用已经交付的设备和应用；不负责协议、算法或软件开发 | Shroom Desktop | 实时画面、采集记录、历史回放、导出文件 |
| **应用工程师** | 懂传感器和客户场景，希望快速做演示、试验或交付版本 | AI Studio + 能力中心（目标态） | 经验证的 Shroom 应用包 |
| **开发者** | 需要接入新协议、新点位映射、新算法或新的平台能力 | Shroom SDK + 验证工具 | 可进入能力中心的受控能力，以及厂商签名版本 |

“非技术”不等于“不需要场景知识”。用户仍需知道自己连接的是什么传感器、想观察什么现象，以及什么结果符合业务常识。

### 2.2 再选择你要使用的产品

#### Shroom Desktop — 运行和使用

**状态：当前可用。**

用于连接硬件、观察实时压力、采集数据、回放历史记录和导出文件。它是最终在客户电脑上运行的稳定桌面端。

适合：非技术用户、现场交付人员、研发测试人员。

#### Shroom AI Studio — 描述和生成

**状态：目标态。**

用于描述应用需求、选择传感器和模板、生成界面与流程、用录制数据预览，并提交应用包发布。

适合：应用工程师、产品工程师和经过授权的方案人员。

#### Shroom 能力中心 — 查找和复用

**状态：逐步建设。**

用于管理经过验证的传感器、数据处理、算法指标、展示组件、报告模板和行业应用模板。

适合：应用工程师和开发者。

#### Shroom SDK — 接入和扩展

**状态：当前已有后端 SDK。**

用于开发和验证新的传感器配置、协议解析、线序、采集、回放和导出能力。SDK 面向开发者，不是普通客户入口。

### 2.3 按目标快速选择

| 你的目标 | 推荐路径 |
| --- | --- |
| 使用已交付应用查看数据 | 直接进入 Shroom Desktop |
| 使用已支持传感器做一次采集并导出 | Shroom Desktop 的实时、采集、回放和下载流程 |
| 为已支持传感器更换界面、品牌或报告 | 目标态 AI Studio 生成新应用包 |
| 接入一个平台从未验证过的传感器 | 先走开发者接入和真实硬件验证，再制作应用 |
| 添加新的算法或关键判断规则 | 先由算法负责人和开发者验证，再放入能力中心 |
| 生成医疗诊断或安全控制结论 | 不允许 AI 自主生成或发布，必须走相应专业和合规审查 |

## 3. 能力中心：把做过一次的事变成资产

能力中心可以理解为一个“经过检查的零件库”。AI Studio 只能从这里选择已经允许使用的能力，不能临时创造一个未经验证的驱动、算法或标定规则。

### 3.1 能力分类与状态

| 能力类别 | 用用户语言解释 | 当前状态 |
| --- | --- | --- |
| 传感器连接 | 找到设备、选择串口、按正确速度接收数据 | 当前可用，支持程度随传感器而异 |
| 传感器配置 | 记录矩阵大小、数据格式、线序和默认参数 | 已有配置基础，需继续统一与验证 |
| 数据处理 | 把设备发来的内容变成可用的压力矩阵和统计值 | 当前已有多类处理能力 |
| 清零与标定 | 去掉空载底值，或按经批准的方法换算测量值 | 清零当前可用；标定依具体项目 |
| 2D 展示 | 数字矩阵、热力图、趋势图和统计卡片 | 当前可用 |
| 3D 展示 | 把压力映射到座椅、床、手、脚或人体模型 | 当前支持多个项目，需按模型验证 |
| 数据采集 | 给一次实验命名并把数据保存到本地 | 当前可用 |
| 历史回放 | 重新播放一次已经保存的采集 | 当前可用 |
| 数据导出 | 将历史数据导出为 CSV 等可分析文件 | 当前可用，字段随场景变化 |
| 算法与指标 | 压力中心、左右平衡、面积、峰值或场景算法 | 部分当前可用，必须逐项说明和验证 |
| 报告模板 | 将结果整理为客户可读的报告 | 部分项目已有，尚未形成统一中心 |
| 应用模板 | 把一套完整场景保存为可复用起点 | 目标态 |
| 发布与回滚 | 检查、签名、安装、保留旧版并在需要时恢复 | 目标态 |

### 3.2 一项能力何时可以正式使用

进入正式能力中心前，至少应满足：

- 有明确名称、用途、输入和输出说明。
- 在指定真实硬件上通过验证，不只是在模拟数据上能运行。
- 实时画面、保存数据、历史回放和导出结果含义一致。
- 有一组可重复使用的录制数据和预期结果。
- 有版本、负责人、适用传感器和已知限制。
- 出错时能够给出明确提示，而不是默默产生看似正常的错误结果。

### 3.3 能力中心不会收录什么

- 没有来源的标定系数或阈值。
- 只能在某位开发者电脑上运行的临时代码。
- 没有真实硬件或录制数据验证的传感器配置。
- 会直接修改 Electron 内核、系统权限或底层通信通道的客户脚本。
- 没有说明数据含义、适用范围和责任人的算法输出。

## 4. AI 推荐路径：先判断任务，再生成应用

AI 的第一项工作不是立即生成，而是判断当前需求能否由已验证能力安全完成。

### 4.1 AI 会先问什么

1. **谁来使用？** 是现场操作人员、研发人员、数据分析人员，还是客户演示人员？
2. **连接什么？** 传感器型号、数量、连接方式和是否已有验证配置。
3. **需要看什么？** 热力图、数值、三维模型、趋势、报警还是多个视图。
4. **需要做什么？** 清零、开始采集、暂停、回放、比较、导出或生成报告。
5. **如何判断正确？** 已知按压点、方向、标定方法、参考结果和验收人。
6. **如何交付？** 电脑系统、是否离线、品牌要求、使用地点和数据隐私要求。

### 4.2 推荐路径

| AI 判断 | 推荐动作 | 是否可以直接生成 |
| --- | --- | --- |
| 硬件和需求都已有验证模板 | 从模板生成应用包并进入预览 | 可以 |
| 硬件已验证，但界面、指标或报告是新组合 | 从能力中心组装，补充必要问题后预览 | 可以 |
| 硬件存在，但配置尚未通过真实设备验证 | 先创建“传感器接入任务” | 不可以发布 |
| 需求需要新算法，但没有预期结果或负责人 | 创建“算法验证任务” | 不可以发布 |
| AI 无法确认线序、方向或标定依据 | 要求人工提供证据和确认 | 不可以发布 |
| 涉及医疗诊断、安全控制或法规要求 | 转交专业负责人和合规流程 | 不可以自主发布 |

### 4.3 怎样描述一个好需求

可以按下面的格式告诉 AI：

```text
使用者：谁会用这套应用
传感器：型号、形态、数量和是否已有 Shroom 配置
任务：使用者要完成什么工作
展示：必须看到哪些画面和指标
操作：需要哪些按钮和步骤
输出：要保存、导出或生成什么
验收：怎样证明方向、数值和流程正确
交付：运行电脑、是否离线、品牌和语言要求
```

示例：

> 现场工程师使用一块已经验证的 16×16 坐垫传感器。需要实时热力图、压力中心和左右平衡；可清零、开始或停止采集；采集结束后能回放并导出 CSV。已知从使用者视角看，左上角按压必须出现在画面左上角。应用在 Windows 电脑离线运行，使用客户品牌色。

### 4.4 AI 能做和不能做的事

AI 可以：

- 把自然语言需求整理成结构化清单。
- 推荐已验证的传感器、组件、算法和模板。
- 生成应用包中的页面布局、流程、文案、品牌和能力组合。
- 根据检查结果提示缺失项，并协助修改应用包。

AI 不可以：

- 修改 Shroom Desktop 内核或扩大系统权限。
- 在应用包中加入任意可执行代码。
- 猜测传感器协议、线序、标定系数或安全阈值。
- 跳过真实数据仿真、人工预览、批准和版本记录。
- 将“画面看起来合理”当成“测量结果已经正确”。

## 5. 快速开始

### 5.1 当前版本：10 分钟完成一次采集和导出

#### 开始前准备

- 已安装与当前交付版本匹配的 Shroom Desktop。
- 传感器、数据线和必要驱动可用。
- 知道要选择的系统或传感器类型。
- 知道设备对应的串口；如果版本支持自动识别，也应核对识别结果。
- 准备一个可以写入文件的导出目录。
- 了解一个简单验收动作，例如按压矩阵左上角并确认画面方向。

#### 操作步骤

1. 打开 Shroom Desktop，按当前授权方式进入主界面。
2. 选择与你的硬件一致的系统或传感器类型。
3. 切换到“实时”模式。
4. 选择串口和通信速度，或使用交付版本提供的一键连接。
5. 等待画面稳定更新，确认连接状态和数据刷新正常。
6. 在传感器无负载、状态稳定时执行“清零”。
7. 用已知位置轻压传感器，确认画面位置、方向和变化趋势正确。
8. 输入清楚的采集名称，开始采集；完成后停止采集。
9. 切换到“回放”，找到刚才的记录并播放。
10. 选择“下载”或“导出”，设置保存目录，完成后打开文件检查。

#### 完成标准

- 连接后数据持续刷新，没有频繁断开。
- 已知按压位置在 2D 和 3D 画面中方向一致。
- 清零后空载值符合当前项目验收要求。
- 回放内容与采集时看到的变化一致。
- 导出文件可打开，记录时间、矩阵和关键指标含义正确。

### 5.2 目标态：用 AI Studio 制作一个应用包

1. 新建应用，选择“从验证模板开始”。
2. 选择角色、使用场景和已经验证的传感器配置。
3. 按需求模板描述展示、操作、输出和验收方式。
4. 回答 AI 提出的必要问题；不确定的硬件事实不要猜。
5. 生成第一版应用包。
6. 选择一段真实录制数据进行仿真和预览。
7. 检查方向、数值、指标、操作流程和导出结果。
8. 查看本次变更内容、使用的能力版本和检查结果。
9. 由有权限的负责人批准并签名。
10. 将应用包导入兼容的 Shroom Desktop；保留上一个可用版本以便回滚。

如果生成过程中提示“缺少平台能力”，不要尝试绕过。应用工程师应补充资料，由开发者或厂商完成能力接入和验证。

### 5.3 开发者：接入新传感器能力

1. 先检查能力中心或 SDK 中是否已有对应传感器配置。
2. 收集协议说明、样例数据帧、矩阵尺寸、通信速度、线序或点位表，以及真实硬件。
3. 使用 SDK 建立传感器配置和解析规则，避免在客户应用中写临时分支。
4. 准备正常、断帧、错误长度、断线重连和方向检查样例。
5. 验证实时、采集、回放和导出四条路径的一致性。
6. 记录能力版本、适用硬件、已知限制和预期结果。
7. 通过评审后再进入能力中心，供应用工程师和 AI Studio 使用。

具体接口和示例见 [Shroom Backend SDK](../sdk/README.md)。

### 6.3 为新项目准备的资料清单

应用工程师在发起新项目时，尽量一次准备：

- 传感器型号、照片、数量和连接方式。
- 协议说明或厂商数据格式说明。
- 至少一段真实原始数据和对应操作说明。
- 矩阵尺寸、物理方向、点位表或模型映射表。
- 清零和标定方法，以及标定依据。
- 希望展示的画面、指标和操作流程。
- 导出字段、报告样例、语言和品牌要求。
- 运行电脑系统、网络条件和数据隐私要求。
- 验收负责人以及“什么叫正确”的具体标准。

## 7. 使用指南

### 7.1 常用词解释

| 名称 | 简单解释 |
| --- | --- |
| 系统类型 | 当前桌面版本中，一组特定硬件和展示方案的选择项 |
| 传感器配置 | 描述某个传感器怎样连接、怎样理解数据以及怎样排列点位的记录 |
| 实时模式 | 直接显示当前传感器正在产生的数据 |
| 采集 | 把一段实时数据保存到本地，供以后查看或导出 |
| 回放 | 按时间顺序重新播放一次历史采集 |
| 清零 | 在已知空载状态下，记录背景值并从后续数据中扣除 |
| 标定 | 用有依据的方法将读数换算到约定单位或参考尺度；标定不等于清零 |
| 能力 | 一个经过验证、可以复用的连接、算法、展示或输出模块 |
| 应用包 | 描述某个应用使用哪些能力、页面和流程的受控交付文件 |
| 稳定内核 | 负责硬件、数据和本地运行的 Shroom Desktop 核心部分 |

### 7.2 连接传感器

1. 先确认当前应用或系统类型与实物一致。
2. 插入传感器后再刷新串口列表；如果没有出现，检查线缆、驱动和系统设备列表。
3. 多路系统可能需要分别选择座面、靠背、头枕、左手或右手端口，不要交叉绑定。
4. 使用项目提供的默认通信速度。没有协议依据时不要反复猜参数。
5. 连接成功后先观察空载数据，再做已知位置按压测试。

如果软件显示“已连接”但画面不合理，不要直接开始正式采集。这可能是系统类型、通信速度、帧格式或线序不匹配。

### 7.3 检查方向和点位

方向错误通常不会导致软件崩溃，因此必须主动检查：

1. 约定从哪个视角观察，例如“使用者视角”或“面对传感器视角”。
2. 依次按压左上、右上、左下、右下和中心。
3. 比较数字矩阵、热力图和三维模型的位置。
4. 保存一段检查数据，并确认回放和导出后的方向仍然一致。

发现左右、上下、旋转或局部点位错误时，应修正传感器配置或映射能力，不能只在某一个画面上临时翻转掩盖问题。

### 7.4 清零与标定

#### 清零

- 在传感器无负载且放置稳定时执行。
- 清零后先观察空载，再用已知动作复查响应。
- 移动、弯折或重新安装传感器后，可能需要重新清零。

#### 标定

- 必须使用项目批准的方法、参考载荷和系数。
- 记录标定日期、设备、方法和负责人。
- AI 只能引用已经批准的标定信息，不能自行推算并作为正式依据。

### 7.5 实时观察

不同视图回答不同问题：

- **数字矩阵**：某个点的具体值是多少？
- **热力图**：压力集中在哪里，分布怎样变化？
- **三维模型**：压力与座椅、人体、手足等真实部位是什么关系？
- **趋势图**：某个指标随时间怎样变化？
- **统计卡片**：当前峰值、总和、面积或压力中心是多少？

建议至少保留一种精确数值视图，避免只凭颜色判断。色阶范围、平滑和插值会影响画面观感，但不应改变原始测量含义。

### 7.6 采集数据

1. 使用可识别的名称，例如“项目-设备-动作-日期-序号”。
2. 采集前记录传感器状态、清零情况和测试动作。
3. 开始后确认计时和数据刷新正常。
4. 采集中不要随意切换系统类型、端口或标定参数。
5. 完成动作后停止采集，并立即回放抽查。

若应用允许设置采样频率，应遵循项目要求。界面刷新速度不一定等于实际采集频率，不要仅凭画面流畅度判断数据完整性。

### 7.7 历史回放

1. 按名称或时间找到记录。
2. 检查总时长和关键动作是否完整。
3. 对比采集时记下的事件点。
4. 检查回放中的方向、指标和三维映射是否与实时一致。
5. 删除记录前先确认是否已经完成所需导出和备份。

回放不仅用于展示，也是一项重要的发布前验证工具。目标平台中的 AI Studio 应优先使用真实录制数据进行应用预览。

### 7.8 导出数据

1. 选择正确的历史记录和保存目录。
2. 按项目要求选择导出选项；不同系统的字段可能不同。
3. 等待软件明确返回成功或失败，不要只看目录中是否出现文件。
4. 打开文件，抽查时间、矩阵长度、关键指标、通道名称和中文表头。
5. 多路系统应确认座面、靠背、头枕、左手或右手文件是否齐全。

如果文件无法打开或字段不完整，保留采集名称、系统类型、应用版本、导出目录和错误提示，交给支持人员排查。

### 7.9 用目标态 AI Studio 制作应用

#### 第一步：限定范围

选择一个已验证传感器和一个清楚的用户任务。第一版不要同时引入新硬件、新算法、新模型和新报告。

#### 第二步：生成应用包

AI 根据模板选择页面、组件和操作流程。应用包只描述“使用哪些已批准能力以及怎样组合”，不包含任意底层代码。

#### 第三步：验证结果

至少检查：

- 传感器与通道绑定正确。
- 四角、中心和关键部位方向正确。
- 清零、标定和单位有明确依据。
- 实时、保存、回放和导出结果一致。
- 报警、指标和报告字段符合预期。
- 断线、错误数据和缺少权限时有明确提示。

#### 第四步：批准和发布

发布记录应包含应用包版本、所需内核版本、能力版本、验证数据、检查结果、批准人和回滚版本。

### 7.10 内核升级与应用包更新

“内核不可变”是对客户和 AI 的权限边界，不是说厂商永远不再更新 Shroom Desktop。

- 客户和 AI 不能修改、替换或向内核注入代码。
- 日常界面、流程、品牌和报告变化通过应用包更新。
- 新协议原语、底层算法节点或系统能力只能由厂商开发和验证。
- 厂商可低频发布签名内核升级，并提供兼容检查、迁移说明和回滚路径。
- 应用包版本和内核版本分别管理；安装前必须确认兼容关系。

### 7.11 数据与隐私

- 当前桌面端的数据采集、回放和导出以本地处理为主。
- 目标态 AI Studio 应默认只读取完成生成所必需的资料。
- 未经项目授权，不应把原始传感器数据、协议文档、客户模型或报告上传到云端。
- 如需云端 AI 处理，应明确告知上传内容、用途、保存时间和访问范围，并由客户主动确认。
- 涉及个人、医疗或商业敏感数据时，按客户和所在地要求执行更严格的权限与留存规则。

### 7.12 常见问题排查

| 现象 | 先检查什么 | 不要做什么 |
| --- | --- | --- |
| 找不到串口 | 线缆、供电、驱动、系统设备列表、是否被其他软件占用 | 不要不断重装应用而忽略硬件连接 |
| 已连接但没有画面 | 系统类型、端口、通信速度、设备是否正在发数 | 不要直接开始正式采集 |
| 画面跳动或数据长度异常 | 协议配置、帧完整性、线缆和通信质量 | 不要只靠加平滑掩盖异常 |
| 左右或上下颠倒 | 观察视角、线序、旋转和点位映射 | 不要只修一个视图 |
| 清零后仍有大面积底值 | 是否真正空载、安装应力、清零时机和传感器状态 | 不要把清零当作标定 |
| 回放与实时不一致 | 保存内容、处理顺序、应用版本和参数版本 | 不要继续发布或出报告 |
| 导出失败 | 目录是否可写、磁盘空间、文件是否被占用、错误提示 | 不要重复点击造成多个不完整文件 |
| 三维画面好看但数值可疑 | 数字矩阵、方向检查、标定依据和原始记录 | 不要用视觉效果代替测量验证 |

## 8. 常见问题

### 8.1 Shroom 现在已经是 AI 应用生成平台了吗？

还不是。当前项目的主要可用能力是桌面端的传感器连接、数据处理、可视化、采集、回放和导出，以及用于复用后端链路的 SDK。AI Studio、统一应用包、签名发布和回滚属于目标态。

### 8.2 非技术用户真的可以自己做应用吗？

目标是让不写代码、但懂硬件或业务场景的应用工程师完成大部分组合工作。完全不了解传感器、方向、标定和验收标准的人，仍需要专业人员协助。

### 8.3 AI 会直接修改 Electron 程序吗？

不会。目标平台规定 AI 在桌面内核之外生成受控应用包。应用包不能加入任意可执行代码，也不能扩大桌面程序的权限。

### 8.4 “内核不可变”是否意味着以后永远不能升级？

不是。客户和 AI 不能修改内核；厂商可以低频发布经过测试和签名的升级。升级必须有兼容检查、迁移说明和回滚方案。

### 8.5 AI 能自动接入任何传感器吗？

不能。AI 可以整理协议资料并推荐接入流程，但新的通信协议、线序、点位映射和标定必须由开发者使用真实硬件验证。未验证配置不能进入正式发布。

### 8.6 为什么不能让 AI 直接生成代码，速度不是更快吗？

传感器应用最危险的问题往往不是崩溃，而是输出看似正常却含义错误。限制 AI 只能组合已验证能力，可以缩小错误范围，并让结果能够复现、检查和回滚。

### 8.7 2D 和 3D 画面应该相信哪个？

它们用于回答不同问题，但都应来自同一份正确数据。先用已知按压位置和数字矩阵检查数据，再使用热力图和三维模型理解分布。任何视图不一致都应在发布前解决。

### 8.8 清零和标定是一回事吗？

不是。清零主要去掉当前空载背景；标定是按有依据的方法把读数换算到约定尺度或单位。清零不能代替标定。

### 8.9 当前是否支持所有压力或触觉传感器？

不支持。项目已经覆盖多类床垫、座椅、手套、足底、人体和机器人场景，但不同类型的验证程度不同。正式项目应先确认对应配置是否已经通过真实硬件验收。

### 8.10 Shroom 能离线运行吗？

当前 Shroom Desktop 以本地桌面运行和本地数据处理为主。目标态应用包发布后也应能由兼容桌面内核离线运行。AI 生成过程是否需要网络，取决于未来 Studio 的部署方式和客户策略。

### 8.11 数据会自动上传到云端吗？

当前桌面采集、回放和导出以本地为主。目标态也应默认本地优先；如果 AI Studio 需要上传协议、样例数据或模型，必须明确告知并获得授权。

### 8.12 新项目最快应该从哪里开始？

先选一个已经验证的传感器，找一段真实录制数据，明确一个用户和一个任务，再从最接近的现有模板开始。不要在第一版同时引入新硬件、新算法、新模型和新报告。

### 8.13 发现应用包缺少能力怎么办？

停止发布并创建能力接入任务。由应用工程师补充需求、协议和验收资料，开发者完成实现与真实硬件验证，审核通过后再进入能力中心。不要在客户应用里加入临时底层代码绕过平台规则。

### 8.14 怎样判断一套应用可以交付？

至少满足：真实硬件连接稳定；方向和点位正确；清零和标定有依据；实时、保存、回放、导出一致；异常有明确提示；版本和批准记录完整；能够恢复到上一可用版本。

### 8.15 Shroom 可以直接用于医疗诊断或自动安全控制吗？

本文没有作出这类承诺。涉及医疗诊断、安全控制或受监管用途时，必须由相应专业人员完成验证，并满足适用法规、质量体系和客户审批要求；AI 不能自主发布相关结论。

---

**平台定位总结**

Shroom 的目标不是让每个客户都得到一套新的代码，而是让每个新项目都沉淀为下一次可复用的能力：稳定内核保证数据链路可信，能力中心保证零件经过验证，AI Studio 加快需求表达和组合，应用包让交付可以预览、批准、安装和回滚。
