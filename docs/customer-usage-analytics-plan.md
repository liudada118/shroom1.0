# Shroom 客户功能使用分析方案

日期：2026-09-24。状态：设计草案，尚未接入采集、部署服务或上传数据。

## 1. 要支持的产品决策

主要问题是哪些客户在使用哪些功能、使用是否持续、在哪里遇到阻碍。按客户公司统计为主，安装实例为辅；没有个人登录时，不把安装实例当成一个真实用户。

| 想知道什么 | 需要看到的信息 | 可以采取的行动 |
| --- | --- | --- |
| 每家客户在用什么 | 系统类型、功能使用次数、活跃天数、最近使用时间 | 针对实际场景沟通需求 |
| 哪些功能值得继续投入 | 使用客户数、可用客户中的使用比例、跨周复用 | 决定迭代优先级 |
| 功能为什么用得少 | 功能可用 → 入口可见 → 尝试 → 成功 → 再次使用 | 分别检查入口、流程、可靠性和实际价值 |
| 客户如何完成工作 | 连接、监测、采集、算法、回放、导出的操作路径 | 改善常见工作流程 |
| 客户是否减少使用 | 与该客户历史相比的活跃天数、有效任务变化 | 结合联网覆盖和客户反馈判断是否需要跟进 |
| 新版本有没有改善使用 | 按版本、系统类型和客户分组的成功率、复用率 | 判断发布后的效果，不能仅凭相关性归因 |

行为数据解释发生了什么；放弃的原因仍需客户反馈。采集历史不能从接入前的空白数据中恢复。

## 2. 身份与现有基础

[Agent 聊天同步接口](agent-chat-sync-api.md) 已记录软件授权与客户公司的服务端关联方式，以及随机 installationId 和离线队列契约。本方案仅参考身份、确认与重试模式；功能统计需要独立的数据范围、开关和接口，不能沿用聊天同步授权自动开启。

- customerId：由自己的服务器鉴权后确定；显示名称来自客户管理记录，不信任客户端自报公司名。
- installationId：随机安装实例标识，正常升级保持；不是硬件序列号，也不代表具体员工。重装可能生成新实例。
- sessionId：一次运行会话；operationId：一次具体操作，用于关联开始与结果。
- 换授权时隔离待传数据，保留事件产生时的归属；不得把旧客户事件归给新客户。
- 第三方分析平台只接收不透明客户/安装标识；软件密钥和请求鉴权头不进入事件属性。

## 3. 第一版事件范围

统一字段：schemaVersion、eventId、eventName、occurredAt、installationId、sessionId、appVersion、environment；按需包含 operationId、featureId、systemType、systemOrigin、algorithmId、result、durationMs、errorCode。服务器补 receivedAt 与 customerId。

systemOrigin 区分内置、内置副本和自定义。featureId 等采用稳定枚举；自定义系统名、算法代码和其他自由文本不直接进入统计。开发、测试、演示数据单独标记，默认排除正式客户报表。

| 事件 | 触发时机/语义 | 回答的问题 |
| --- | --- | --- |
| app_session_started | 应用可用后一次 | 活跃安装、版本分布、最近使用 |
| feature_availability_snapshot | 会话首次就绪及授权/配置变化，记录实际可用功能 | 哪些客户有机会使用该功能 |
| feature_exposed | 功能入口实际可见，每会话/功能去重 | 有功能但没有发现入口？ |
| feature_attempted | 客户明确发起，带 operationId | 客户是否尝试使用？ |
| system_entered | 真实工作区就绪，非预览卡片点击 | 客户主要使用哪种展示系统？ |
| device_connection_result | 连接尝试终态，带成功/失败/取消及耗时 | 连接能否完成？ |
| monitoring_usage_summary | 定期提交时段增量，区分实时/回放、前台/后台 | 实际监测时长与软件打开时长的差异 |
| collection_started | 后端确认采集开始 | 是否进入采集工作流？ |
| collection_finished | 后端确认结束，含成功/失败/取消、时长和帧数量摘要 | 是否完成有效采集？ |
| export_result | 实际导出终态，格式、记录数量、耗时 | 客户是否把结果导出去？ |
| playback_started | 回放真正开始 | 历史数据功能是否被使用？ |
| algorithm_result | 算法首次输出或启用失败，固定 ID 与内置/自定义类型 | 哪些算法被真正用上？ |
| analysis_tool_used | 框选、量尺、图表等完成一次有效动作 | 辅助工具的实际价值 |
| custom_system_saved | 新建/复制/修改成功 | 客户是否在配置自己的系统？ |
| agent_task_result | 任务终态，只有预定义类别、成功状态和耗时 | Agent 是否帮助完成工作？ |
| usage_session_summary | 定期或正常结束提交去重增量 | 交互时长、监测时长、采集时长 |

前端负责入口可见与交互事件，业务结果在确认结果的所属层记录一次。通用 feature_attempted 通过 operationId 对齐领域结果，不把点击当成功，不重复上报同一结果。

监测区间仅统计有新鲜有效帧的时段；断流、休眠和退出截断。无人操作的持续采集仍可计入采集时长，但不计成人的交互时长。使用单调时钟测量时长，增量摘要有唯一标识；崩溃后未确认结束的任务记为未知，不默认失败或成功。

## 4. 指标与计算口径

统计时区默认 Asia/Shanghai。周采用自然周；趋势比较完整周期。下面的目标和预警是试运行建议，不是已有业务基线。

暂定核心指标：每周有有效核心使用的客户数。有效使用包括实时监测累计至少 5 分钟、成功结束且有数据的采集、有效历史回放或成功导出之一。5 分钟只是初始分析阈值，需要按客户的短测量/长监测场景校准。

统计人群限定为支持该事件版本、启用使用统计且有可观测数据的客户。始终显示可观测客户数与全部交付客户数，不把未上传客户直接算成未使用客户。

| 层级/指标 | 定义与数据源 | 展示方式 | 初期目标 | 预警/调查条件 |
| --- | --- | --- | --- | --- |
| 核心：周有效使用客户数 | 一周内满足上述有效使用条件的去重 customerId | 总数与周趋势 | 前 2–4 周建立基线 | 明显低于同范围历史时人工检查，先排除上传/版本变化 |
| 输入：功能客户使用率 | 周内有效使用功能的客户数 / 周内活跃且当时拥有该功能的客户数；来自可用快照和业务结果 | 功能排行与比例，同时显示分子/分母 | 找出覆盖低但值得验证的功能 | 不设全功能统一阈值 |
| 输入：发现率 | 周内实际看到入口的客户数 / 周内活跃且功能可用客户数 | 功能漏斗 | 建立各入口基线 | 使用率低时先检查发现率 |
| 输入：尝试成功率 | 同一 operationId 成功数 / 已到观察截止的尝试数；取消、失败、未知单列 | 漏斗与结果堆叠 | 基线后按功能设目标 | 试行：至少 30 次尝试，成功率比前 4 个完整周下降 10 个百分点时人工调查 |
| 输入：跨周复用率 | 首次成功使用某功能的一周客户群中，下一周仍成功使用的客户数 / 首次成功客户数；仅观察已满一周且功能仍可用的客户 | 客户群留存表 | 判断尝试是否转成稳定使用 | 少样本显示原始人数，不推断趋势；失去观测的客户单列 |
| 输入：有效使用天数 | 每客户/周满足核心使用条件的日期数 | 客户列表与趋势 | 区分偶发测试和持续使用 | 仅对历史持续使用客户分析变化 |
| 健康：业务失败率 | 确认失败操作数 / 有明确终态操作数；按功能、版本、系统类型拆分 | 趋势、失败码排行 | 建立可靠性基线 | 与成功率调查一起处理 |
| 健康：数据覆盖/延迟 | 支持版本与统计启用的客户覆盖；receivedAt − occurredAt 的延迟分布、客户端队列丢弃计数 | 报表顶部覆盖提示 | 让使用率结论有可解释范围 | 试行：覆盖骤降或延迟 P95 超过 24 小时先排查上报链路；识别客户端时钟偏差 |
| 商业：续约关联 | 有合同/续约数据后比较功能使用与续约客户群 | 客户群对比，后续阶段 | 本期不设收入指标 | 无数据时显示未接入，不推算收入、流失或付费意愿 |

## 5. 两张主看板

### 总览：决定功能投入

- 顶部：统计范围、覆盖客户数、周有效使用客户数、版本分布。
- 功能表：功能、可用客户数、使用客户数、使用率、成功率、跨周复用率。
- 客户 × 功能矩阵：按系统类型/版本筛选，每格展示使用天数或成功次数；无权限、无数据、未使用分别显示。
- 流程漏斗：连接 → 监测 → 采集 → 导出，按同一会话/操作关联；不是所有客户都需要导出，因此允许按目标工作流分群，不把仅监测视为失败。
- 版本对比：先控制客户类型、系统和观测周期差异，再分析变化。

### 客户详情：了解每家客户

- 最近一次可观测使用、使用版本、安装实例数、常用展示系统。
- 最近 7/30 天使用日历、前台交互/实时监测/后台采集时长。
- 常用功能、首次尝试的新功能、成功/失败/取消/未知次数。
- 最近操作时间线，例如“进入系统 → 连接成功 → 采集 → 导出完成”。
- 一次使用后未复用的功能、目前可用但未观察到使用的功能。
- 数据覆盖与延迟提示；安装设备共享时，页面明确无法识别具体员工。

## 6. 实现与产品范围

建议拓扑：Shroom 统一事件接口 → 有界离线队列 → 自有 HTTPS 接收接口（鉴权、归属、白名单、去重）→ 事件存储与统计 → 客户后台。

现有客户后台适合承载客户详情和固定功能表；需要灵活探索漏斗、留存和路径时，可评估 PostHog。官方能力参考：[分析类型](https://posthog.com/docs/product-analytics/insights)、[漏斗](https://posthog.com/docs/product-analytics/funnels)。工具选择不会替代事件语义设计。

- 面向客户说明收集范围，提供独立的使用统计设置；关闭后停止新采集和发送，并明确处理待传事件。
- 默认仅收集功能 ID、结果、次数、时长和必要环境字段。Agent 仅记录任务类型/状态，不读取聊天正文；不传压力矩阵、文件内容、完整路径、客户自定义文本或密钥。
- 第一版不启用屏幕录制或全量点击自动采集；重要动作显式记录，避免大量噪声。
- 异步批量上传，设置队列容量、有效期、指数退避和幂等确认；重要流程不等待网络。断网摘要可能延迟或因队列上限丢弃，看板应反映覆盖限制。
- 服务端按事件白名单校验；查看客户明细的后台账号应有相应权限。
- 保留期限初步建议为原始事件 90 天、日汇总 12 个月，实施前按实际分析需要确定。

## 7. 落地与复盘

实施采用自有接收接口与现有客户后台。先完成一条可核对的端到端流程，再增加覆盖范围。以下模块名、接口和表名是拟议新增内容，不表示已经存在。

### 阶段一：固定事件语义与身份

- 把第 3 节整理成事件字典：固定名称、允许字段、触发点、来源层、成功含义、去重方式和引入版本。
- 明确 company/customer 与安装实例的关系：客户归属由服务端确认，安装 ID 随机生成并保留；没有员工账号不生成虚假的个人用户数。
- 试点选“进入真实系统 → 连接设备 → 开始采集 → 结束采集 → 导出结果”；各操作使用 operationId，整次运行使用 sessionId。
- 为功能可用和入口可见保留不同事件，后续分析分母基于实际可用客户。
- 服务端代码根据现有文档位于 E:/key；正式编码前需读取该仓库的任务规则、身份模型、数据库迁移和后台页面入口。本次尚未检查该仓库。

交付：事件字典、请求/回执样例、身份和时间口径。验收：同一个动作由哪层报告、什么算成功都有唯一明确答案。

### 阶段二：新增客户端统一采集与发送层

拟议模块边界：

| 位置 | 工作内容 |
| --- | --- |
| client/src/services/usageAnalytics.js | 提供有限的 track 接口；通过专用 preload 方法提交 UI 事件，普通浏览器开发态可用测试适配器 |
| app/electron/preload.js | 增加独立 usage 命名空间，仅暴露记录、设置和状态；不提供任意 URL/凭据访问 |
| app/electron/usageAnalytics.js | 初始化安装身份、设置、可信窗口 IPC 校验、发送器及退出清理 |
| backend/extensions/usage-analytics/ | 事件白名单、业务事件桥、去重、时长摘要及有界队列；业务层只提交有限字段 |
| Electron 与后端组合根 | 装配事件订阅和生命周期；保持 backend/runtime/index.js 冻结导出不变 |

主进程负责上传。当前后端同进程运行，业务完成事件通过应用内部桥交给发送器；独立 Agent 通过已有进程消息边界提取任务终态。关闭统计或发送器不可用时业务事件为安全空操作；发送器故障不能改变业务结果。

已查代码：backend/agent-runtime/chatSync.js 使用按会话保留最新快照和 writeJsonAtomic 的策略。功能事件必须逐次保留，不直接复用整套聊天队列，也不在业务调用中同步重写整份日志。

- 队列放在 userData 下独立 usage-analytics 目录；采用异步串行追加的有界分段文件，不写入采集数据库。
- 初始建议每 30 秒或累积 50 条触发批次，批次和单事件另设字节上限；这是待压测配置，不是性能承诺。
- 为事件在产生时固定来源范围，按上传目的地和授权范围隔离文件；旧授权队列不得用新客户凭证发送。服务端保存事件确认归属，不因以后公司绑定变化静默迁移历史。
- 网络失败使用退避重试；成功回执确认到 eventId 后才能清理。关闭统计停止新采集和发送，清除待传使用统计；已经送达的数据遵循服务端保留/删除机制。
- 容量、保留期、退出等待都有上限；监测摘要定期保存，异常终止最多损失未持久化窗口，报表不承诺完整无损。

交付：客户端可在本机检查事件和队列状态。验收：记录一次操作只产生规定事件；断网、关闭统计和队列写入失败均不阻断采集。

### 阶段三：接收接口与最小端到端流程

在已有客户服务中拟增 POST /api/usage/events/batch：鉴权 → 解析客户来源 → 校验字段与大小 → 持久化/去重 → 返回逐事件确认。鉴权流程沿用已核验的服务端客户映射模式，但需独立支持此接口；客户端只向指定官方 HTTPS 地址发送授权凭据，禁止重定向转发。

最小数据模型：

- usage_installations：按客户来源范围关联安装 ID、首次/最近观测、版本和统计能力。
- usage_events：原始业务事件、事件发生时间与接收时间、当时归属；来源范围 + installationId + eventId 唯一。重复请求不重复入库，相同身份但不同正文视为冲突。
- usage_feature_daily：可重建的按客户、日期、功能汇总。由已去重原始事件聚合；离线迟到事件触发相关日期重算，避免补传重复累加。

初期保留原始事件供核对，按当前数据库能力实现，不先引入消息中间件和新分析数据库。统计客户级时長时明确多设备时长是相加还是区间去重，页面标明口径。

先提供受权限保护的内部事件列表，跑通阶段一的试点流程。服务端先部署兼容接口，客户端再发试点版本；实际部署和客户分发另行授权。

交付：一台测试安装的操作出现在正确客户的事件列表中。验收：同公司两台安装可区分、换客户不串数据、重复补传不增加次数、晚到事件更新正确日期。

### 阶段四：完成第一版客户后台与事件覆盖

- 增加“使用分析”总览：客户 × 功能表、使用客户数、活跃天数、最近使用、版本与系统筛选。
- 客户详情增加“软件使用”：安装实例、常用功能、监测/采集时长和操作时间线。
- 在端到端流程稳定后扩展回放、算法、框选/量尺/图表、自定义系统、Agent；业务动作成功后记录，避免随每帧渲染或每条流式输出埋点。
- 最后增加功能曝光与复用分析，显示功能不可用、未观测、未使用三个不同状态。多步操作通过 sessionId/operationId 关联，不能把不同日期的不相关动作拼成一次完成流程。

交付：第 5 节两张主看板。验收：人工执行给定操作脚本，逐项核对客户、功能、次数、状态和时长；只监测的客户不会被算成导出流程失败。

### 阶段五：验证与分批上线

局部开发先验证事件语义、队列和统计查询；集成涉及 Electron、身份鉴权和跨层接入，按仓库要求执行 scripts/verify-changed.ps1 -Mode Full，构建产物写入系统临时目录。服务端另按 E:/key 的验证规则执行。

重点场景：真实安装包 IPC、断网/重启补传、回执丢失、重复/冲突事件、换授权、关闭统计、休眠/断流、应用崩溃未知终态、低磁盘、开发测试数据隔离及后台访问权限。对比启用前后的采集率、显示率、事件循环延迟和存储积压；真实性能结论需要真实设备负载。
