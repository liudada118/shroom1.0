# Shroom 算法交易平台产品反驳评审

评审日期：2026-10-20。评审对象：[算法交易平台 PRD](PRD-Shroom-算法交易平台.md) 0.1 版。

核心判断：这份 PRD 已较完整地安排交易、权益和售后，当前最需要验证的是交易平台能带来多少额外价值。卖出自营算法、接到定制项目、完成第三方标准商品交易，分别证明不同的业务能力，不能用同一组订单共同证明平台成立。

算法类型开放、自营加邀请卖家，以及既有软件到期权益均按已确认方向评审。以下反例用于检验产品假设，不代表真实事故或已经确认的代码缺陷。补充建议供讨论，不改动原 PRD 或既有规则。

## 一 最需要挑战的十项假设

### R1 有付费订单 还需要证明平台带来了额外价值

**原文依据**：第四章建议约 3 家供给方、6 个商品、5 家需求企业，争取 3 笔付费订单、覆盖 2 个买家组织；第八章已安排人工撮合与小额试点，并明确小样本不能推断全市场。

因此不应反驳样本少就没有探索价值。真正的问题是这些订单分别证明了什么。

**反例**：三笔订单全部来自已有设备客户，由原交付员工推荐、自营团队适配、原商务人员收款。订单真实且客户满意，能证明算法销售有需求；没有证明引入外部卖家、商品目录、独立采购及分成结算比现有交付流程更有价值。

**补充**：试点订单分别标记自营、第三方标准商品和定制服务，记录线索来源、既有成交关系、平台提供的服务、人工接管与支持投入。比较同类任务通过现有销售交付方式完成的成本和结果。试点允许形成自营收入，但进入第三方交易建设阶段应有对应的第三方成交与交付证据。

平台单均贡献为正时，还需对照观察期内的总贡献与持续运营投入。试点前确定资源上限、观察窗口和继续投入条件；不要求少量订单立即摊平初期研发，也不能用每单正贡献代替平台整体可持续性的验证。

**证伪信号**：买家始终需要原交付人员完成选择，卖家只获得已有项目转单，平台新增流程未减少任何一方投入。此时应继续优化销售与交付，暂缓扩大交易基础设施。

### R2 复购与跨客户复用应分开证明

**原文依据**：4.1 将同一算法被不同买家有效使用，或独立买家追加采购，作为复用性证据；4.2 已要求人工定制另计。

**反驳**：追加采购可能购买了其他算法、更多电脑许可或新的定制服务，并不必然证明原算法可复用。“同一商品”也可能在每次交付中暗含不同模型、映射或参数适配。

**反例**：两个客户都购买商品 A，但第二单需要重新标注、训练和大量调参。商品 ID 相同、成交数增加，仍可能是一门持续按客户开发的服务业务。

**补充**：分别记录新增组织使用、席位扩购、同品续费、跨品购买与定制复购。核对实际执行版本、模型或配置变化、客户适配工时及约定支持期的投入。允许配置化适配，但需要用真实工时证明复用降低了边际投入，不能仅靠一个商品名称判断。

**证伪信号**：每个新买家都需要接近重新开发的投入。此时优先按定制服务报价和验收，继续寻找可以抽取为标准商品的部分。

### R3 可包装成商品的算法 不一定值得单独收费

**原文依据**：第五章候选包括动作识别、接触状态、时序特征和历史差异；6.2 已区分免费、自营收费和第三方收费；7.13 允许 Agent 查找及推荐商品。

**反驳**：付费算法需要相对客户当前做法提供可说明的增量。尤其已确认由 Agent 围绕具体问题组织分析，一部分需求可能由现有指标和通用计算完成，客户无需另购商品。

**反例**：客户只问两条记录的均值与峰值差异，已有工具可以计算。Agent 推荐收费比较算法，却说不清额外价值，容易让客户感到基础能力被再次收费。

**补充**：Agent 理解问题后，先核对已有权益与免费能力；可以完成就直接完成。推荐付费商品时说明新增能力、效果证据、适用限制、额外成本及可行替代方式。特殊模型、验证与维护可以成为价值来源，但要由试用证明，而非由商品标签证明。

**证伪信号**：客户得知已有功能足够后拒绝购买，或者卖家主要靠隐藏基础替代方案成交。应调整付费边界及选品，不能依赖推荐入口扩大收费。

### R4 买家能够启动试用 不代表能够评价试用结果

**原文依据**：7.4 已要求输入契约、效果证据及适用限制；7.5 支持自有数据试用；4.2 定义预登记任务的有效完成；7.10 按购买时数据条件与证据处理争议。

这些防护方向正确，但还需要回答评价条件如何获得。

**反例**：动作识别算法能安装、有输出，买家却没有代表性标签或可核对的目标，无法判断未知结果和错分是否可接受。试用结束后没有购买，不一定是商品无效，也可能是根本没有完成有效评价。

**补充**：在兼容预检之外增加可评价条件：任务目标、代表性数据、参照或标签、可接受结果，以及验证责任人。缺少条件时先进入样例体验或验证支持，不把能运行标记为效果通过。报告区分环境兼容、执行成功、效果达到约定标准与最终业务任务完成。

**证伪信号**：多数试用需要平台员工重新收集、标注和解释数据才能判定价值。此时验证服务是交易的重要组成部分，需要明确范围、费用及责任，不能作为无成本的免费试用隐含提供。

### R5 平台单均贡献之外 还要验证卖家是否值得持续维护

**原文依据**：4.2 已定义平台单均贡献，自营与第三方分开核算；6.2 的 80% 与 20% 明确只是测算样例；7.11 已提供分成和结算口径。

**反驳**：即使试点平台单均贡献为正，邀请卖家的持续参与仍需独立验证。卖家还承担接入格式、整理证据、适配依赖、更新测试、售后和等待结算的投入，这些可能高于减少重复对接带来的收益。

**反例**：卖家首单有收入，但后续持续维护多套客户环境，每次宿主变化都要重新验证，最终不愿意继续提交新版。目录仍有商品，实际维护能力逐渐消失。

**补充**：除逐单结算外，记录卖家接入投入、每新增客户的适配与支持时间、版本维护、结算等待和再次上架意愿。平台费随实际承担的获客、验证、分发和售后服务测算；对自营算法另记研发与持续维护投入。

**证伪信号**：卖家成交后不再愿意接入第二个商品或支持新客户。先改善接入和维护成本，或调整服务分工，再扩大邀请名单。

### R6 自营商品与平台裁定存在需要明确处理的利益冲突

**原文依据**：第二章有自营算法团队、技术审核与争议运营；第 33 行要求同一企业不能审核自己的商品或裁定自己的争议。

**反驳**：自营团队与平台审核、售后如果属于同一企业，按当前文字理解，就会遇到自己的商品由谁审核、自己的争议由谁裁定的问题。不同员工执行可以减少直接冲突，却不自动满足“同一企业不能”的表述。

**反例**：自营商品效果争议由平台否决，第三方卖家又发现自营商品获得更靠前的推荐。即使结论有依据，买卖双方仍需要能够核对适用规则是否一致。

**补充**：明确哪些环节由不同负责人复核，使用统一的证据要求并留存理由；自营争议设置回避与升级处理办法。推荐区分兼容和效果依据、商业推广及自营身份。无需要求每笔订单引入外部裁定，但应准确界定内部复核能够解决的范围及重大争议处理方式。

**证伪信号**：同类问题因卖家身份不同采用不同验收、退款或排序规则。先修正规则与执行，再扩大第三方供给。

### R7 客户数据不离机时 效果争议需要可执行的复核办法

**原文依据**：7.12 不默认授权卖家读取原库；本机算法以本地运行为主；7.10 要求按数据条件和执行证据裁定；7.14 要求保留运行依据。

**反驳**：保护客户原始数据与售后需要证据可以同时成立，但需要具体工作流。仅规定双方举证，无法保证卖家有能力诊断，也无法保证买家能够说明问题。

**反例**：算法在客户本机持续误判，卖家在样例上正常，客户又不能提供原始数据。订单金额被冻结，但双方无法取得足够信息来区分配置错误、范围外输入或算法问题。

**补充**：商品上架时定义诊断所需的最小信息、客户本机复核方式和明确限制。先提供不含原始数据的版本、配置、输入质量、运行错误和评价摘要；仍不能裁定时，再由客户选择是否提供必要样本或接受受限支持。购买前约定无法取得证据时的处理办法，不能无限冻结或要求客户默认上传全部原库。

诊断信息的生成与发送仍遵守既有到期、数据读取和上传规则，不能为售后暗设导出例外。若某条复核路径需要新增权限或与当前限制冲突，应先明确决策，再作为支持承诺使用。

**证伪信号**：效果争议反复停留在双方无法举证。应调整商品适用范围、验证支持和退款责任，而不是继续依赖人工协调。

### R8 双重授权已经说清 还需要验证客户是否接受完整使用成本

**原文依据**：7.7 保留已确认的软件到期规则，给出软件与算法权益矩阵，并要求购买前披露宿主依赖；8.4 将宿主依赖列为待决策。

这里不建议更改已确认的到期规则。质疑的是买家愿不愿接受这种商品组合。

**反例**：买家购买年期算法，宿主软件两个月后到期。算法仍能对历史记录运行，但数据和分析结果不能导出；如果买家的实际任务需要提交报告，仅算法许可仍无法完成该任务。

**补充**：购买或报价时展示完成客户目标任务所需的整体权益、期限重叠与额外续期成本，不仅提供技术性的到期提示。用包含宿主、算法和实际支持的完整报价验证购买意愿；记录因权益组合导致的未成交或续费退出。商品若允许独立系统调用，则按照既有 PRD 的独立 SKU 探索，不默认改变 Shroom 内的限制。

**证伪信号**：客户愿付算法费，却普遍拒绝完整权益组合。应重新评估报价与服务安排；披露充分本身不能证明商业接受度。

### R9 本机包优先应由首批交易条件支持

**原文依据**：概要和第八章建议本机包先形成标准闭环，同时允许云试点和人工定制；7.6 已明确现有内置 Python 不等于任意第三方代码已安全隔离；7.12 已承认本机保护不绝对。

**反驳**：类型开放无需收缩，但首发执行格式也不能只因为已有本机入口就确定。客户是否允许数据离机、卖家是否接受本机交付、执行格式是否可以安全接入，共同决定最先可以成交的商品。

**反例**：首批客户需要本地数据处理，邀请卖家却不接受当前本机分发方式，或者现有执行格式无法约束其依赖与行为。商品目录和支付先完成，实际没有可以安全交付的第三方商品。

**补充**：用真实候选商品同时核对买家数据条件、卖家交付意愿、执行格式准入和维护成本。按结果决定哪类商品先跑通。每种开放的执行格式单独通过相应隔离与稳定性验收，不能以首个自营包可运行覆盖其他第三方格式。

**证伪信号**：首批买卖双方无法接受同一种交付方式，或安全接入成本高于可验证交易收益。保留类型探索，调整首发商品与节奏。

### R10 固定试用次数需要先明确何时算真正开始

**原文依据**：7.5 建议每组织每商品一次可审计试用，时长、电脑数与输出按 SKU 确认；7.4 允许未验证状态，明确不匹配时拒绝。

**反驳**：如果完成环境准备和验证数据的成本由用户承担，试用规则可能让客户在取得有效评价之前消耗掉唯一机会。

**反例**：买家启动试用后发现宿主依赖、数据阶段或配置需要修正。修复后却已到期，必须付费才能真正验证；卖家修复版本后是否可重新试用，也没有明确规则。

**补充**：区分样例体验、环境预检、验证准备和正式试用。正式次数与时限从明确的事件开始计算，对平台或卖家原因导致的失败、关键修复版本和中断恢复规定处理办法，保留审计以控制重复滥用。不要用一次试用限制代替评价机会的定义。

**证伪信号**：大量试用退出来自未准备好或故障耗时，转化率既无法衡量效果，也损害交易信任。先修试用机制，再解释转化数据。

## 二 下一轮验证怎样更有说服力

原 PRD 已有先验证、再建设的阶段安排。建议补足下表的证据，不额外编造市场规模、费率或统一成交目标。样本继续用于发现问题，阶段扩大条件在试点开始前确认。

| 验证问题 | 最小可行动作 | 应留下的证据 | 不成立时的处理 |
| --- | --- | --- | --- |
| 客户为何要额外付费 | 比较当前办法、已有能力及付费方案 | 客户具体问题、替代方式、接受或拒绝完整报价的理由 | 调整选品和付费边界 |
| 平台贡献了什么 | 对照现有销售交付方式完成同类任务 | 线索、匹配、试用、支持投入和有效结果 | 保留销售交付业务，暂缓扩大平台建设 |
| 是否可以跨客户复用 | 同一实际算法能力向独立买家交付 | 版本与模型变化、适配工时及后续维护 | 按定制项目处理，继续抽取共用能力 |
| 试用能否判定效果 | 在试用前确认评价数据、任务与标准 | 条件检查、执行结果、效果判定与未能评价原因 | 补验证支持或收缩商品声明 |
| 卖家能否持续供给 | 核对首单至支持期的全部投入 | 接入、维护、结算等待及后续供给意愿 | 改善成本和责任分工 |
| 能否交付第三方商品 | 选定实际执行格式并做准入 | 签名、许可、隔离、依赖和资源限制证据 | 不开放未通过格式的收费交付 |
| 能否处理真实争议 | 演练或复核本地数据不离机的效果问题 | 所需证据、取得方式、时限和裁定依据 | 修订验证、支持与退款规则 |

建议为每个候选商品建立简短记录：买家任务、替代办法、卖家能力、实际交付版本、报价和完整依赖、评价方式、平台服务、适配与支持投入、最终结果。这样既能区分服务业务与标准商品，也不会用全平台总订单数掩盖不同类型的障碍。

## 三 必须在对应交易前关闭的风险

以下是建议责任角色和完成节点，不是已确认排期。可以继续探索其他方向，不要求所有事项同时完成后才做客户访谈或演示。

| 风险 | 建议牵头角色 | 必须完成的结果 | 完成节点 |
| --- | --- | --- | --- |
| 付费价值与试用无法判定 R3 R4 R10 | 产品、算法与交付 | 可评价条件、付费增量及有效试用规则 | 对应商品公开付费试用前 |
| 自营复核与争议冲突 R6 | 平台运营与产品负责人 | 自营商品复核、回避和争议升级规则 | 对应自营交易开放前 |
| 客户不出原始数据时无法复核 R7 | 支持、算法与卖家 | 最小诊断证据、本机检查及无法举证时的处置 | 对应商品收费前 |
| 双重授权导致任务无法完成 R8 | 产品与商务 | 完整权益报价、期限说明及接受度验证 | 对应商品下单前 |
| 第三方执行尚未具备交付条件 R9 | 运行时与技术审核负责人 | 特定格式的安全、资源、依赖及许可验收 | 该格式收费分发前 |
| 平台与供给无法持续 R1 R2 R5 | 产品、运营与商务 | 第三方交易增量、跨客户复用与双方投入记录 | 扩大卖家和平台建设前 |

商品数量、开发者工作台与自动化程度可在上述证据出现后扩展。订单、权益、支付、售后和账目证据仍须保持可核对，人工试点不等于省去必要记录。

## 四 不宜过度投入的担忧

- **必须一开始限定一种算法**：类型开放本身不是错误。按任务与交付类型分别验证，避免把三个方向的不同结果合并成一个平台成功率即可。
- **必须有很多卖家才值得开始**：邀请制足以支持探索。要检查的是具体买家问题能否匹配到可交付能力，而非单纯增加目录规模。
- **必须第一天支持全自动支付和结算**：PRD 已允许人工采购、对账与结算。先保留可核对记录，自动化由实际工作量驱动。
- **本机算法必须绝对防复制才可售卖**：原 PRD 已正确说明保护边界。实际卖家能否接受相应交付方式，比追求绝对承诺更需要验证。
- **必须逐场景开发完整报告页**：沿用已确认的对话式分析方向，由 Agent 根据具体问题组织已有能力。市场负责补足值得购买的能力，不要求所有问题都进入购物流程。

## 五 仍需证据的关键假设

| 假设 | 当前评审判断 | 具体怎样检验 |
| --- | --- | --- |
| 客户愿为超出现有能力的算法单独付费 | 待验证，不能由已有设备客户数量推出 | 比较已有能力与完整付费报价，记录真实接受和拒绝原因 |
| 同一执行能力能以较低额外投入交付其他客户 | 待验证，复购口径尚不能单独证明 | 记录实际版本、适配与维护投入，区分标准商品和项目服务 |
| 邀请卖家愿在分成后持续维护 | 待验证，完成入驻不代表会持续供给 | 跟踪首单和支持期投入，以及后续接入与维护行为 |
| 客户具备有效评价所需的数据与参照 | 待验证，安装兼容与评价能力是不同条件 | 在正式试用前检查数据、目标、标准与评价负责人 |
| 目录与 Agent 推荐能减少匹配和交付投入 | 待验证，聊天和浏览量不能单独证明 | 与现有人工流程比较任务完成、用户准备和支持投入 |
| 原始数据不外发时也能处理效果争议 | 待验证，需要实际演练 | 用最小诊断信息和本机复核走完一次有争议的任务 |

## 六 建议的产品推进判断

继续使用现有客户和邀请卖家做受控交易探索，保留开放的算法类型。下一版 PRD 应优先补充商品为什么值得购买、试用怎样评价、真实复用怎样识别，以及平台相对现有交付方式贡献了什么。

如果目前证据主要来自自营和人工定制，可以继续经营这些业务，同时保持第三方平台建设受控；这不必被解释为产品失败。只有当匹配、复用、双方投入和售后处置得到对应证据后，扩大交易平台才有更明确的依据。
