## 1 产品只抓一条主线

**Shroom 帮客户把传感器数据变成能解释、能复核的结果。**

1. **连接设备**：确认数据有效，通道与实际传感器对应。
2. **采集保存**：把数据与必要配置保存在本机。
3. **查看回放**：看实时变化，也能重看历史记录。
4. **聊天分析**：客户提具体问题，Agent 调用已支持的工具解决。
5. **按权限交付**：需要时生成比较、判断或报告，按权益决定能否导出。

例如：“这两次采集有什么差异？”Agent 只补问缺少的信息，复用已明确的数据范围；有评价标准才判断“更好”或“合格”。结论要说明数据、方法和依据；证据不足就说明限制。

**不为每个场景预建一套比较、判断和报告页面，也不要求每次回答都出报告。**

优先使用已有、免费或已购能力解决原问题。扩大目标、增加费用或向新接收方发送数据，需要相应授权；已有授权范围内直接推进。

详细规则：[对话分析与报告](客户端与服务端协同设计说明-v1.6.md#通过对话按需完成分析与报告)。

## 2 正常到期后怎么办

**已确认：立即停采，保留原库；能回放、能分析，不能导出。**

| 动作 | 正常到期后 |
| --- | --- |
| 新增采集 | 立即停止，无宽限期；断网或休眠不延长期限 |
| 到期前已收到、尚未写完的数据 | 继续写入当前采集数据库，不丢弃、不因到期换库 |
| 查看历史、回放、Agent 分析已有记录 | 允许 |
| 在软件内查看分析和报告内容 | 允许 |
| 导出数据、分析结果、报告或备份文件 | 禁止 |

**执行要求，待实现核对与验收：** 文件在最终交付时核验导出权限，不能靠提前提交任务绕过到期限制。已交付和原有文件不删；内部数据库保存、必要分析留痕照常进行。批量任务要说明哪些已交付、哪些受阻。

此规则针对**正常到期**。吊销、解绑、凭证异常等情况仍需单独决策。

详细规则：[到期收尾](客户端与服务端协同设计说明-v1.6.md#运行中授权失效与数据收尾)、[导出最终交付](客户端与服务端协同设计说明-v1.6.md#文件导出最终交付边界)。

## 3 客户端、Agent、服务端各管什么

| 角色 | 主要职责 |
| --- | --- |
| 客户端界面 | 连接、采集、显示、回放、聊天与结果查看 |
| 本地后端 | 处理设备数据、存储、计算和权限检查 |
| 内置 Agent | 理解问题、选择数据和已有工具、解释结果；不能虚构能力或越权 |
| 配套服务端 | 管理授权、公司系统交付、更新及获准上传的信息 |
| 算法供给方 | 提供扩展能力、说明适用条件，承担约定的交付与维护责任 |

**核心数据默认留在本地。** 公司系统制作、审核、签名和授权安装的细节，按现行专项契约执行。

详细规则：[架构与职责](客户端与服务端协同设计说明-v1.6.md#2-总体架构与运行边界)、[系统发布](客户端与服务端协同设计说明-v1.6.md#公司系统制作与发布)。

## 4 实现时守住五条边界

以下汇总完整设计；其中 v1.5、v1.6 新增方案仍待确认与验证。

1. **数据必须能解释。** 区分原始值、相对值和标定值，不凭空标物理单位。记录必要的通道身份、时间与配置；端口连上不代表数据正确，部分可读不代表完整保存。

2. **影响数值的配置不能悄悄变。** 协议、映射、主处理算法和标定等默认停采后修改。采集中归零等操作，只有能保存参考状态及准确生效分段时才开放，否则先停采；待写旧数据沿用旧依据，纯显示设置不一并冻结。

3. **上传要按用途分开。** 模型请求、聊天同步、使用统计和云算法分别说明接收方与授权范围。关闭聊天同步不等于停止模型请求；不自动上传原始数据库、商业源码或密钥。历史队列恢复也按已授权范围处理。

4. **交付检查整个运行组合。** 一起检查客户端、网页、系统包、算法、标定、依赖及权益。软件与算法许可独立，购买算法不等于续期或免除额外调用费。拟要求已保存的最低结果可独立查看，平台更新不能让承诺支持的任务靠重复购买才能恢复。

5. **保存、备份、恢复要有责任人。** 承诺可恢复前，明确保存对象、备份和恢复条件，实际验证回放及结果可读。换机不复制凭证；恢复不自动续期或开放导出。迁移、降级先保护已有及新增数据，不静默覆盖数据库。

按问题查细则：[测量依据](客户端与服务端协同设计说明-v1.6.md#量值等级与测量可信度) · [配置分段](客户端与服务端协同设计说明-v1.6.md#采集中配置变更与生效边界) · [数据安全](客户端与服务端协同设计说明-v1.6.md#7-数据接口与安全边界) · [运行组合](客户端与服务端协同设计说明-v1.6.md#完整运行组合与购买后的连续使用) · [恢复](客户端与服务端协同设计说明-v1.6.md#数据保管与恢复范围)

## 5 下一步：从一个真实问题开始

**算法交易是发展方向。已确认：类型先开放探索，自营加邀请开发者；具体商品、顺序、价格和分成仍待确认。** 不把探索写成已上线能力。

建议按以下顺序推进：

1. **选一个客户问题。** 说清现有办法哪里不够、什么结果算解决；已有能力够用就直接完成。
2. **定一个最小试点。** 一轮可以只验证一个任务、一种交付方式，不要求本地包、云 API、定制服务同时开展。
3. **先查实际依赖。** 设备、数据或运行链路受阻时，不受理依赖它的收费与交付承诺；有证据证明不受影响的任务可继续。候选招募数量不作为强制启动门槛。
4. **算完整投入。** 计入买家的学习、数据准备和复验，卖家的维护，以及平台的人工与费用；同时记录失败、放弃和实际复用。两次成交不能单独证明平台值得建设。
5. **按证据决定继续或暂停。** 先验证试用、交付、结果保存、售后及退款能走通，再决定扩大哪些能力；不得挤占已承诺的主线任务。

每个试点只保留**一份内部任务记录**，贯穿试用、订单和验收，不要求客户反复填表：

| 记录项 | 最少写清 |
| --- | --- |
| 问题与结果 | 谁的问题、可接受结果、评价标准 |
| 数据与范围 | 使用哪些数据、已有授权、依赖与阻断项 |
| 运行与权益 | 版本配置组合、许可期限、额外费用及预算 |
| 证据与交付 | 实际结果、保存位置、恢复条件、导出状态 |
| 责任与节点 | 负责人、验收人、支持边界和下一节点 |

详细规则：[算法探索与交易](客户端与服务端协同设计说明-v1.6.md#8-算法交易与生态发展方向)、[交付验收](客户端与服务端协同设计说明-v1.6.md#9-版本交付运行维护与验收)、[完整待决策清单](客户端与服务端协同设计说明-v1.6.md#10-产品决策与修订记录)。
